    This book is about making things appear on the ZX Spectrum screen — pixels, characters, sprites, scrolling backgrounds — using Z80 assembly language. By the time you reach the final chapter you will be able to draw and move sprites with transparency, scroll the screen smoothly, render text from a custom character set, and keep animation flicker-free. Every one of those techniques is built from the same two operations: writing pixel data to the right memory address, and writing colour data to a corresponding address in the attribute file.

    The book assumes you are comfortable with Z80 basics: registers, arithmetic instructions, jumps, and subroutine calls. If any of those feel uncertain, the companion introduction book covers them thoroughly. What this book adds is the Spectrum-specific knowledge — how the display hardware works, how its memory layout is organised, and how to exploit both efficiently in real graphics code.

    Chapter 1 lays the only foundation the rest of the book needs: how display memory is structured, and how to turn a pixel coordinate into the correct memory address. Everything else follows from that. Read it carefully, work through the examples by hand, and the address formula will feel like second nature within an hour.

    1. The Display File & Memory Map

    [Back to Contents]

    Before you can draw a single pixel, you need to understand the Spectrum's display memory. Unlike a modern framebuffer — where pixel (0,0) lives at the first byte and pixels follow in neat left-to-right, top-to-bottom order — the ZX Spectrum's display memory has a peculiar layout that surprises almost every programmer who meets it for the first time. Understanding it thoroughly is not optional: every graphics routine you will ever write depends on it.

    The Spectrum's display occupies two distinct areas of RAM. The first is the display file, which holds the raw pixel data. The second is the attribute file, which controls the colour of each 8×8 pixel block. Together they form the complete display system. Understanding both — and the reasons behind their organisation — makes every subsequent chapter straightforward.

    To make that concrete: suppose you want to draw a sprite that is 8 pixels tall and one byte (8 pixels) wide. The natural assumption — the one that works on most platforms — is that the display file is stored row by row: all of pixel row 0, then all of pixel row 1, and so on. Each row is 32 bytes wide (256 pixels ÷ 8 pixels per byte), so to move from one row of the sprite to the next you would add 32 to the address. You write your eight sprite bytes to $4000, $4020, $4040, $4060, $4080, $40A0, $40C0, $40E0 and expect to see a solid block of eight pixel rows stacked on top of each other.

    What you actually get: $4000 is pixel row 0, but $4020 is pixel row 8. $4040 is pixel row 16. $4060 is pixel row 24. The eight addresses you chose do not map to eight consecutive rows — they map to rows 0, 8, 16, 24, 32, 40, 48 and 56, one eighth of the way down the screen apart. Your sprite appears as eight isolated single-pixel-tall strips with seven blank rows between each one, spread across most of the screen's height. The data is correct; the addresses are wrong.

    This is not a bug in your code's logic, only in your assumption about the memory layout. Understanding the actual layout — which has a clear structure of its own — is all it takes to fix it, and that is what this chapter explains.

    Pixel Memory Layout

    The ZX Spectrum displays 256 pixels horizontally and 192 pixels vertically. Since each byte holds 8 pixels (one bit per pixel — 1 means ink colour, 0 means paper colour), the full screen requires 256 × 192 ÷ 8 = 6,144 bytes of pixel data. This block of memory is called the display file, and it lives from address $4000 (16384) to $57FF (22527).

    If the Spectrum stored pixels in simple row order — all 32 bytes of row 0, then all 32 bytes of row 1, and so on — calculating an address would be trivial: $4000 + (y * 32) + (x / 8). But that is not what happens. The display file is organised to match the way the ULA (the Spectrum's display chip) scans video memory, and that organisation has a logic of its own. Once you see it, the address formula becomes easy to remember and easy to construct in Z80 code.

    Three Thirds

    The screen is divided vertically into three equal bands of 64 pixel rows each. Each band is called a third. Pixel rows 0–63 belong to the first third, rows 64–127 to the second, and rows 128–191 to the third. Each third occupies exactly 2,048 bytes ($800 hex), so the thirds are neatly separated in memory:

    ; ┌──────────────────────────────────────────┐  ← $4000  (16384)
; │                                          │
; │         FIRST THIRD   (rows   0–63)      │  2048 bytes
; │                                          │
; ├──────────────────────────────────────────┤  ← $4800  (18432)
; │                                          │
; │         SECOND THIRD  (rows  64–127)     │  2048 bytes
; │                                          │
; ├──────────────────────────────────────────┤  ← $5000  (20480)
; │                                          │
; │         THIRD THIRD   (rows 128–191)     │  2048 bytes
; │                                          │
; └──────────────────────────────────────────┘  ← $5800  (22528)  ← attribute file begins here

    To find which third a pixel row belongs to, divide y by 64: third = y / 64. The base address of that third is then $4000 + (third * $800).

    Inside a Third

    Before going further, three terms need precise definitions.

    A pixel row is a single horizontal line of pixels stretching across the full 256-pixel width of the screen, one pixel tall. The y coordinate selects which pixel row you are on. There are 192 of them, numbered 0 at the top to 191 at the bottom.

    A character row is a horizontal band of 8 pixel rows stacked vertically, the same height as one text character on screen. The Spectrum's character set uses 8×8 pixel cells, so the screen naturally divides into 24 character rows (192 ÷ 8). Character row 0 contains pixel rows 0–7, character row 1 contains pixel rows 8–15, character row 2 contains pixel rows 16–23, and so on.

    A scan line is the position of a pixel row within its character row, numbered 0–7 from the top of the character row. It is a local index, not a global one. Pixel row 19 sits in character row 2 (rows 16–23) at position 3 within that band, so its scan line is 3. The formula is: scan line = y AND 7, character row = y / 8. These are the LLL and RRR fields from the TTRRRLL breakdown introduced later in this chapter.

    With those definitions in place: within each third, you might expect the 64 pixel rows to be stored in plain order — pixel row 0 first, then pixel row 1, down to pixel row 63. They are not. Each third contains 8 character rows stacked vertically, and each character row is 8 scan lines tall. The display file does not store them character-row by character-row; it groups by scan line number instead, collecting scan line 0 from every character row before moving on to scan line 1.

    The ordering is: first, store scan line 0 of every character row (pixel rows 0, 8, 16, 24, 32, 40, 48, 56); then scan line 1 of every character row (pixel rows 1, 9, 17, 25...); then scan line 2; and so on to scan line 7. The scan line number advances slowly; the character row advances quickly:

    ; Layout inside the first third ($4000–$47FF):
;
;  $4000 ← scan line 0 of char row 0  (pixel row  0)
;  $4020 ← scan line 0 of char row 1  (pixel row  8)
;  $4040 ← scan line 0 of char row 2  (pixel row 16)
;  $4060 ← scan line 0 of char row 3  (pixel row 24)
;  $4080 ← scan line 0 of char row 4  (pixel row 32)
;  $40A0 ← scan line 0 of char row 5  (pixel row 40)
;  $40C0 ← scan line 0 of char row 6  (pixel row 48)
;  $40E0 ← scan line 0 of char row 7  (pixel row 56)
;  ---
;  $4100 ← scan line 1 of char row 0  (pixel row  1)
;  $4120 ← scan line 1 of char row 1  (pixel row  9)
;  ...etc...
;  ---
;  $4700 ← scan line 7 of char row 0  (pixel row  7)
;  $4720 ← scan line 7 of char row 1  (pixel row 15)
;  ...etc...
;  $47E0 ← scan line 7 of char row 7  (pixel row 63)

    The same information as a grid makes the pattern immediately visible. Each cell shows the memory address and, in brackets, the global pixel row that address holds. Moving one column right (to the next character row) adds $20 to the address. Moving one row down (to the next scan line) adds $100:

    Char row 0Char row 1Char row 2…Char row 7
    Scan line 0$4000 (pixel row 0)$4020 (pixel row 8)$4040 (pixel row 16)…$40E0 (pixel row 56)
    Scan line 1$4100 (pixel row 1)$4120 (pixel row 9)$4140 (pixel row 17)…$41E0 (pixel row 57)
    Scan line 2$4200 (pixel row 2)$4220 (pixel row 10)$4240 (pixel row 18)…$42E0 (pixel row 58)
    ………………

    Notice that pixel rows 0, 8, 16, 24, 32, 40, 48 and 56 are stored consecutively at $4000, $4020, $4040... only after all eight character rows have had their first scan line stored does the layout move on to scan line 1 at $4100. This is the opposite of what most programmers expect — but it is how the ULA reads memory, and it is what makes hardware character rendering efficient and inexpensive. When the ULA finishes drawing one scan line across the screen and needs to move to the next, it simply adds $100 to the address. No recalculation is needed: the new address automatically points to the correct scan line of the same set of character rows.

    The practical consequence is that if you try to draw a sprite by writing consecutive bytes from the same address onward, the image will look scrambled. You must calculate the correct address for each row separately. That is what the routines in this chapter do.

    Decoding y into Three Fields

    Any pixel row y in the range 0–191 can be split into three fields by looking at its 8 bits directly. The naming TTRRRLLL is a useful mnemonic — each letter stands for the field it represents: T for Third, R for character Row, L for scan Line:

    ; y  as 8 bits:   T T R R R L L L
;                 ↑ ↑ ↑ ↑ ↑ ↑ ↑ ↑
;               bit 7   bit 5   bit 2   bit 0
;
;  TT  = bits 7–6  →  which third          (0, 1, or 2)
;  RRR = bits 5–3  →  character row within the third  (0–7)
;  LLL = bits 2–0  →  scan line within the character row  (0–7)

    For example, pixel row 73:

    ; y = 73  →  binary: 0 1 0 0 1 0 0 1
;                    T T R R R L L L
;
;  TT  = 01  →  second third  (base $4800)
;  RRR = 001  →  character row 1  within that third
;  LLL = 001  →  scan line 1  within that character row
;
;  Pixel row 73 = scan line 1 of character row 9  (= 8 + 1)

    Working through a few more values makes the pattern obvious. Any y value in the range 0–191 splits cleanly into three non-overlapping fields:

    yBinaryTT (third)RRR (char row)LLL (scan line)Meaning
    000 000 00000000000First third, char row 0, scan line 0 — very top of screen
    800 001 00000001000First third, char row 1, scan line 0 — second character row begins
    1000 001 01000001010First third, char row 1, scan line 2
    6401 000 00001000000Second third begins — TT flips to 01
    7301 001 00101001001Second third, char row 1, scan line 1
    19110 111 11110111111Third third, char row 7, scan line 7 — very bottom of screen

    Notice that incrementing y by 1 always increments LLL by 1 — until LLL wraps at 7, at which point RRR increments instead. This is exactly the same as counting in binary with the bits grouped as 2+3+3. The address formula exploits this directly: each field slots into a fixed position in the 16-bit address with no arithmetic needed, only bit manipulation.

    The Full Address Formula

    Two more terms before the formula.

    A 16-bit address on the Z80 is made up of two 8-bit bytes. The high byte holds the upper eight bits (bits 15–8) and the low byte holds the lower eight bits (bits 7–0). When you write LD HL, $4920, H is the high byte ($49) and L is the low byte ($20). The display file address formula builds H and L separately, then combines them.

    A column is the horizontal byte position along a pixel row — how far along the x-axis a byte sits, not how far down the screen. Each pixel row is 256 pixels wide and each byte holds 8 pixels, so each row is 32 bytes wide. Those 32 bytes are columns 0–31, increasing from left to right. The column number for a given x coordinate is simply x / 8 — the same division that strips the three low bits identifying the pixel within its byte. Column 0 covers pixels 0–7, column 1 covers pixels 8–15, column 31 covers pixels 248–255.

    With those in place: the display file address is assembled by placing the three y fields and the column into specific bit positions in the high and low bytes. Each field plugs directly into a dedicated slot with no multiplication needed:

    ; 16-bit address:
;
;  High byte:  0  1  0  T1 T0 L2 L1 L0
;  Low  byte: R2 R1 R0 C4 C3 C2 C1 C0
;
;  T1 T0  =  bits 7–6 of y  (which third)
;  L2 L1 L0  =  bits 2–0 of y  (scan line)
;  R2 R1 R0  =  bits 5–3 of y  (character row within third)
;  C4..C0  =  bits 7–3 of x  (column byte = x / 8,  range 0–31)

    The 010 at the top of the high byte locks the address into the display file range. The third (TT) occupies the next two bits — each step of TT adds $800 to the address. The scan line (LLL) follows in the high byte's lower three bits — each step adds $100. The character row (RRR) leads the low byte — each step adds $20 (32 bytes, one byte per column). The column (CCCCC) fills the low byte's remaining five bits.

    Let's verify with pixel row 73, column 10 (x = 80):

    ; y = 73 = %01001001   →   TT=01  RRR=001  LLL=001
; x = 80              →   column byte = 80 / 8 = 10  =  %01010  →  C4..C0 = 01010
;
;  High byte: 0 1 0 0 1 0 0 1  =  $49
;  Low  byte: 0 0 1 0 1 0 1 0  =  $2A
;
;  Address = $492A
;
; Cross-check:  second third base $4800
;             + scan line 1  → +$100  =  $4900
;             + char row 1   → +$020  =  $4920
;             + column 10    → +$00A  =  $492A  ✓

    Attribute Memory Layout

    The attribute file begins immediately after the display file, at address $5800 (22528), and occupies 768 bytes through to $5AFF (23295). There is one attribute byte for every 8×8 block of pixels on screen — 32 columns of blocks across and 24 rows of blocks down = 768 blocks in total, one byte each. Each block is called a character cell; Chapter 2 explains the term and the full attribute byte format in detail.

    Unlike the display file, the attribute file is perfectly linear. The attribute bytes are laid out in simple row order: all 32 bytes of character row 0 first, then character row 1, and so on. The address of the attribute byte for the character cell containing pixel (x, y) is:

    ; attr_address = $5800 + (cy * 32) + cx
;
;   cy = y / 8   (pixel row → character row, 0–23)
;   cx = x / 8   (pixel col → character col, 0–31)
;
; Examples:
;   Top-left cell    cy=0,  cx=0  →  $5800 + 0   + 0   =  $5800
;   Top-right cell   cy=0,  cx=31 →  $5800 + 0   + 31  =  $581F
;   Second row       cy=1,  cx=0  →  $5800 + 32  + 0   =  $5820
;   Bottom-right     cy=23, cx=31 →  $5800 + 736 + 31  =  $5AFF

    One attribute byte controls the colour of all 64 pixels in its cell — every pixel in that 8×8 block shares the same ink and paper colour. This 8×8 granularity is the most distinctive constraint of Spectrum graphics programming: you can never colour a single pixel independently; you always colour the entire cell it belongs to. The attribute byte format — ink, paper, BRIGHT and FLASH — is covered in full in Chapter 2. For now, the crucial point is the layout: display file is quirky, attribute file is simple.

    Calculating Screen Addresses

    Now we turn the address formula into working Z80 code. The two routines below accept a pixel coordinate — y in register B, x in register C — and return either a display file address or an attribute address in HL. These are the building blocks every subsequent chapter depends on, so it is worth reading them carefully and understanding each step.

    calc_pixel_addr: Display File Address

    The routine returns the address in the HL register pair. H stands for High and L stands for Low. HL is two 8-bit registers used together as a single 16-bit value: H holds the high byte — the upper eight bits, bits 15–8 — and L holds the low byte — the lower eight bits, bits 7–0. When the routine finishes, HL contains the complete 16-bit address. The reason for building H and L separately is that the address formula splits cleanly at the byte boundary: the third (TT) and scan line (LLL) fields belong entirely in H, and the character row (RRR) and column (CCCCC) fields belong entirely in L. No field crosses from one byte to the other.

    The routine also uses RRCA — Rotate Right Circular the Accumulator. RRCA shifts every bit in A one position to the right, and the bit that would fall off the right end (bit 0) wraps around to the left end (bit 7) instead of being lost:

    ; RRCA on %10110000:
;   before:  1 0 1 1 0 0 0 0
;   after:   0 1 0 1 1 0 0 0   ← each bit moved right one place; bit 0 (0) wrapped to bit 7
;
; RRCA on %00000001:
;   before:  0 0 0 0 0 0 0 1
;   after:   1 0 0 0 0 0 0 0   ← bit 0 (1) wrapped to bit 7

    This wrapping is why an AND instruction always appears before a sequence of RRCAs in this routine. If we rotated the raw value of y, bits from the low end would wrap into the high end and corrupt the result. AND first zeroes out all bits except the ones we want to move, so the wrapped bit is always 0 and harmless.

    The header block below shows the routine's inputs, output, and register side effects. Destroys: B means that B does not hold its original value when the routine returns — it is overwritten as part of the calculation. Any value you needed from B must be saved before calling the routine.

    ; calc_pixel_addr
; Input:  B = y  (0–191)
;         C = x  (0–255)
; Output: HL = display file address of the byte containing the pixel
;          A = bitmask for that pixel  (bit 7 = leftmost)
; Destroys: B

    Stage 1 — Build the high byte

    The high byte we need has the bit pattern 010 TT LLL. The fixed 010 at the top three bits ensures the address falls in the range $4000–$5FFF, which is where the display file lives. TT (bits 7–6 of y) sits at bit positions 4–3, contributing $000, $800, or $1000 to the address — selecting which third. LLL (bits 2–0 of y) sits at bit positions 2–0, contributing 0–7 × $100 — selecting which scan line within the character row.

    TT starts at bits 7–6 of y and needs to move to bits 4–3 of H: three positions to the right. LLL starts at bits 2–0 of y and needs to stay at bits 2–0 of H: no movement needed. We extract and place each one separately, then OR them together.

    calc_pixel_addr:
    ; Extract TT: bits 7–6 of y → rotate right 3 → land at positions 4–3
    LD  A, B             ; A = y
    AND %11000000        ; A = TT000000  (isolate bits 7–6)
    RRCA                 ; A = 0TT00000
    RRCA                 ; A = 00TT0000
    RRCA                 ; A = 000TT000  (TT now in positions 4–3)
    OR  %01000000        ; A = 010TT000  (set bit 6: the fixed $40 base)
    LD  H, A             ; save — H holds 010TT000, LLL still missing

    ; Extract LLL: bits 2–0 of y → already at positions 2–0, slot straight in
    LD  A, B             ; A = y
    AND %00000111        ; A = 00000LLL
    OR  H                ; A = 010TTLLL
    LD  H, A             ; H is complete

    Stage 2 — Build the low byte

    The low byte has the pattern RRR CCCCC. RRR (bits 5–3 of y) sits at positions 7–5, contributing 0–7 × $20 — selecting which character row. CCCCC (the column, x ÷ 8) sits at positions 4–0, contributing 0–31 — selecting which byte along the row.

    RRR starts at bits 5–3 of y and needs to move to bits 7–5 of L: two positions to the left. This uses RLCA — Rotate Left Circular the Accumulator — which works exactly like RRCA but in the opposite direction: every bit shifts one place left, and the bit that would fall off the left end (bit 7) wraps around to the right end (bit 0):

    ; RLCA on %00111000:  (RRR = 111 — character row 7)
;   before:  0 0 1 1 1 0 0 0
;   after:   0 1 1 1 0 0 0 0   ← each bit moved left one place; bit 7 (0) wrapped to bit 0
;
; RLCA again:
;   before:  0 1 1 1 0 0 0 0
;   after:   1 1 1 0 0 0 0 0   ← RRR now occupies bits 7–5

    The AND before the RLCAs serves the same purpose as in Stage 1: it zeroes the bits we do not want, so the wrapped bit is always 0 and harmless. The column calculation uses three RRCAs (rightward shift) with AND cleaning up the bits that wrapped in from the right — exactly as described above for Stage 1.

        ; Extract RRR: bits 5–3 of y → rotate left 2 → land at positions 7–5
    LD  A, B             ; A = y
    AND %00111000        ; A = 00RRR000  (isolate bits 5–3)
    RLCA                 ; A = 0RRR0000
    RLCA                 ; A = RRR00000  (RRR now in positions 7–5)
    LD  L, A             ; L = RRR00000

    ; Extract CCCCC: bits 7–3 of x → rotate right 3 → land at positions 4–0
    ; RRCA rotates, so low bits wrap into the top — AND clears them.
    LD  A, C             ; A = x
    RRCA                 ; }
    RRCA                 ; }  divide x by 8
    RRCA                 ; }
    AND %00011111        ; A = 000CCCCC  (mask off the rotated-in bits)
    OR  L                ; A = RRRCCCCC
    LD  L, A             ; L is complete

    Stage 3 — Calculate the bitmask

    Each byte in the display file holds 8 pixels, one per bit. To set, clear, or read a single pixel you need to know which bit within its byte represents that pixel. A bitmask is a byte with exactly one bit set — a 1 in the position of the target pixel and 0s everywhere else. You then use that mask with a logical operation to affect only the target pixel while leaving the other seven bits untouched: OR with the mask to set the pixel, AND with the inverted mask to clear it, XOR with the mask to toggle it.

    On the Spectrum, bit 7 of a display byte is the leftmost pixel in that byte and bit 0 is the rightmost. A pixel at x coordinate 0 is at bit 7 of column 0; a pixel at x coordinate 7 is at bit 0 of column 0; a pixel at x coordinate 8 is at bit 7 of column 1. The bit position within the byte is always x AND 7 — the three low bits of x. So for x=0 the mask is %10000000, for x=1 it is %01000000, for x=7 it is %00000001, for x=8 it is %10000000 again (new byte, back to bit 7).

    The stage calculates that mask: start with %10000000 (bit 7, the leftmost position) and rotate it right x AND 7 times to move the set bit to the correct position.

        LD  A, C             ; A = x
    AND %00000111        ; A = pixel's position within its byte (0–7). Also sets the Zero flag if result is 0.
    LD  B, A             ; B = shift count  (LD never affects flags, so Zero flag is still set from AND)
    LD  A, %10000000     ; A = leftmost pixel mask  (LD never affects flags)
    JR  Z, .mask_done    ; Zero flag still set from AND — if shift count was 0, mask is already correct
.mask_shift:
    RRCA                 ; move mask one position right
    DJNZ .mask_shift     ; Decrement B and Jump if Not Zero — loops B times then falls through
.mask_done:
    RET

    ; y = 10 = %00001010

    calc_attr_addr: Attribute File Address

    The attribute address is simpler because the attribute file is stored linearly. We convert the pixel coordinates to character cell coordinates, then compute $5800 + (cy * 32) + cx. Multiplying by 32 is done with five consecutive ADD HL, HL instructions. Each one computes HL = HL + HL = 2 × HL, so five doublings multiply the original value by 2⁵ = 32.

    ; calc_attr_addr
; Input:  B = y  (0–191)
;         C = x  (0–255)
; Output: HL = attribute byte address
; Destroys: A, DE
calc_attr_addr:
    ; Convert y to character row (cy = y / 8) by shifting right 3
    LD  A, B             ; A = y
    RRCA                 ; }  divide by 8
    RRCA                 ; }
    RRCA                 ; }  A = character row (0–23), with 3 rotated-in bits
    AND %00011111        ; A = cy  (masks away the rotated-in bits)

    ; Multiply character row by 32 to get byte offset of this row
    LD  H, 0
    LD  L, A             ; HL = cy  (0–23)
    ADD HL, HL           ; HL = cy *  2
    ADD HL, HL           ; HL = cy *  4
    ADD HL, HL           ; HL = cy *  8
    ADD HL, HL           ; HL = cy * 16
    ADD HL, HL           ; HL = cy * 32  (byte offset to this character row)

    ; Add the column: cx = x / 8
    LD  A, C             ; A = x
    RRCA                 ; }  divide by 8
    RRCA                 ; }
    RRCA                 ; }
    AND %00011111        ; A = cx  (0–31)
    ADD A, L             ; add column to row offset (safe: L ≤ $E0, cx ≤ $1F, sum ≤ $FF — no 8-bit overflow)
    LD  L, A             ; HL = cy*32 + cx  (offset within attribute area)

    ; Add the attribute file base address
    LD  DE, $5800        ; DE = attribute base
    ADD HL, DE           ; HL = final attribute address
    RET

    These two routines are the engine beneath every drawing operation in this book. A sprite-drawing loop calls calc_pixel_addr once for the sprite's top row, then steps to subsequent rows using simple address arithmetic — which turns out to be a short sequence of operations once you understand the layout. That technique is covered in Chapter 6. For now, we have everything needed to write our first complete graphics program.

    A Complete Example: Lighting a Single Pixel

    When coordinates are fixed and known at assembly time you do not need a subroutine. Apply the address formula by hand, derive the numbers once, and write them directly into the code. To give all four fields of the layout something to do, let's use a non-trivial coordinate: pixel (x=52, y=100), somewhere in the middle of the screen.

    Working through the formula by hand:

    ; y = 100 = %01100100
;            T T R R R L L L
;            0 1 1 0 0 1 0 0
;
;   TT  = 01  →  second third  (base $4800)
;   RRR = 100  →  character row 4  within that third
;   LLL = 100  →  scan line 4  within that character row
;
;  High byte:  0 1 0 0 1 1 0 0  =  $4C
;  Low  byte:  1 0 0 0 0 1 1 0  =  $86
;  Display file address  =  $4C86
;
; Cross-check:  second third base $4800
;             + scan line 4  → +$400  =  $4C00
;             + char row 4   → +$080  =  $4C80
;             + column 6     → +$006  =  $4C86  ✓
;
;  x = 52,  bit offset = 52 AND 7 = 4
;  Bitmask: %10000000 rotated right 4  →  %00001000
;
;  cy = 100 / 8 = 12,  cx = 52 / 8 = 6
;  Attribute address  =  $5800 + (12 × 32) + 6  =  $5800 + $180 + 6  =  $5986

    Notice that all four fields are non-zero this time — TT, RRR, LLL and the column all contribute to the final address, so you can verify the formula is doing real work. Here is the complete program:

        ORG $8000

    ; Set pixel at (x=52, y=100)
    ; Display file address = $4C86,  bitmask = %00001000 (bit 3)
    LD  HL, $4C86        ; point at the byte containing our pixel
    LD  A, (HL)          ; read the existing byte — preserves the other 7 pixels in this byte
    OR  %00001000        ; set bit 3 — our pixel
    LD  (HL), A          ; write back

    ; Colour the character cell at (52, 100): bright yellow ink on black paper
    ; Attribute value $46 — format covered in Chapter 2
    LD  HL, $5986        ; attribute byte for this cell
    LD  (HL), $46        ; bright yellow ink on black paper

    RET                  ; return to BASIC

    END $8000

    Assemble with Pasmo (or whichever Z80 assembler your toolchain uses) and load into your emulator. The pixel appears at approximately x=52, y=100 — a little over one-sixth across the screen and just past halfway down. You will see a small black square (the 8×8 character cell, whose paper colour is now black) with a single bright yellow dot inside it, against the otherwise white default background.

    The OR %00001000 pattern deserves attention. The byte at $4C86 holds eight pixels, not one — bits 7 down to 0 represent the eight pixels in that horizontal run. Writing the mask directly with LD (HL), %00001000 would clear the other seven pixels in the same byte. The correct approach — and the one every graphics routine in this book follows — is to read the existing byte, OR your bit in, then write back. That preserves the neighbours. The counterpart operations are AND with an inverted mask to clear a pixel, and XOR to toggle one; both are covered in Chapter 3.

    Reusable Library Files

    Rather than copying the routines into every program, save each one as its own .asm file. Pasmo's INCLUDE directive pastes the file in at assembly time, making all its labels available to the rest of your program. Save the following two files alongside your programs.

    calc_pixel_addr.asm

    ; calc_pixel_addr
; Input:  B = y  (0–191)
;         C = x  (0–255)
; Output: HL = display file address of the byte containing the pixel
;          A = bitmask for that pixel  (bit 7 = leftmost)
; Destroys: B
calc_pixel_addr:
    LD  A, B
    AND %11000000        ; isolate TT (bits 7–6)
    RRCA                 ; }
    RRCA                 ; } rotate TT right 3
    RRCA                 ; }
    OR  %01000000        ; set fixed $40 base
    LD  H, A             ; H = 010TT000
    LD  A, B
    AND %00000111        ; isolate LLL (bits 2–0)
    OR  H                ; A = 010TTLLL
    LD  H, A             ; H complete

    LD  A, B
    AND %00111000        ; isolate RRR (bits 5–3)
    RLCA                 ; } rotate RRR left 2
    RLCA                 ; }
    LD  L, A             ; L = RRR00000
    LD  A, C
    RRCA                 ; }
    RRCA                 ; } divide x by 8
    RRCA                 ; }
    AND %00011111        ; mask off rotated-in bits
    OR  L                ; A = RRRCCCCC
    LD  L, A             ; L complete — HL = display file address

    LD  A, C
    AND %00000111        ; A = bit position within byte (0–7)
    LD  B, A             ; B = shift count
    LD  A, %10000000     ; start with leftmost pixel mask
    JR  Z, .mask_done    ; shift count was 0: mask already correct
.mask_shift:
    RRCA                 ; move mask right by one
    DJNZ .mask_shift     ; repeat B times
.mask_done:
    RET

    calc_attr_addr.asm

    ; calc_attr_addr
; Input:  B = y  (0–191)
;         C = x  (0–255)
; Output: HL = attribute byte address
; Destroys: A, DE
calc_attr_addr:
    LD  A, B
    RRCA                 ; }
    RRCA                 ; } divide y by 8 to get character row
    RRCA                 ; }
    AND %00011111        ; A = cy (0–23)
    LD  H, 0
    LD  L, A             ; HL = cy
    ADD HL, HL           ; HL = cy *  2
    ADD HL, HL           ; HL = cy *  4
    ADD HL, HL           ; HL = cy *  8
    ADD HL, HL           ; HL = cy * 16
    ADD HL, HL           ; HL = cy * 32
    LD  A, C
    RRCA                 ; }
    RRCA                 ; } divide x by 8 to get column
    RRCA                 ; }
    AND %00011111        ; A = cx (0–31)
    ADD A, L
    LD  L, A             ; HL = cy*32 + cx
    LD  DE, $5800
    ADD HL, DE           ; HL = attribute file address
    RET

    A Moving Pixel

    With the library files in place, the following program moves a single pixel from the left edge of the screen to the right edge and then returns to BASIC. Three instructions appear here that have not been used before:

    EI — Enable Interrupts. The Z80 has a flag inside the CPU that controls whether it responds to interrupt signals from external hardware. DI (Disable Interrupts) clears that flag; EI sets it again. When you run a program from BASIC with RANDOMIZE USR, interrupts are normally already enabled, so EI here is a safety measure rather than strictly necessary — but it costs one byte and one cycle, and makes the program reliable regardless of what state the CPU was left in.

    HALT suspends execution until the next maskable interrupt. The Spectrum's display chip fires that interrupt 50 times per second, so one HALT is a clean 20 ms pause — enough for the eye to follow the dot as it moves. If interrupts were disabled, HALT would pause forever, which is why EI comes first.

    CPL flips every bit in A. After calc_pixel_addr returns the bitmask in A (one bit set, the rest clear), CPL inverts it to give one bit clear and the rest set — exactly the mask needed for AND (HL) to clear a single pixel while leaving its neighbours untouched.

    Save the following as moving_pixel.asm in the same folder as the two library files:

        ORG  $8000

main:
    EI                   ; ensure interrupts are on so HALT works
    LD  B, 88            ; y = 88 — just above the middle of the screen
    LD  C, 0             ; x = 0 — left edge

.loop:
    ; — Draw pixel at current position —
    PUSH BC              ; calc_pixel_addr destroys B, so save coordinates
    CALL calc_pixel_addr ; HL = byte address,  A = bitmask
    OR  (HL)             ; set our pixel bit, preserve the other seven
    LD  (HL), A
    POP  BC

    ; — Wait one TV frame so the dot is visible —
    HALT                 ; 50 Hz interrupt — pauses ~20 ms

    ; — Erase pixel at current position —
    PUSH BC
    CALL calc_pixel_addr ; HL = byte address,  A = bitmask
    CPL                  ; invert mask: 0 in our pixel's bit, 1s everywhere else
    AND (HL)             ; clear our pixel bit, preserve the other seven
    LD  (HL), A
    POP  BC

    ; — Move one pixel right and loop —
    INC  C               ; x = x + 1
    JR  NZ, .loop        ; when C wraps from 255 to 0 we have crossed the screen

    RET                  ; back to BASIC

    INCLUDE "calc_pixel_addr.asm"

    END  $8000

    Assemble with pasmo --tapbas moving_pixel.asm moving_pixel.tap and load the TAP into your emulator — the BASIC loader runs automatically. A single dot slides smoothly across pixel row 88, crossing all 256 x positions — eight complete character columns — before the program exits. Because calc_pixel_addr recalculates the byte address and bitmask on every iteration, the dot crosses character-cell boundaries correctly without any special-case code: the same pattern (OR (HL) to set, CPL / AND (HL) to clear) works at every x coordinate from 0 to 255.

    Key fact: everything visual on the ZX Spectrum ultimately comes down to reading and writing bytes in two memory regions — the display file ($4000–$57FF) for pixel data, and the attribute file ($5800–$5AFF) for colour. No ROM calls are needed to draw anything. The address calculation routines in this chapter are the general form of exactly what the moving pixel example does on every iteration.

    2. Colours & Attributes

    [Back to Contents]

    Chapter 1 used the attribute byte value $46 without explaining what it meant. This chapter explains exactly what is in those 8 bits, how to construct any colour combination, and how to write attribute data efficiently. By the end you will have two new library routines and a complete program that draws a coloured trail across the screen.

    The Attribute Byte

    The screen divides naturally into a grid of 8×8 pixel blocks — 32 columns wide and 24 rows tall. Each block is called a character cell, or just a cell. The name comes from the fact that one text character occupies exactly one cell. Every cell on screen has exactly one byte in the attribute file, and that byte controls the colour of all 64 pixels in the cell. That byte is the attribute byte for that cell, and its eight bits divide into four fields:

    ; Bit:   7      6      5   4   3      2   1   0
;        FLASH  BRIGHT P2  P1  P0     I2  I1  I0
;        │      │      └───┬───┘      └───┬───┘
;        │      │        PAPER            INK
;        │      │        (0–7)            (0–7)
;        │      └── BRIGHT: 0 = normal colours,  1 = bright colours
;        └───────── FLASH:  0 = steady,           1 = ink/paper swap at ~1.7 Hz

    INK (bits 2–0) is the colour used to draw pixels whose bit in the display file is 1. PAPER (bits 5–3) is the colour used for pixels whose bit is 0 — the background colour of the cell. BRIGHT (bit 6) switches the entire cell to a more vivid palette. FLASH (bit 7) causes the ULA to swap ink and paper automatically at about 1.7 Hz — no code is needed to maintain it once the bit is set.

    To make this concrete, here is $46 from Chapter 1 decoded field by field:

    ; $46 = %01000110
;
;  Bit 7   FLASH  = 0  →  steady (no flashing)
;  Bit 6   BRIGHT = 1  →  bright colours
;  Bits 5–3  PAPER = 000  →  colour 0 (black)
;  Bits 2–0  INK   = 110  →  colour 6 (yellow)
;
;  Result: bright yellow pixels on a black background

    One attribute byte controls all 64 pixels in its 8×8 cell — every pixel in that block shares the same ink and paper colour. This is the central constraint of Spectrum graphics programming: you can never colour an individual pixel independently; you colour the entire cell it belongs to. This 8×8 granularity is why Spectrum games tend to align sprites to character-cell boundaries, and why two differently-coloured objects produce a colour clash when they share a cell. The pixel trail at the end of this chapter makes colour clash directly visible.

    Ink, Paper, Bright & Flash

    Both INK and PAPER are encoded as a 3-bit number in the range 0–7. The eight colours in order are:

    ValueColourNormalBright
    0BlackBlackBlack — BRIGHT has no effect on colour 0
    1BlueDark blueBright blue
    2RedDark redBright red
    3MagentaDark magentaBright magenta
    4GreenDark greenBright green
    5CyanDark cyanBright cyan
    6YellowDark yellowBright yellow
    7WhiteWhiteWhite (slightly more vivid)

    BRIGHT switches the entire cell to a more vivid palette — the ULA drives a higher voltage level for the affected cell. Because BRIGHT applies to the whole cell, both ink and paper are brightened together. The exception is colour 0: black with BRIGHT is still black. This gives 15 distinct colours in practice — 7 normal shades, 7 bright shades, and one black that looks the same at both brightness levels.

    FLASH is handled entirely by the ULA in hardware. Once bit 7 of an attribute byte is set to 1, the display chip swaps that cell's ink and paper colours at roughly 1.7 Hz. No code runs to maintain the effect. Writing 0 to bit 7 stops the flash immediately on the next display frame.

    Building Attribute Bytes

    To assemble an attribute byte from its parts, shift each field to its correct bit position and OR the results together. The comments below use the left-shift notation <<: 1 << 6 means "take the value 1 and shift its bits six places to the left", giving %01000000. This is assembler arithmetic evaluated before your program runs — the assembler computes the result and embeds it as a plain byte, so the CPU never performs any shifting. This is different from instructions like RLCA or RRCA, which shift the live contents of A while the program is executing. << only works on constants you know when writing the code; RLCA/RRCA work on values that only exist at runtime.

    ; attr = (FLASH << 7) | (BRIGHT << 6) | (PAPER << 3) | INK
;
; Example: bright cyan ink on black paper, no flash
;   FLASH=0, BRIGHT=1, PAPER=0 (black), INK=5 (cyan)
;
;   FLASH  shifted left 7: 0 << 7 = %00000000
;   BRIGHT shifted left 6: 1 << 6 = %01000000
;   PAPER  shifted left 3: 0 << 3 = %00000000
;   INK                  :     5 = %00000101
;                         OR'd  = %01000101  =  $45

    Alternatively, work the arithmetic out in your notes and write the final hex value directly — either way the result is the same: a constant byte baked into the program. The common pattern in game code is to give each such value a memorable name using the EQU directive. EQU (short for EQUate) tells the assembler to substitute the given value wherever the name appears. Unlike DB or ORG, it does not place any bytes in memory — it is purely a compile-time name for a number:

    ; Useful attribute constants
ATTR_CYAN_BRT  EQU  $45   ; bright cyan ink, black paper
ATTR_YEL_BRT   EQU  $46   ; bright yellow ink, black paper
ATTR_WHT_BRT   EQU  $47   ; bright white ink, black paper
ATTR_DEFAULT   EQU  $38   ; black ink, white paper — BASIC default

    A reference table of the values used most often in game code:

    ValueMeaning
    $00Black ink on black paper — invisible pixels; useful for erasing cells
    $07White ink on black paper (normal brightness)
    $38Black ink on white paper — the Spectrum's BASIC default
    $41Bright blue ink on black paper
    $42Bright red ink on black paper
    $44Bright green ink on black paper
    $45Bright cyan ink on black paper
    $46Bright yellow ink on black paper (from Chapter 1)
    $47Bright white ink on black paper

    $80Flash, black ink on black paper

    Writing Attributes

    Writing an attribute byte is a one-instruction operation once you have the address: LD (HL), A. The interesting work is finding the right address and doing it efficiently for ranges of cells. This section builds three tools — a single-cell write routine, a row fill, and a full-screen fill — then puts them to work in a complete program.

    Writing a Single Cell — set_attr

    calc_attr_addr from Chapter 1 handles the address calculation. set_attr wraps it with the write, giving a one-call interface. Because calc_attr_addr destroys A, the attribute value must be saved across the call.

    The Z80 has no instruction to push A alone — the only way to stack the accumulator is PUSH AF, which saves A and the Flags register together as a 16-bit pair. The flags are not needed here; they come along because that is how the hardware works. POP AF restores both: A gets back the attribute value, and the flags are restored to whatever state they were in before the call, which is a harmless side effect.

    ; set_attr
; Input:  B = y  (0–191)
;         C = x  (0–255)
;         A = attribute byte to write
; Output: none
; Destroys: HL, DE
set_attr:
    PUSH AF              ; PUSH AF saves A and Flags together — the only way to stack A
    CALL calc_attr_addr  ; HL = attribute file address  (overwrites A and DE)
    POP  AF              ; restore A (attribute byte) and Flags
    LD  (HL), A          ; write it
    RET

    Save this as set_attr.asm. Any program that includes both calc_attr_addr.asm and set_attr.asm can colour any cell with a single CALL set_attr.

    Writing a Row of Cells

    The attribute file is linear, so the 32 bytes of one character row are at consecutive addresses. To colour a full row, find the first cell with calc_attr_addr (passing x=0), then step through the remaining 31 cells with INC HL:

    ; Colour one full character row
; Input:  B = any y coordinate in the target row  (0–191)
;         A = attribute byte
    PUSH AF              ; save attribute
    LD  C, 0             ; x = 0 — leftmost column
    CALL calc_attr_addr  ; HL = first attribute byte in this row
    POP  AF              ; restore attribute
    LD  B, 32            ; 32 cells per row
.row_loop:
    LD  (HL), A          ; write attribute
    INC HL               ; next cell — safe because attribute file is linear
    DJNZ .row_loop

    This is an inline fragment, not a standalone routine — embed it directly in your code where you need a row fill, or wrap it in a labelled subroutine with a RET if you need to call it from multiple places. It works because attribute bytes for adjacent cells are adjacent in memory. The same trick does not work in the display file, where consecutive pixel rows are not consecutive in memory — which is exactly why the address calculation routines from Chapter 1 are necessary.

    Filling the Whole Screen

    The entire attribute file is 768 bytes ($5800 to $5AFF) stored linearly. A full-screen fill writes the same value to all 768 addresses. Three passes of 256 bytes each — using DJNZ's property that starting at B=0 gives 256 iterations — keeps the loop body as tight as possible:

    ; fill_screen_attr
; Fill all 768 attribute bytes with a single value
; Input:  A = attribute byte to fill with
; Output: none
; Destroys: BC, HL
fill_screen_attr:
    LD  HL, $5800        ; start of attribute file
    LD  B, 3             ; 3 outer passes of 256 bytes = 768 bytes total
.outer:
    PUSH BC
    LD  B, 0             ; B=0 → DJNZ loops 256 times (decrements to 255 on first pass)
.inner:
    LD  (HL), A          ; write attribute — DJNZ does not touch A
    INC HL
    DJNZ .inner
    POP  BC
    DJNZ .outer          ; 3 × 256 = 768
    RET

    A Coloured Pixel Trail

    This program extends the moving pixel from Chapter 1. The pixel no longer erases itself — it leaves every dot set as it advances, drawing a solid line of pixels across row 88. At each column boundary (every 8 pixels) the program pauses one frame, then writes a new attribute byte with the next ink colour in a 7-step cycle. Because the attribute colours the full 8×8 character cell, the visible result is a horizontal band one character cell tall (8 pixels) running the full width of the screen, divided into 32 coloured segments that snap into place one at a time from left to right.

    The ink cycle skips colour 0 (black on black paper is invisible). The wrapping logic increments the current ink value, masks it to 0–7 with AND, then nudges it to 1 if it landed on 0, producing the sequence 1, 2, 3, 4, 5, 6, 7, 1, 2, …

    Save the following as pixel_trail.asm alongside calc_pixel_addr.asm and calc_attr_addr.asm:

        ORG  $8000

main:
    EI                    ; ensure interrupts are on for HALT
    LD   B, 88           ; y = 88 — just above the middle of the screen
    LD   C, 0            ; x = 0 — left edge

.loop:
    ; At each column boundary: pause and colour the new cell
    LD   A, C
    AND  %00000111        ; x mod 8: is this the first pixel of a new cell?
    JR   NZ, .draw_pixel  ; no — just draw and continue

    HALT                  ; yes — pause ~20 ms so each coloured band is visible

    ; Advance ink colour through 1–7, skipping 0 (black on black = invisible)
    LD   A, (ink_colour)
    INC  A
    AND  %00000111        ; wrap: 8 → 0
    JR   NZ, .store_ink
    INC  A                ; nudge: 0 → 1, skipping black
.store_ink:
    LD   (ink_colour), A
    OR   %01000000        ; set BRIGHT bit — A = BRIGHT=1, PAPER=0, INK=colour
    PUSH BC
    PUSH AF               ; save A (attribute) and Flags — PUSH AF is the only way to stack A
    CALL calc_attr_addr   ; HL = attribute address for this cell  (overwrites A and DE)
    POP  AF               ; restore A (attribute) and Flags
    LD   (HL), A          ; colour the cell
    POP  BC

.draw_pixel:
    PUSH BC
    CALL calc_pixel_addr  ; HL = byte address,  A = bitmask
    OR   (HL)             ; set pixel bit, preserve neighbours
    LD   (HL), A
    POP  BC

    INC  C                ; x = x + 1
    JR   NZ, .loop        ; stop when x wraps 255 → 0

    RET                   ; back to BASIC

ink_colour: DB 0         ; current ink index (0 = uninitialised; first use advances to 1)

    INCLUDE "calc_pixel_addr.asm"
    INCLUDE "calc_attr_addr.asm"

    END  $8000

    Assemble with pasmo --tapbas pixel_trail.asm pixel_trail.tap and load the TAP into your emulator — the BASIC loader runs automatically. A coloured band builds across the screen from left to right — blue, red, magenta, green, cyan, yellow, white, cycling — each cell snapping in with a 20 ms pause. The finished result is a single stripe one character cell tall spanning the full width of the screen.

    Two things are worth watching closely. First, colour clash: when a new cell's attribute byte is written, every pixel already set in that cell is immediately repainted in the new ink colour. The rightmost drawn pixel changes colour as each new cell opens, not after the cell is complete. This is the attribute system working exactly as designed — ink and paper are cell properties, not pixel properties.

    Second, notice that calc_attr_addr is called only 32 times (once per column boundary) while calc_pixel_addr is called 256 times (once per pixel). The attribute address calculation is the more expensive operation, but by calling it only when the cell changes the program avoids unnecessary work. This pattern — detect a boundary, then handle it — appears throughout game graphics code.

    Key fact: the attribute system separates colour from pixels entirely. Writing to the display file never affects colour; writing to the attribute file never affects which pixels are set. The two are independent, which makes it possible to repaint the screen's colours without touching a single pixel, and to move pixel data without changing any colours.

    3. Drawing Pixels

    [Back to Contents]

    Chapters 1 and 2 used pixel operations informally — OR (HL) to set a pixel, CPL / AND (HL) to clear one, with the explanation that XOR toggles. This chapter puts all three on a firm footing, explains exactly why each logical operation is the right tool, and wraps each one in a clean library routine. By the end you will have three new .asm files and a bouncing pixel that uses all of them in a proper animation loop.

    Setting a Single Pixel

    Setting a pixel means forcing one specific bit in a display file byte to 1 while leaving the other seven bits exactly as they are. The right tool is OR.

    OR combines two bits according to one rule: the result is 1 if either input is 1, and 0 only if both inputs are 0. Applied to a full byte, each bit pair is processed independently:

    Existing bitMask bitResultEffect
    000Unaffected — mask bit is 0, existing 0 stays 0
    011Pixel set — mask bit forces result to 1
    101Unaffected — mask bit is 0, existing 1 stays 1
    111Pixel set (was already set)

    The bitmask from calc_pixel_addr has exactly one 1 — the target pixel's bit — and seven 0s everywhere else. OR with a 0 leaves any existing bit unchanged; OR with a 1 forces the result to 1. The seven bits that are 0 in the mask therefore pass through untouched, and only the target bit is set. This is why the read-modify-write sequence is necessary: the read preserves those seven neighbours, OR sets the one target bit, and the write puts the whole byte back.

    ; set_pixel
; Input:  B = y  (0–191)
;         C = x  (0–255)
; Output: none
; Destroys: A, B, HL
set_pixel:
    CALL calc_pixel_addr  ; HL = byte address,  A = bitmask
    OR   (HL)             ; set target bit, preserve the other seven
    LD   (HL), A          ; write back
    RET

    Save this as set_pixel.asm. Note that calc_pixel_addr must also be included in any program that uses set_pixel, since set_pixel calls it. The routine destroys B because calc_pixel_addr uses B internally as a shift counter.

    Clearing a Single Pixel

    Clearing a pixel means forcing one specific bit to 0 while leaving the other seven unchanged. OR cannot do this — OR can only set bits, never clear them. The right tool is AND, but with an inverted mask.

    AND produces a 1 only when both inputs are 1; if either input is 0 the result is 0:

    Existing bitInverted mask bitResultEffect
    010Unaffected — existing 0 stays 0
    000Pixel cleared (was already 0)
    111Unaffected — existing 1 stays 1
    100Pixel cleared — inverted mask bit forces result to 0

    The inverted mask has exactly one 0 — at the target pixel's bit position — and seven 1s everywhere else. AND with a 1 passes the existing bit through unchanged; AND with a 0 forces the result to 0. So only the target bit is cleared, and the seven neighbours are untouched.

    calc_pixel_addr returns the normal mask in A (one 1, seven 0s). CPL inverts every bit in A, producing the inverted mask (one 0, seven 1s) needed for the AND:

    ; clear_pixel
; Input:  B = y  (0–191)
;         C = x  (0–255)
; Output: none
; Destroys: A, B, HL
clear_pixel:
    CALL calc_pixel_addr  ; HL = byte address,  A = bitmask  (one 1, seven 0s)
    CPL                   ; invert A  →  inverted mask  (one 0, seven 1s)
    AND  (HL)             ; clear target bit, preserve the other seven
    LD   (HL), A          ; write back
    RET

    Save this as clear_pixel.asm.

    Toggling a Pixel

    Toggling a pixel means flipping one bit — 0 becomes 1, 1 becomes 0 — without needing to know which state it is currently in. Neither OR nor AND can do this cleanly. The right tool is XOR.

    XOR (eXclusive OR) produces a 1 when the two inputs are different, and a 0 when they are the same:

    Existing bitMask bitResultEffect
    000Unaffected — XOR with 0 never changes a bit
    011Flipped: 0 → 1
    101Unaffected
    110Flipped: 1 → 0

    XOR with a 0 leaves the existing bit unchanged. XOR with a 1 flips the existing bit, regardless of what it was. Because the mask has exactly one 1, exactly one bit is flipped and the rest are left alone. Call toggle_pixel twice on the same coordinate and the pixel returns to its original state — which makes XOR ideal for animation: you do not need to track whether the pixel is currently on or off, because the toggle works correctly either way.

    ; toggle_pixel
; Input:  B = y  (0–191)
;         C = x  (0–255)
; Output: none
; Destroys: A, B, HL
toggle_pixel:
    CALL calc_pixel_addr  ; HL = byte address,  A = bitmask
    XOR  (HL)             ; flip target bit, leave the other seven unchanged
    LD   (HL), A          ; write back
    RET

    Save this as toggle_pixel.asm.

    The three operations together cover every pixel state transition possible:

    OperationInstructionUse when
    SetOR (HL)You want the pixel on, regardless of current state
    ClearCPL then AND (HL)You want the pixel off, regardless of current state
    ToggleXOR (HL)You want to flip the pixel without checking its state

    A Bouncing Pixel

    This program uses set_pixel and clear_pixel together to animate a pixel bouncing left and right across pixel row 88. It introduces three new ideas.

    A direction variable stored in memory. The pixel's x coordinate is kept in a memory byte rather than a register, because the animation loop must preserve it across many HALTs and subroutine calls. The direction is stored as a signed byte: 1 means moving right, $FF means moving left. On the Z80, $FF is the two's complement representation of −1 — adding $FF to an 8-bit value is identical to subtracting 1. The direction byte is added to x each frame to advance the pixel; negating it reverses direction.

    CP — ComPare. CP n subtracts n from A and sets the flags exactly as SUB would, but throws away the result — A is unchanged. This lets you test a value and branch on the outcome without overwriting A. After CP 0, the Zero flag is set if A was 0; after CP 255, the Zero flag is set if A was 255. Combined with JR Z, this detects when the pixel hits either edge.

    NEG — Negate. NEG computes A = 0 − A, which is the two's complement negation of A. Applied to 1 it produces $FF (−1); applied to $FF it produces 1. This flips the direction between +1 and −1 with a single instruction, with no need for a branch or a comparison.

    The animation loop follows the pattern every game uses: clear old position → update state → draw new position → wait for next frame:

        ORG  $8000

main:
    EI
    LD   B, 88            ; y = 88 — fixed for the whole program
    LD   A, 0
    LD   (px), A          ; starting x = 0
    LD   A, 1
    LD   (dir), A         ; starting direction = +1 (moving right)

.loop:
    HALT                  ; sync to frame start — clear+draw finish before the beam reaches row 88

    ; — Clear pixel at current position —
    LD   A, (px)
    LD   C, A             ; C = current x
    PUSH BC
    CALL clear_pixel      ; erase the dot  (destroys A, B, HL)
    POP  BC               ; restore B = y = 88,  C = current x

    ; — Advance x by direction —
    LD   A, (dir)
    ADD  A, C             ; x = x + direction
    LD   (px), A          ; save new x

    ; — Reverse direction at edges —
    CP   255              ; did x reach the right edge?
    JR   Z, .reverse
    CP   0               ; did x reach the left edge?
    JR   NZ, .draw        ; neither edge — keep going
.reverse:
    LD   A, (dir)
    NEG                   ; negate direction: 1 → $FF ($FF = −1),  $FF → 1
    LD   (dir), A

.draw:
    ; — Draw pixel at new position —
    LD   A, (px)
    LD   C, A             ; C = new x
    PUSH BC
    CALL set_pixel        ; draw the dot  (destroys A, B, HL)
    POP  BC               ; restore B = y = 88

    JR   .loop            ; repeat forever

px:  DB  0               ; current x position
dir: DB  1               ; direction: 1 = right,  $FF = left

    INCLUDE "calc_pixel_addr.asm"
    INCLUDE "set_pixel.asm"
    INCLUDE "clear_pixel.asm"

    END  $8000

    Assemble with pasmo --tapbas bounce.asm bounce.tap and load the TAP into your emulator — the BASIC loader runs automatically. The pixel travels right across the screen, bounces off the right edge, travels left, bounces off the left edge, and repeats indefinitely. On real Spectrum hardware the motion is perfectly smooth. On an emulator running on a modern computer you may see occasional stuttering — the Spectrum outputs frames at 50 Hz but most monitors refresh at 60 Hz, so roughly one in every six Spectrum frames is held on screen for two monitor refresh cycles instead of one. This is a display hardware mismatch rather than a code problem; the Z80 is producing frames at a perfectly constant rate.

    Notice that HALT is at the top of the loop, not the bottom. This matters for two reasons — speed consistency and flicker.

    Speed. The interrupt fires at exactly 50 Hz. Every iteration starts by waiting for the interrupt, then does all its work — clear, advance, draw — in the ~19.85 ms gap before the next one arrives. Because those operations together take only a few hundred microseconds, the next HALT is always reached long before the following interrupt fires, giving a consistent 20 ms wait every time and moving the pixel at a rock-steady 50 pixels per second. Placing HALT at the bottom of the loop instead would break this: if the interrupt happened to fire just before HALT was reached, HALT would return almost immediately and the pixel would advance again after only a few microseconds, producing alternating very-short and very-long frames — the pixel darts then pauses, darts then pauses. HALT at the top is the fix.

    Flicker. The Spectrum's TV beam scans from the top of the screen downward. The interrupt fires when the beam reaches the bottom — the start of the vertical blanking period — so returning from HALT means the beam is about to start a fresh pass from the top. Row 88 is roughly halfway down, which means the clear and draw both complete approximately 9 ms before the beam reaches that row. With HALT at the bottom, clear and draw happen at an unpredictable point mid-frame; if the beam happened to be scanning row 88 between those two calls the pixel would visibly flicker.

    Notice also that B is saved with PUSH BC and restored with POP BC around each CALL. Both set_pixel and clear_pixel call calc_pixel_addr, which destroys B. The y coordinate must survive those calls because it is used again in the next iteration, so it is held in B between frames and pushed to the stack for the duration of each call.

    Key fact: OR sets, AND-with-inverted-mask clears, XOR toggles. Every pixel operation in this book is one of these three patterns applied to the byte that calc_pixel_addr identifies. The choice between them depends entirely on what you want to happen to a bit that is already in the state you are trying to produce — OR leaves it set, AND leaves it clear, XOR flips it.

    4. Drawing Lines

    [Back to Contents]

    Horizontal and vertical lines are the building blocks of almost every game screen — borders, platforms, maze walls, health bars, HUD frames. A line is nothing more than a sequence of pixels, but drawing it efficiently matters: a naive approach that calls set_pixel for every pixel is eight times slower than it needs to be. This chapter builds three library routines — draw_hline, draw_vline, and draw_line — and closes with a screen border example that uses the two axis-aligned routines.

    Horizontal Lines

    A horizontal line shares one y coordinate across all its pixels. On the Spectrum, eight consecutive pixels on the same row are packed into a single byte of the display file. Writing $FF to that byte sets all eight at once — eight times faster than calling set_pixel eight times. The routine below exploits this wherever it can.

    The Three-Region Model

    A horizontal line from x1 to x2 on row y spans up to three regions in the display file:

    RegionDescriptionHow to draw
    Left partial bytex1 to the end of its byte (if x1 is not byte-aligned)OR a mask — preserve pixels to the left of x1
    Middle full bytesAll complete bytes between the two partial endsLD (HL), $FF — overwrite all eight pixels
    Right partial byteStart of the last byte to x2 (if x2 is not byte-aligned)OR a mask — preserve pixels to the right of x2

    When x1 and x2 fall inside the same byte there is only one region: a single OR combining both the left and right masks.

    Advancing along a row is just INC L — not INC HL. All bytes on the same pixel row share the same H byte; only the low byte changes as the column advances from 0 to 31. Because a row spans at most 32 bytes, L never overflows into H, so INC L is safe and one byte shorter than INC HL.

    Edge Masks

    The left-edge mask covers bit positions from x1's pixel down to bit 0 of the byte. The right-edge mask covers bit positions from bit 7 down to x2's pixel. Both depend only on the low three bits of x — that is, x & 7, the pixel's position within its byte. There are only eight possible values for each, so a lookup table is the natural first idea:

    x & 7Left mask
    (x1 to bit 0)    		Right mask
    (bit 7 to x2)
    0%11111111%10000000
    1%01111111%11000000
    2%00111111%11100000
    3%00011111%11110000
    4%00001111%11111000
    5%00000111%11111100
    6%00000011%11111110
    7%00000001%11111111

    To read from such a table you load its base address into HL, add the index (x & 7) to L, then read through HL. That approach works, but it consumes HL — which draw_hline needs to hold the current screen address throughout the routine. Saving and restoring HL around every table lookup adds PUSH/POP pairs that erode the speed advantage the table was supposed to provide.

    For at most seven shift operations it is simpler and no slower to compute the mask directly at runtime using SRL and SLA.

    draw_hline

    SRL (Shift Right Logical) shifts A one bit right, filling bit 7 with 0. Repeating it n times produces $FF >> n — exactly the left-edge mask. SLA (Shift Left Arithmetic) shifts A one bit left, filling bit 0 with 0. Repeating it n times produces $FF << n — the right-edge mask. Both are CB-prefixed instructions, two bytes each, and both are valid on every Z80. The shift count is at most 7, so the loop runs at most seven iterations — fast enough that no table is needed.

    The middle-byte count requires the byte column of x1 and x2 — that is, x divided by 8 (x >> 3). The Z80 has no right-shift instruction that operates on A directly in fewer than two bytes per shift, but RRCA (Rotate Right Circular A) is a single byte and very fast. After three RRCAs the original bits 7–3 have rotated into positions 4–0. AND %00011111 then masks away the three bits that wrapped around from the bottom, leaving exactly x >> 3 in the low five bits.

    ; draw_hline
; Draw a horizontal line on pixel row y from x1 to x2.
; Input:  B = y   (0–191)
;         C = x1  (0–255, left end)
;         D = x2  (0–255, right end, must be >= x1)
; Output: none
; Destroys: A, B, C, D, E, H, L
; Note: calc_pixel_addr preserves C and D, so x1 and x2 survive the CALL.
draw_hline:
    CALL calc_pixel_addr   ; HL = byte address of x1  (C=x1 and D=x2 are preserved)

    ; — Same-byte check: XOR high bits of x1 and x2 —
    LD   A, D
    XOR  C
    AND  %11111000         ; non-zero if x1 and x2 are in different bytes
    JR   Z, .same_byte

    ; — Left partial byte: mask = $FF >> (x1 & 7) —
    LD   A, C
    AND  %00000111         ; shift count = x1 mod 8
    LD   B, A
    LD   A, $FF
    JR   Z, .lm_done       ; count=0: x1 is at leftmost bit, mask stays $FF
.lm_loop:
    SRL  A                 ; shift right, 0 fills from top — one step of $FF >> n
    DJNZ .lm_loop
.lm_done:
    OR   (HL)              ; set pixels from x1 down to end of byte, preserve left neighbours
    LD   (HL), A
    INC  L                 ; next byte (same row — INC L safe, not INC HL)

    ; — Middle full bytes: count = (x2>>3) - (x1>>3) - 1 —
    ; Extract byte column via three RRCA then AND %00011111
    LD   A, D
    RRCA
    RRCA
    RRCA
    AND  %00011111         ; x2 byte column (0–31)
    LD   E, A
    LD   A, C
    RRCA
    RRCA
    RRCA
    AND  %00011111         ; x1 byte column (0–31)
    LD   B, A
    LD   A, E
    SUB  B                 ; x2col - x1col
    DEC  A                 ; - 1 = number of middle bytes
    JR   Z, .right_byte    ; zero: x1 and x2 are adjacent bytes, no middle
    JR   C, .right_byte    ; carry guard (should not occur)
    LD   B, A
.middle:
    LD   (HL), $FF         ; all 8 pixels set
    INC  L
    DJNZ .middle

.right_byte:
    ; — Right partial byte: mask = $FF << (7 - x2 & 7) —
    LD   A, D
    AND  %00000111         ; x2 mod 8
    LD   B, A
    LD   A, 7
    SUB  B                 ; shift count = 7 - (x2 mod 8)
    LD   B, A
    LD   A, $FF
    JR   Z, .rm_done       ; count=0: x2 is at rightmost bit, mask stays $FF
.rm_loop:
    SLA  A                 ; shift left, 0 fills from bottom — one step of $FF << n
    DJNZ .rm_loop
.rm_done:
    OR   (HL)              ; set pixels from start of byte down to x2, preserve right neighbours
    LD   (HL), A
    RET

.same_byte:
    ; — Both x1 and x2 in the same byte: AND the left and right masks —
    LD   A, C
    AND  %00000111
    LD   B, A
    LD   A, $FF
    JR   Z, .sb_lm_done
.sb_lm_loop:
    SRL  A
    DJNZ .sb_lm_loop
.sb_lm_done:
    LD   E, A              ; E = left mask

    LD   A, D
    AND  %00000111
    LD   B, A
    LD   A, 7
    SUB  B
    LD   B, A
    LD   A, $FF
    JR   Z, .sb_rm_done
.sb_rm_loop:
    SLA  A
    DJNZ .sb_rm_loop
.sb_rm_done:
    AND  E                 ; intersection: only the pixels strictly between x1 and x2
    OR   (HL)
    LD   (HL), A
    RET

    Save this as draw_hline.asm. Any program that uses it must also INCLUDE "calc_pixel_addr.asm".

    Vertical Lines

    A vertical line shares one x coordinate across all its pixels. Consecutive pixels on the same column are in completely different bytes — different rows have different TTRRRLLL addresses — so writing eight pixels at once is not possible. Every pixel on a vertical line needs its own display file byte access.

    There is no single magic constant that steps one pixel row in all cases. The address formula from Chapter 1 shows why:

    ; Address = $4000 + (T × $800) + (L × $100) + (R × $20) + C
; (T = third, bits 7:6 of y;  L = scan line, bits 2:0 of y;  R = char row, bits 5:3 of y)
;
; L (scan line) lives in H bits 2:0 — one step = INC H  (+$0100)
; R (char row)  lives in L bits 7:5 — one step = ADD $20 to L  (+$0020)
;
; Moving from scan line L to L+1 increases the address by $0100 (= INC H).
; That works cleanly while L < 7.
; When L = 7, INC H would carry into H bit 3 (part of the T field) — wrong.
; Instead: AND H with $F8 to reset L=0, then ADD $20 to the low byte to step R.
; If R then wraps from 7 to 0, add $08 to H to step T.
;
; Example: y=7  → H=$47, L=C      (T=0, R=0, L=7)
;          y=8  → H=$40, L=$20+C  (T=0, R=1, L=0  — character row stepped)
;          y=63 → H=$47, L=$E0+C  (T=0, R=7, L=7  — end of first third)
;          y=64 → H=$48, L=C      (T=1, R=0, L=0  — third stepped)

    The scan line (L) field is in H bits 2:0, so advancing one pixel row is normally a single INC H. The special case at L = 7 needs explicit handling: carry from H bits 2:0 into bit 3 would corrupt the T field, so the code clears the LLL bits with AND $F8 and advances R separately.

    draw_vline

    ; draw_vline
; Draw a vertical line on pixel column x from y1 to y2.
; Input:  B = y1  (0–191, top)
;         C = x   (0–255)
;         D = y2  (0–191, bottom, must be >= y1)
; Output: none
; Destroys: A, B, C, D, E, H, L
draw_vline:
    PUSH BC                ; save y1 (B) — calc_pixel_addr destroys B
    CALL calc_pixel_addr   ; HL = byte address,  A = bitmask for column x
    LD   E, A              ; save bitmask in E before POP overwrites A
    POP  BC                ; restore B = y1  (C = x, no longer needed)

    LD   A, D              ; y2
    SUB  B                 ; y2 - y1  (B = y1 restored by POP)
    INC  A                 ; pixel count = y2 - y1 + 1
    LD   B, A              ; B = DJNZ counter

    LD   C, E              ; bitmask into C
dv_loop:
    LD   A, C              ; bitmask
    OR   (HL)              ; set pixel, preserve neighbours
    LD   (HL), A
    ; advance HL to the next pixel row
    LD   A, H
    AND  $07               ; isolate scan line field (LLL, H bits 2:0)
    CP   $07               ; at scan line 7?
    JR   Z, dv_cross       ; yes: step the character row explicitly
    INC  H                 ; no: simple scan line increment
    DJNZ dv_loop
    RET
dv_cross:
    ; Scan line 7 → 0: reset LLL, step RRR in L
    LD   A, H
    AND  $F8               ; clear H bits 2:0 (LLL = 0), T field in bits 4:3 preserved
    LD   H, A
    LD   A, L
    ADD  A, $20            ; step RRR (character row field, L bits 7:5)
    LD   L, A
    JR   NC, dv_next       ; no carry: still in same third
    LD   A, H
    ADD  A, $08            ; RRR overflowed: step TT (third field, H bits 4:3)
    LD   H, A
dv_next:
    DJNZ dv_loop
    RET

    Save this as draw_vline.asm. Any program using it must also INCLUDE "calc_pixel_addr.asm".

    Two register discipline points worth noting. First, calc_pixel_addr destroys B (it uses B as an internal shift counter), so y1 must be saved on the stack before the call and restored with POP BC afterwards. Second, the bitmask is moved from E to C before the loop so that A is free for the row-advance calculations inside dv_cross without disturbing the bitmask or the DJNZ counter in B.

    Bresenham's Line Algorithm

    Horizontal and vertical lines cover most game needs, but arbitrary diagonal lines require a general solution. Bresenham's line algorithm draws the closest integer approximation to any straight line using only addition and subtraction — no multiplication, no division, no floating-point arithmetic, making it well-suited to the Z80.

    The Idea

    Imagine walking from (x1, y1) to (x2, y2) one step at a time along the longer axis (the major axis). At each step you advance one pixel along the major axis. Occasionally you also step one pixel along the shorter axis (the minor axis) to track the true line's slope. The question is: when do you take the minor step?

    Bresenham's answer: keep an integer error variable that accumulates the difference between where the true line is and where the drawn line is. Each major step adds a fixed amount to the error. When the error exceeds the half-way threshold, take a minor step and subtract the threshold from the error. The result is a line that stays within half a pixel of the true line at every point.

    The algorithm handles all directions by tracking the sign of dx and dy separately:

    ; Bresenham variables
;   dx = |x2 - x1|,  sx = +1 if x2 > x1 else -1 ($FF)
;   dy = |y2 - y1|,  sy = +1 if y2 > y1 else -1 ($FF)
;   err = dx - dy
;
; Each iteration:
;   set pixel at (x, y)
;   if x==x2 and y==y2: done
;   e2 = 2 * err
;   if e2 > -dy: err -= dy;  x += sx
;   if e2 <  dx: err += dx;  y += sy

    On the Z80, 2 * err is just ADD A, A (left shift by one). The comparisons use signed arithmetic — JP M (jump if minus, i.e. if the sign flag is set) rather than the unsigned JR C.

    draw_line

    The Z80 has no instruction to add or subtract a memory-addressed value directly to A except via (HL). Instructions like ADD A, (addr) and SUB (addr) are not valid. Every memory operand must be loaded into a register first: LD B, A to save A, then LD A, (addr), then ADD A, B. Bresenham requires several such operations, which is why the routine stores all working state in named memory variables and loads them explicitly as needed.

    A second constraint: with 8-bit signed arithmetic, the error variable fits in a byte only when dx and dy are each at most 63. Longer diagonals require 16-bit error tracking; draw_line as written works correctly for lines up to 63 pixels in each dimension — sufficient for most game sprites and HUD elements.

    ; draw_line
; Draw a line from (x1,y1) to (x2,y2) using Bresenham's algorithm.
; Input:  B = y1  (0–191)    C = x1  (0–255)
;         D = y2  (0–191)    E = x2  (0–255)
; Constraint: |x2-x1| and |y2-y1| must each be at most 63.
; Output: none    Destroys: A, B, C, D, E, H, L
draw_line:
    LD   A, C
    LD   (dl_x),  A         ; x = x1
    LD   A, B
    LD   (dl_y),  A         ; y = y1
    LD   A, E
    LD   (dl_x2), A         ; target x2
    LD   A, D
    LD   (dl_y2), A         ; target y2

    ; dx = |x2-x1|,  sx = +1 or $FF (-1)
    LD   A, E
    SUB  C                  ; A = x2 - x1 (signed)
    JP   P, .dx_pos
    NEG                     ; make positive for dx
    LD   (dl_dx), A
    LD   A, $FF
    LD   (dl_sx), A          ; sx = $FF (-1): moving left
    JR   .dy_calc
.dx_pos:
    LD   (dl_dx), A
    LD   A, 1
    LD   (dl_sx), A          ; sx = 1: moving right

.dy_calc:
    ; dy = |y2-y1|,  sy = +1 or $FF (-1)
    LD   A, D
    SUB  B                  ; A = y2 - y1 (signed)
    JP   P, .dy_pos
    NEG
    LD   (dl_dy), A
    LD   A, $FF
    LD   (dl_sy), A          ; sy = $FF (-1): moving up
    JR   .err_calc
.dy_pos:
    LD   (dl_dy), A
    LD   A, 1
    LD   (dl_sy), A          ; sy = 1: moving down

.err_calc:
    ; err = dx - dy
    LD   A, (dl_dx)
    LD   B, A
    LD   A, (dl_dy)
    LD   C, A
    LD   A, B
    SUB  C                  ; A = dx - dy
    LD   (dl_err), A

dl_loop:
    ; — Draw pixel at (x, y) —
    LD   A, (dl_y)
    LD   B, A
    LD   A, (dl_x)
    LD   C, A
    PUSH BC
    CALL set_pixel
    POP  BC

    ; — Check if done: x==x2 and y==y2 —
    LD   A, (dl_x2)
    LD   B, A
    LD   A, (dl_x)
    CP   B
    JR   NZ, dl_not_done
    LD   A, (dl_y2)
    LD   B, A
    LD   A, (dl_y)
    CP   B
    JR   Z, dl_done
dl_not_done:

    ; — e2 = 2 * err —
    LD   A, (dl_err)
    ADD  A, A               ; e2 = err * 2 (left shift by 1)
    LD   B, A               ; B = e2, preserved across both branch tests below

    ; — if e2 > -dy: err -= dy;  x += sx —
    ; Test: dy + e2 > 0  ↔  e2 > -dy
    LD   A, (dl_dy)
    ADD  A, B               ; A = dy + e2
    JR   Z, dl_skip_x       ; e2 == -dy: condition false
    JP   M, dl_skip_x       ; e2 < -dy: condition false
    LD   A, (dl_err)
    LD   C, A
    LD   A, (dl_dy)
    LD   D, A
    LD   A, C
    SUB  D                  ; err -= dy  (load dy to D, subtract from err in C)
    LD   (dl_err), A
    LD   A, (dl_x)
    LD   C, A
    LD   A, (dl_sx)
    ADD  A, C               ; x += sx  ($FF + x = x - 1 in 8-bit arithmetic)
    LD   (dl_x), A
dl_skip_x:

    ; — if e2 < dx: err += dx;  y += sy —
    ; Test: e2 - dx < 0  ↔  e2 < dx
    LD   A, B               ; restore e2 (B unchanged since we saved it)
    LD   C, A
    LD   A, (dl_dx)
    LD   D, A
    LD   A, C
    SUB  D                  ; A = e2 - dx
    JP   P, dl_skip_y       ; positive or zero: e2 >= dx, condition false
    LD   A, (dl_err)
    LD   C, A
    LD   A, (dl_dx)
    ADD  A, C               ; err += dx
    LD   (dl_err), A
    LD   A, (dl_y)
    LD   C, A
    LD   A, (dl_sy)
    ADD  A, C               ; y += sy
    LD   (dl_y), A
dl_skip_y:

    JR   dl_loop

dl_done:
    RET

dl_x:   DB 0   ; current x
dl_y:   DB 0   ; current y
dl_x2:  DB 0   ; target x
dl_y2:  DB 0   ; target y
dl_dx:  DB 0   ; |x2-x1|
dl_dy:  DB 0   ; |y2-y1|
dl_sx:  DB 0   ; x step: 1 or $FF
dl_sy:  DB 0   ; y step: 1 or $FF
dl_err: DB 0   ; Bresenham error accumulator

    Save this as draw_line.asm. Any program using it must also INCLUDE "calc_pixel_addr.asm" and INCLUDE "set_pixel.asm".

    Every memory load follows the same pattern: LD A, (addr) to get the value into A, then LD reg, A to move it to a working register, leaving A free for the arithmetic. This is the only way to operate on memory-resident values on the Z80 — there is no ADD A, (addr) instruction.

    JP P / JP M — Jump if Positive / Jump if Minus. These branch on the Sign flag, which reflects the most significant bit of the last arithmetic result. A result with bit 7 set is treated as negative in two's complement; JP M jumps if that bit is set, JP P jumps if it is clear. Bresenham's comparisons must be signed because the error accumulator represents a signed difference.

    The dl_x, dl_y and companion variables at the end of the routine are writable working storage, not constants. The routine overwrites them on every call. This means draw_line.asm must be assembled into RAM — it cannot be placed in ROM. For a pasmo --tapbas program loaded at $8000 this is always the case.

    draw_line example

    The following program draws four diagonal lines radiating from the screen centre, one into each quadrant, demonstrating all four directions of travel.

        ORG  $8000

main:
    ; centre (128,96) to top-left (68,36)  — dx=60, dy=60

    ; centre (128,96) to bottom-left (68,156)  — dx=60, dy=60

    ; centre (128,96) to bottom-right (188,156)  — dx=60, dy=60

    INCLUDE "draw_line.asm"

    END  $8000

    Assemble with pasmo --tapbas diagonals.asm diagonals.tap. Four lines radiate from near the screen centre, forming an X. Each line spans exactly 60 pixels in both x and y — well within the 63-pixel per-axis constraint, so the 8-bit error accumulator does not overflow.

    A Screen Border

    This program draws a one-pixel border around the full screen using draw_hline and draw_vline, then loops forever so BASIC cannot overwrite the display.

        ORG  $8000

main:
    ; Top edge: y=0, x1=0, x2=255
    LD   B, 0
    LD   C, 0
    LD   D, 255
    CALL draw_hline

    ; Bottom edge: y=191, x1=0, x2=255
    LD   B, 191
    LD   C, 0
    LD   D, 255
    CALL draw_hline

    ; Left edge: x=0, y1=0, y2=191
    LD   B, 0
    LD   C, 0
    LD   D, 191
    CALL draw_vline

    ; Right edge: x=255, y1=0, y2=191
    LD   B, 0
    LD   C, 255
    LD   D, 191
    CALL draw_vline

    EI
.done:
    HALT
    JR   .done             ; loop forever — reset to exit

    INCLUDE "calc_pixel_addr.asm"
    INCLUDE "draw_hline.asm"
    INCLUDE "draw_vline.asm"

    END  $8000

    Assemble with pasmo --tapbas border.asm border.tap and load the TAP into your emulator — the BASIC loader runs automatically. A white rectangle appears around the full screen boundary: two horizontal lines at y=0 and y=191, two vertical lines at x=0 and x=255.

    The program does not end with RET. If it returned to BASIC, the interpreter would print its 0 OK report at the bottom of the screen — character rows 20–23, which cover pixel rows 160–191. That would immediately erase the bottom border line at y=191. Instead the program loops on HALT forever, waiting for interrupts and doing nothing else. The border stays visible until you reset the machine.

    Notice that draw_line is not included here — this example does not need it. Include only the library files a program actually calls; unused routines waste memory and assembly time.

    Key fact: horizontal lines are fast because an entire byte of eight pixels can be written in one instruction. Vertical lines must touch a separate byte for every pixel but gain efficiency from the constant +$20 address step between rows. Arbitrary lines call set_pixel for every point and are the slowest of the three — use draw_hline and draw_vline whenever the line is axis-aligned.

    5. Drawing Shapes

    [Back to Contents]

    The line routines from chapter 4 are the foundation for every closed shape. A rectangle is four lines. A filled rectangle is a stack of horizontal lines. A circle is a sequence of pixel pairs arranged by an integer decision variable. This chapter builds four new library routines — draw_rect, fill_rect, draw_circle, and flood_fill — and closes with a focused example for each one.

    Rectangles

    Hollow Rectangle

    A hollow rectangle is exactly four lines: top edge, bottom edge, left edge, right edge. draw_hline draws the horizontal edges and draw_vline draws the vertical ones. The corners are included in the horizontal calls; the vertical calls run between the corners so no pixel is drawn twice — though overdrawing with OR is harmless in any case.

    ; draw_rect
; Draw a hollow rectangle.
; Input:  B = y1  (0–191, top)
;         C = x1  (0–255, left)
;         D = y2  (0–191, bottom, must be >= y1)
;         E = x2  (0–255, right,  must be >= x1)
; Destroys: A, B, C, D, E, H, L
draw_rect:
    ; Top edge: y=y1, x1 to x2
    PUSH BC
    PUSH DE
    LD   D, E              ; draw_hline needs x2 in D; E holds x2, D holds y2
    CALL draw_hline        ; B=y1, C=x1, D=x2
    POP  DE
    POP  BC

    ; Bottom edge: y=y2, x1 to x2
    PUSH BC
    PUSH DE
    LD   B, D              ; y = y2
    LD   D, E              ; draw_hline needs x2 in D
    CALL draw_hline        ; B=y2, C=x1, D=x2
    POP  DE
    POP  BC

    ; Skip vertical edges if height is 1 (y1 == y2)
    LD   A, B
    CP   D                 ; y1 == y2?
    JR   Z, dr_no_vert

    ; Left edge: x=x1, y1+1 to y2-1
    PUSH BC
    PUSH DE
    INC  B                 ; y1+1 — skip corner already drawn
    DEC  D                 ; y2-1 — skip corner already drawn
    CALL draw_vline        ; B=y1+1, C=x1, D=y2-1
    POP  DE
    POP  BC

    ; Right edge: x=x2, y1+1 to y2-1
    INC  B                 ; y1+1
    DEC  D                 ; y2-1
    LD   C, E              ; x = x2
    CALL draw_vline        ; B=y1+1, C=x2, D=y2-1
dr_no_vert:
    RET

    Save this as draw_rect.asm. It requires draw_hline.asm, draw_vline.asm, and calc_pixel_addr.asm.

    The PUSH/POP pairs preserve the original coordinates across each sub-call. draw_hline and draw_vline both destroy B, C, D — so the inputs must be saved before every call and restored before the next. The vertical edges run from y1+1 to y2-1 to avoid drawing the corners twice; with OR semantics this is a style choice rather than a correctness requirement. The LD A, B / CP D / JR Z, .no_vert guard before the vertical calls handles the degenerate case where y1 == y2 — without it, the vertical calls would receive an inverted range (y1+1 > y2-1) and produce undefined behaviour.

    Filled Rectangle

    A filled rectangle is a horizontal line repeated for every row from y1 to y2. The row count is y2 - y1 + 1. The row counter is kept in memory and decremented with DEC A / JR NZ — DJNZ cannot be used because draw_hline destroys B on every call.

    ; fill_rect
; Draw a solid filled rectangle.
; Input:  B = y1  (0–191, top)
;         C = x1  (0–255, left)
;         D = y2  (0–191, bottom, must be >= y1)
;         E = x2  (0–255, right,  must be >= x1)
; Destroys: A, B, C, D, E, H, L
fill_rect:
    LD   A, D
    SUB  B                 ; y2 - y1
    INC  A                 ; row count = y2 - y1 + 1
    LD   (fr_rows), A
    LD   A, B
    LD   (fr_y),    A      ; save starting y
    LD   A, C
    LD   (fr_x1),   A      ; save x1
    LD   A, E
    LD   (fr_x2),   A      ; save x2

fr_loop:
    LD   A, (fr_y)
    LD   B, A              ; current row
    LD   A, (fr_x1)
    LD   C, A              ; x1
    LD   A, (fr_x2)
    LD   D, A              ; x2
    CALL draw_hline

    LD   A, (fr_y)
    INC  A
    LD   (fr_y), A          ; advance to next row

    LD   A, (fr_rows)
    DEC  A
    LD   (fr_rows), A
    JR   NZ, fr_loop
    RET

fr_y:    DB 0
fr_x1:   DB 0
fr_x2:   DB 0
fr_rows: DB 0

    Save this as fill_rect.asm. It requires draw_hline.asm and calc_pixel_addr.asm.

    DJNZ cannot be used directly here because draw_hline destroys B. The row counter is kept in memory (fr_rows) and decremented with DEC A / JR NZ instead. The same pattern — store working state in named variables, reload before each sub-call — is the standard approach whenever a called routine destroys the registers you need to preserve.

    Filled rectangles are the fastest shape per pixel: draw_hline writes eight pixels per instruction in the middle of each row. A 32×32 filled rectangle writes all 32 middle bytes per row with 32 LD (HL), $FF instructions and only touches partial bytes at the left and right edges.

    Circles

    The Midpoint Circle Algorithm

    Drawing a circle with floating-point trigonometry is too slow for the Z80. The midpoint circle algorithm (sometimes called Bresenham's circle algorithm) draws a circle using only integer addition and subtraction — no multiply, divide, or sine table.

    The algorithm exploits 8-fold symmetry: a circle centred at (cx, cy) is symmetric across both axes and both diagonals. If you know the pixel at offset (+x, +y) lies on the circle, the seven mirrors are immediate:

    OctantPixel
    1(cx+x, cy+y)
    2(cx−x, cy+y)
    3(cx+x, cy−y)
    4(cx−x, cy−y)
    5(cx+y, cy+x)
    6(cx−y, cy+x)
    7(cx+y, cy−x)
    8(cx−y, cy−x)

    Each step of the algorithm computes one new (x, y) offset and plots all eight mirrors. The decision variable d starts at 1 - radius and tells the algorithm whether to step only in x or also in y:

    ; Midpoint circle — pseudocode
;   x = 0,  y = radius,  d = 1 - radius
;
; while x <= y:
;   plot 8 symmetric pixels
;   x += 1
;   if d < 0:  d += 2*x + 1
;   else:      y -= 1 ;  d += 2*(x - y) + 1

    On the Z80, 2*x is ADD A, A. The signed comparison d < 0 tests the Sign flag after updating d — the same JP M technique used in draw_line.

    draw_circle

    All eight pixel plots call set_pixel, so B and C (the y and x inputs) must be reloaded before each call. The centre coordinates and the current x/y offsets are kept in memory. The constraint is that centre ± radius must stay within the screen boundary (0–255 in x, 0–191 in y); checking this is the caller's responsibility.

    ; draw_circle
; Draw a circle using the midpoint algorithm.
; Input:  B = cy  (centre y, 0-191)
;         C = cx  (centre x, 0-255)
;         D = radius  (must keep centre +/- radius within screen bounds)
; Destroys: A, B, C, D, E, H, L
; Limitation: dc_d is a single signed byte. For radius > 129 the initial
;             value 1-radius underflows, producing an incorrect circle.
;             For typical Spectrum use (radius <= 95) this is not a concern.
draw_circle:
    LD   A, B
    LD   (dc_cy), A        ; save centre y
    LD   A, C
    LD   (dc_cx), A        ; save centre x
    LD   A, D              ; radius
    LD   (dc_y),  A        ; y offset starts at radius
    XOR  A
    LD   (dc_x),  A        ; x offset starts at 0

    ; d = 1 - radius
    LD   A, 1
    SUB  D
    LD   (dc_d),  A

dc_loop:
    ; while x <= y
    LD   A, (dc_x)
    LD   B, A
    LD   A, (dc_y)
    CP   B                 ; y - x: if x > y, done
    JR   C, dc_done        ; carry set means y < x

    ; plot 8 symmetric pixels
    CALL dc_plot8

    ; x += 1
    LD   A, (dc_x)
    INC  A
    LD   (dc_x), A

    ; if d < 0: d += 2*x + 1
    LD   A, (dc_d)
    OR A
    JP   M, dc_d_neg

; d >= 0: d += 2*(x-y) + 1,  y -= 1
    LD   B, A              ; save d

    ; Update Y first
    LD   A, (dc_y)
    DEC  A
    LD   (dc_y), A         ; y -= 1
    LD   D, A              ; D = new y

    ; Calculate 2*(x-y) + 1
    LD   A, (dc_x)         ; A = new x
    SUB  D                 ; A = x - y
    ADD  A, A              ; 2*(x - y)
    INC  A                 ; 2*(x - y) + 1
    ADD  A, B              ; d += 2*(x-y) + 1
    LD   (dc_d), A
    JR   dc_loop

dc_d_neg:
    ; d += 2*x + 1
    LD   B, A              ; save d
    LD   A, (dc_x)
    ADD  A, A              ; 2*x
    INC  A                 ; 2*x + 1
    ADD  A, B              ; d += 2*x + 1
    LD   (dc_d), A
    JR   dc_loop

dc_done:
    RET

; dc_plot8 -- plot the 8 symmetric pixels for current (x, y) offsets
; set_pixel destroys all registers, so dc_x and dc_y are reloaded from
; memory before every pixel. D = x offset, E = y offset throughout.
dc_plot8:
    ; (cx+x, cy+y)
    LD   A, (dc_x)
    LD   D, A
    LD   A, (dc_y)
    LD   E, A
    LD   A, (dc_cy)
    ADD  A, E
    LD   B, A
    LD   A, (dc_cx)
    ADD  A, D
    LD   C, A
    CALL set_pixel

    ; (cx-x, cy+y)
    LD   A, (dc_x)
    LD   D, A
    LD   A, (dc_y)
    LD   E, A
    LD   A, (dc_cy)
    ADD  A, E
    LD   B, A
    LD   A, (dc_cx)
    SUB  D
    LD   C, A
    CALL set_pixel

    ; (cx+x, cy-y)
    LD   A, (dc_x)
    LD   D, A
    LD   A, (dc_y)
    LD   E, A
    LD   A, (dc_cy)
    SUB  E
    LD   B, A
    LD   A, (dc_cx)
    ADD  A, D
    LD   C, A
    CALL set_pixel

    ; (cx-x, cy-y)
    LD   A, (dc_x)
    LD   D, A
    LD   A, (dc_y)
    LD   E, A
    LD   A, (dc_cy)
    SUB  E
    LD   B, A
    LD   A, (dc_cx)
    SUB  D
    LD   C, A
    CALL set_pixel

    ; (cx+y, cy+x)  -- x and y roles swap
    LD   A, (dc_x)
    LD   D, A
    LD   A, (dc_y)
    LD   E, A
    LD   A, (dc_cy)
    ADD  A, D
    LD   B, A
    LD   A, (dc_cx)
    ADD  A, E
    LD   C, A
    CALL set_pixel

    ; (cx-y, cy+x)
    LD   A, (dc_x)
    LD   D, A
    LD   A, (dc_y)
    LD   E, A
    LD   A, (dc_cy)
    ADD  A, D
    LD   B, A
    LD   A, (dc_cx)
    SUB  E
    LD   C, A
    CALL set_pixel

    ; (cx+y, cy-x)
    LD   A, (dc_x)
    LD   D, A
    LD   A, (dc_y)
    LD   E, A
    LD   A, (dc_cy)
    SUB  D
    LD   B, A
    LD   A, (dc_cx)
    ADD  A, E
    LD   C, A
    CALL set_pixel

    ; (cx-y, cy-x)
    LD   A, (dc_x)
    LD   D, A
    LD   A, (dc_y)
    LD   E, A
    LD   A, (dc_cy)
    SUB  D
    LD   B, A
    LD   A, (dc_cx)
    SUB  E
    LD   C, A
    CALL set_pixel

    RET

dc_cx: DB 0   ; centre x
dc_cy: DB 0   ; centre y
dc_x:  DB 0   ; current x offset (0 -> radius)
dc_y:  DB 0   ; current y offset (radius -> 0)
dc_d:  DB 0   ; decision variable

    Save this as draw_circle.asm. It requires set_pixel.asm and calc_pixel_addr.asm.

    The helper dc_plot8 is not a general routine — it is an internal subroutine of draw_circle and should not be called from outside. Because dc_done is a RET, execution never falls into dc_plot8 by accident; it is only reached by the explicit CALL dc_plot8 inside the loop.

    set_pixel destroys every register, so all four values needed per pixel — dc_x, dc_y, dc_cy, and dc_cx — are reloaded from memory before every one of the eight pixel calculations. Four loads per pixel across eight pixels equals thirty-two memory reads per call to dc_plot8. That is the cost of having no free registers to keep any of these values alive across set_pixel calls.

    Limitation: dc_d is a single signed byte. The initial value 1 − radius is stored as 8-bit two's complement, which holds values from −128 to +127. For radius > 129, 1 − radius underflows to a positive value, causing the JP M branch to take the wrong path and producing an incorrect circle. For typical Spectrum screen usage (radius ≤ 95, keeping the circle within the 192-pixel screen height) this limit is never reached.

    Flood Fill

    Flood fill starts from a seed pixel and spreads to all connected unset pixels, setting each one. The simplest version is 4-connected: from each pixel, the fill spreads to the four orthogonal neighbours (up, down, left, right) but not diagonally.

    The natural implementation is recursive: set the current pixel, then recurse to each unset neighbour. On the Z80 each recursive call pushes at least the return address (2 bytes) plus any saved registers — roughly 10 bytes per call. Filling a 30×30 area can push the call stack hundreds of frames deep, consuming several kilobytes. This is safe when filling small enclosed areas such as icon backgrounds or HUD boxes. Do not use recursive flood fill on large open areas.

    ; flood_fill
; 4-connected flood fill from a seed pixel.
; Input:  B = y  (0–191)
;         C = x  (0–255)
; Fills all unset pixels reachable from (x,y) by 4-connectivity.
; Warning: stack depth grows with fill area. Safe for small regions only.
; Destroys: A, B, C, H, L (and uses stack heavily)
flood_fill:
    ; bounds check: stay within 0–255 x, 0–191 y
    LD   A, B
    CP   192
    RET  NC               ; y >= 192: off screen

    ; check if pixel is already set — if so, stop
    PUSH BC
    CALL calc_pixel_addr   ; HL = byte addr, A = bitmask
    LD   B, A              ; save bitmask
    AND  (HL)              ; test pixel
    JR   NZ, ff_already_set

    ; set the pixel
    LD   A, B
    OR   (HL)
    LD   (HL), A

    POP  BC                ; restore y=B, x=C

    ; recurse: up (y-1)
    PUSH BC
    DEC  B
    CALL flood_fill
    POP  BC

    ; recurse: down (y+1)
    PUSH BC
    INC  B
    CALL flood_fill
    POP  BC

    ; recurse: left (x-1)
    PUSH BC
    DEC  C
    CALL flood_fill
    POP  BC

    ; recurse: right (x+1)
    INC  C
    JP   flood_fill        ; tail call — no PUSH/POP needed for last branch

ff_already_set:
    POP  BC
    RET

    Save this as flood_fill.asm. It requires calc_pixel_addr.asm.

    The final recursive call (right neighbour) is a tail call — flood_fill has nothing left to do after it returns. Replacing CALL flood_fill / RET with JP flood_fill eliminates one stack frame for every right-moving step, slightly reducing peak stack depth.

    The y ≥ 192 bounds check at the entry prevents going off the bottom of the screen. There is no x bounds check: x is an 8-bit register, so incrementing past 255 wraps to 0, and decrementing below 0 wraps to 255 — both of which land on valid (if distant) screen pixels. In practice, a correctly drawn enclosing border stops the fill before it reaches the edge.

    Example: Filled Circle

    A filled circle requires two steps: draw the outline with draw_circle to create a closed border, then seed flood_fill at the centre. The flood fill follows the four-neighbour rule and stops at every set pixel — which is exactly the outline just drawn. Keep the radius small: the recursive fill uses approximately 10 bytes of stack per pixel visited, so a radius of 15 gives a 30-pixel-diameter interior of roughly 700 pixels, well within safe limits.

        ORG  $8000

main:
    ; Step 1 — draw the circle outline
    ; Centre (95, 127), radius 15  (interior ~700 pixels, safe stack depth)
    LD   B, 95             ; cy
    LD   C, 127            ; cx
    LD   D, 15             ; radius
    CALL draw_circle

    ; Step 2 — flood-fill from the centre (guaranteed interior pixel)
    LD   B, 95             ; seed y = cy
    LD   C, 127            ; seed x = cx
    CALL flood_fill

    EI
.done:
    HALT
    JR   .done

    INCLUDE "calc_pixel_addr.asm"
    INCLUDE "set_pixel.asm"
    INCLUDE "draw_circle.asm"
    INCLUDE "flood_fill.asm"

    END  $8000

    Assemble with pasmo --tapbas filled_circle.asm filled_circle.tap. You will see a solid white disc. Seeding at the exact centre is reliable because the centre coordinate is always interior for any radius greater than zero. The fill works because draw_circle produces a fully closed border with no gaps — the eight-fold symmetry of the midpoint algorithm guarantees this for all integer radii.

    Key fact: shape routines are wrappers around line routines. A rectangle is four line calls. A filled rectangle is a loop of horizontal line calls. A circle plots 8 pixels per step using the same integer decision-variable technique as Bresenham's line. Each layer of abstraction adds no new Z80 instructions — only new ways to organise calls to the primitives already built.
