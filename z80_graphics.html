Introduction

^ Back to top

This book is about making things appear on the ZX Spectrum screen — pixels, characters, sprites, scrolling backgrounds — using Z80 assembly language. By the time you reach the final chapter you will be able to draw and move sprites with transparency, scroll the screen smoothly, render text from a custom character set, and keep animation flicker-free. Every one of those techniques is built from the same two operations: writing pixel data to the right memory address, and writing colour data to a corresponding address in the attribute file.

The book assumes you are comfortable with Z80 basics: registers, arithmetic instructions, jumps, and subroutine calls. If any of those feel uncertain, the companion introduction book covers them thoroughly. What this book adds is the Spectrum-specific knowledge — how the display hardware works, how its memory layout is organised, and how to exploit both efficiently in real graphics code.

Chapter 1 lays the only foundation the rest of the book needs: how display memory is structured, and how to turn a pixel coordinate into the correct memory address. Everything else follows from that. Read it carefully, work through the examples by hand, and the address formula will feel like second nature within an hour.

1. The Display File & Memory Map

[Back to Contents]

Before you can draw a single pixel, you need to understand the Spectrum's display memory. Unlike a modern framebuffer — where pixel (0,0) lives at the first byte and pixels follow in neat left-to-right, top-to-bottom order — the ZX Spectrum's display memory has a peculiar layout that surprises almost every programmer who meets it for the first time. Understanding it thoroughly is not optional: every graphics routine you will ever write depends on it.

The Spectrum's display occupies two distinct areas of RAM. The first is the display file, which holds the raw pixel data. The second is the attribute file, which controls the colour of each 8×8 pixel block. Together they form the complete display system. Understanding both — and the reasons behind their organisation — makes every subsequent chapter straightforward.

To make that concrete: suppose you want to draw a sprite that is 8 pixels tall and one byte (8 pixels) wide. The natural assumption — the one that works on most platforms — is that the display file is stored row by row: all of pixel row 0, then all of pixel row 1, and so on. Each row is 32 bytes wide (256 pixels ÷ 8 pixels per byte), so to move from one row of the sprite to the next you would add 32 to the address. You write your eight sprite bytes to $4000, $4020, $4040, $4060, $4080, $40A0, $40C0, $40E0 and expect to see a solid block of eight pixel rows stacked on top of each other.

What you actually get: $4000 is pixel row 0, but $4020 is pixel row 8. $4040 is pixel row 16. $4060 is pixel row 24. The eight addresses you chose do not map to eight consecutive rows — they map to rows 0, 8, 16, 24, 32, 40, 48 and 56, one eighth of the way down the screen apart. Your sprite appears as eight isolated single-pixel-tall strips with seven blank rows between each one, spread across most of the screen's height. The data is correct; the addresses are wrong.

This is not a bug in your code's logic, only in your assumption about the memory layout. Understanding the actual layout — which has a clear structure of its own — is all it takes to fix it, and that is what this chapter explains.

Pixel Memory Layout

The ZX Spectrum displays 256 pixels horizontally and 192 pixels vertically. Since each byte holds 8 pixels (one bit per pixel — 1 means ink colour, 0 means paper colour), the full screen requires 256 × 192 ÷ 8 = 6,144 bytes of pixel data. This block of memory is called the display file, and it lives from address $4000 (16384) to $57FF (22527).

If the Spectrum stored pixels in simple row order — all 32 bytes of row 0, then all 32 bytes of row 1, and so on — calculating an address would be trivial: $4000 + (y * 32) + (x / 8). But that is not what happens. The display file is organised to match the way the ULA (the Spectrum's display chip) scans video memory, and that organisation has a logic of its own. Once you see it, the address formula becomes easy to remember and easy to construct in Z80 code.

Three Thirds

The screen is divided vertically into three equal bands of 64 pixel rows each. Each band is called a third. Pixel rows 0–63 belong to the first third, rows 64–127 to the second, and rows 128–191 to the third. Each third occupies exactly 2,048 bytes ($800 hex), so the thirds are neatly separated in memory:

; ┌──────────────────────────────────────────┐  ← $4000  (16384)
; │                                          │
; │         FIRST THIRD   (rows   0–63)      │  2048 bytes
; │                                          │
; ├──────────────────────────────────────────┤  ← $4800  (18432)
; │                                          │
; │         SECOND THIRD  (rows  64–127)     │  2048 bytes
; │                                          │
; ├──────────────────────────────────────────┤  ← $5000  (20480)
; │                                          │
; │         THIRD THIRD   (rows 128–191)     │  2048 bytes
; │                                          │
; └──────────────────────────────────────────┘  ← $5800  (22528)  ← attribute file begins here

To find which third a pixel row belongs to, divide y by 64: third = y / 64. The base address of that third is then $4000 + (third * $800).

Inside a Third

Before going further, three terms need precise definitions.

A pixel row is a single horizontal line of pixels stretching across the full 256-pixel width of the screen, one pixel tall. The y coordinate selects which pixel row you are on. There are 192 of them, numbered 0 at the top to 191 at the bottom.

A character row is a horizontal band of 8 pixel rows stacked vertically, the same height as one text character on screen. The Spectrum's character set uses 8×8 pixel cells, so the screen naturally divides into 24 character rows (192 ÷ 8). Character row 0 contains pixel rows 0–7, character row 1 contains pixel rows 8–15, character row 2 contains pixel rows 16–23, and so on.

A scan line is the position of a pixel row within its character row, numbered 0–7 from the top of the character row. It is a local index, not a global one. Pixel row 19 sits in character row 2 (rows 16–23) at position 3 within that band, so its scan line is 3. The formula is: scan line = y AND 7, character row = y / 8. These are the LLL and RRR fields from the TTRRRLL breakdown introduced later in this chapter.

With those definitions in place: within each third, you might expect the 64 pixel rows to be stored in plain order — pixel row 0 first, then pixel row 1, down to pixel row 63. They are not. Each third contains 8 character rows stacked vertically, and each character row is 8 scan lines tall. The display file does not store them character-row by character-row; it groups by scan line number instead, collecting scan line 0 from every character row before moving on to scan line 1.

The ordering is: first, store scan line 0 of every character row (pixel rows 0, 8, 16, 24, 32, 40, 48, 56); then scan line 1 of every character row (pixel rows 1, 9, 17, 25...); then scan line 2; and so on to scan line 7. The scan line number advances slowly; the character row advances quickly:

;  $4020 ← scan line 0 of char row 1  (pixel row  8)
;  $4040 ← scan line 0 of char row 2  (pixel row 16)
;  $4060 ← scan line 0 of char row 3  (pixel row 24)
;  $4080 ← scan line 0 of char row 4  (pixel row 32)
;  $40A0 ← scan line 0 of char row 5  (pixel row 40)
;  $40C0 ← scan line 0 of char row 6  (pixel row 48)
;  $40E0 ← scan line 0 of char row 7  (pixel row 56)

;  $4100 ← scan line 1 of char row 0  (pixel row  1)

Notice that pixel rows 0, 8, 16, 24, 32, 40, 48 and 56 are stored consecutively at $4000, $4020, $4040... only after all eight character rows have had their first scan line stored does the layout move on to scan line 1 at $4100. This is the opposite of what most programmers expect — but it is how the ULA reads memory, and it is what makes hardware character rendering efficient and inexpensive. When the ULA finishes drawing one scan line across the screen and needs to move to the next, it simply adds $100 to the address. No recalculation is needed: the new address automatically points to the correct scan line of the same set of character rows.

The practical consequence is that if you try to draw a sprite by writing consecutive bytes from the same address onward, the image will look scrambled. You must calculate the correct address for each row separately. That is what the routines in this chapter do.

Decoding y into Three Fields

Any pixel row y in the range 0–191 can be split into three fields by looking at its 8 bits directly. The naming TTRRRLLL is a useful mnemonic — each letter stands for the field it represents: T for Third, R for character Row, L for scan Line:

; y  as 8 bits:   T T R R R L L L
;                 ↑ ↑ ↑ ↑ ↑ ↑ ↑ ↑
;               bit 7   bit 5   bit 2   bit 0
;
;  TT  = bits 7–6  →  which third          (0, 1, or 2)
;  RRR = bits 5–3  →  character row within the third  (0–7)
;  LLL = bits 2–0  →  scan line within the character row  (0–7)

For example, pixel row 73:

; y = 73  →  binary: 0 1 0 0 1 0 0 1
;                    T T R R R L L L
;
;  TT  = 01  →  second third  (base $4800)
;  RRR = 001  →  character row 1  within that third
;  LLL = 001  →  scan line 1  within that character row
;
;  Pixel row 73 = scan line 1 of character row 9  (= 8 + 1)

Working through a few more values makes the pattern obvious. Any y value in the range 0–191 splits cleanly into three non-overlapping fields:

Notice that incrementing y by 1 always increments LLL by 1 — until LLL wraps at 7, at which point RRR increments instead. This is exactly the same as counting in binary with the bits grouped as 2+3+3. The address formula exploits this directly: each field slots into a fixed position in the 16-bit address with no arithmetic needed, only bit manipulation.

The Full Address Formula

Two more terms before the formula.

A 16-bit address on the Z80 is made up of two 8-bit bytes. The high byte holds the upper eight bits (bits 15–8) and the low byte holds the lower eight bits (bits 7–0). When you write LD HL, $4920, H is the high byte ($49) and L is the low byte ($20). The display file address formula builds H and L separately, then combines them.

A column is the horizontal byte position along a pixel row — how far along the x-axis a byte sits, not how far down the screen. Each pixel row is 256 pixels wide and each byte holds 8 pixels, so each row is 32 bytes wide. Those 32 bytes are columns 0–31, increasing from left to right. The column number for a given x coordinate is simply x / 8 — the same division that strips the three low bits identifying the pixel within its byte. Column 0 covers pixels 0–7, column 1 covers pixels 8–15, column 31 covers pixels 248–255.

With those in place: the display file address is assembled by placing the three y fields and the column into specific bit positions in the high and low bytes. Each field plugs directly into a dedicated slot with no multiplication needed:

; 16-bit address:
;
;  High byte:  0  1  0  T1 T0 L2 L1 L0
;  Low  byte: R2 R1 R0 C4 C3 C2 C1 C0
;
;  T1 T0  =  bits 7–6 of y  (which third)
;  L2 L1 L0  =  bits 2–0 of y  (scan line)
;  R2 R1 R0  =  bits 5–3 of y  (character row within third)
;  C4..C0  =  bits 7–3 of x  (column byte = x / 8,  range 0–31)

The 010 at the top of the high byte locks the address into the display file range. The third (TT) occupies the next two bits — each step of TT adds $800 to the address. The scan line (LLL) follows in the high byte's lower three bits — each step adds $100. The character row (RRR) leads the low byte — each step adds $20 (32 bytes, one byte per column). The column (CCCCC) fills the low byte's remaining five bits.

Let's verify with pixel row 73, column 10 (x = 80):

; y = 73 = %01001001   →   TT=01  RRR=001  LLL=001
; x = 80              →   column byte = 80 / 8 = 10  =  %01010  →  C4..C0 = 01010
;
;  High byte: 0 1 0 0 1 0 0 1  =  $49
;  Low  byte: 0 0 1 0 1 0 1 0  =  $2A
;
;  Address = $492A
;
; Cross-check:  second third base $4800
;             + scan line 1  → +$100  =  $4900
;             + char row 1   → +$020  =  $4920
;             + column 10    → +$00A  =  $492A  ✓

Attribute Memory Layout

The attribute file begins immediately after the display file, at address $5800 (22528), and occupies 768 bytes through to $5AFF (23295). There is one attribute byte for every 8×8 block of pixels on screen — 32 columns of blocks across and 24 rows of blocks down = 768 blocks in total, one byte each. Each block is called a character cell; Chapter 2 explains the term and the full attribute byte format in detail.

Unlike the display file, the attribute file is perfectly linear. The attribute bytes are laid out in simple row order: all 32 bytes of character row 0 first, then character row 1, and so on. The address of the attribute byte for the character cell containing pixel (x, y) is:

; attr_address = $5800 + (cy * 32) + cx
;
;   cy = y / 8   (pixel row → character row, 0–23)
;   cx = x / 8   (pixel col → character col, 0–31)
;
; Examples:
;   Top-left cell    cy=0,  cx=0  →  $5800 + 0   + 0   =  $5800
;   Top-right cell   cy=0,  cx=31 →  $5800 + 0   + 31  =  $581F
;   Second row       cy=1,  cx=0  →  $5800 + 32  + 0   =  $5820
;   Bottom-right     cy=23, cx=31 →  $5800 + 736 + 31  =  $5AFF

One attribute byte controls the colour of all 64 pixels in its cell — every pixel in that 8×8 block shares the same ink and paper colour. This 8×8 granularity is the most distinctive constraint of Spectrum graphics programming: you can never colour a single pixel independently; you always colour the entire cell it belongs to. The attribute byte format — ink, paper, BRIGHT and FLASH — is covered in full in Chapter 2. For now, the crucial point is the layout: display file is quirky, attribute file is simple.

Calculating Screen Addresses

Now we turn the address formula into working Z80 code. The two routines below accept a pixel coordinate — y in register B, x in register C — and return either a display file address or an attribute address in HL. These are the building blocks every subsequent chapter depends on, so it is worth reading them carefully and understanding each step.

calc_pixel_addr: Display File Address

The routine returns the address in the HL register pair. H stands for High and L stands for Low. HL is two 8-bit registers used together as a single 16-bit value: H holds the high byte — the upper eight bits, bits 15–8 — and L holds the low byte — the lower eight bits, bits 7–0. When the routine finishes, HL contains the complete 16-bit address. The reason for building H and L separately is that the address formula splits cleanly at the byte boundary: the third (TT) and scan line (LLL) fields belong entirely in H, and the character row (RRR) and column (CCCCC) fields belong entirely in L. No field crosses from one byte to the other.

The routine also uses RRCA — Rotate Right Circular the Accumulator. RRCA shifts every bit in A one position to the right, and the bit that would fall off the right end (bit 0) wraps around to the left end (bit 7) instead of being lost:

; RRCA on %10110000:
;   before:  1 0 1 1 0 0 0 0
;   after:   0 1 0 1 1 0 0 0   ← each bit moved right one place; bit 0 (0) wrapped to bit 7
;
; RRCA on %00000001:
;   before:  0 0 0 0 0 0 0 1
;   after:   1 0 0 0 0 0 0 0   ← bit 0 (1) wrapped to bit 7

This wrapping is why an AND instruction always appears before a sequence of RRCAs in this routine. If we rotated the raw value of y, bits from the low end would wrap into the high end and corrupt the result. AND first zeroes out all bits except the ones we want to move, so the wrapped bit is always 0 and harmless.

The header block below shows the routine's inputs, output, and register side effects. Destroys: B means that B does not hold its original value when the routine returns — it is overwritten as part of the calculation. Any value you needed from B must be saved before calling the routine.

; calc_pixel_addr
; Input:  B = y  (0–191)
;         C = x  (0–255)
; Output: HL = display file address of the byte containing the pixel
;          A = bitmask for that pixel  (bit 7 = leftmost)
; Destroys: B

Stage 1 — Build the high byte

The high byte we need has the bit pattern 010 TT LLL. The fixed 010 at the top three bits ensures the address falls in the range $4000–$5FFF, which is where the display file lives. TT (bits 7–6 of y) sits at bit positions 4–3, contributing $000, $800, or $1000 to the address — selecting which third. LLL (bits 2–0 of y) sits at bit positions 2–0, contributing 0–7 × $100 — selecting which scan line within the character row.

TT starts at bits 7–6 of y and needs to move to bits 4–3 of H: three positions to the right. LLL starts at bits 2–0 of y and needs to stay at bits 2–0 of H: no movement needed. We extract and place each one separately, then OR them together.

calc_pixel_addr:
    ; Extract TT: bits 7–6 of y → rotate right 3 → land at positions 4–3
    LD  A, B             ; A = y
    AND %11000000        ; A = TT000000  (isolate bits 7–6)
    RRCA                 ; A = 0TT00000
    RRCA                 ; A = 00TT0000
    RRCA                 ; A = 000TT000  (TT now in positions 4–3)
    OR  %01000000        ; A = 010TT000  (set bit 6: the fixed $40 base)
    LD  H, A             ; save — H holds 010TT000, LLL still missing

    ; Extract LLL: bits 2–0 of y → already at positions 2–0, slot straight in
    LD  A, B             ; A = y
    AND %00000111        ; A = 00000LLL
    OR  H                ; A = 010TTLLL
    LD  H, A             ; H is complete

Stage 2 — Build the low byte

The low byte has the pattern RRR CCCCC. RRR (bits 5–3 of y) sits at positions 7–5, contributing 0–7 × $20 — selecting which character row. CCCCC (the column, x ÷ 8) sits at positions 4–0, contributing 0–31 — selecting which byte along the row.

RRR starts at bits 5–3 of y and needs to move to bits 7–5 of L: two positions to the left. This uses RLCA — Rotate Left Circular the Accumulator — which works exactly like RRCA but in the opposite direction: every bit shifts one place left, and the bit that would fall off the left end (bit 7) wraps around to the right end (bit 0):

; RLCA on %00111000:  (RRR = 111 — character row 7)
;   before:  0 0 1 1 1 0 0 0
;   after:   0 1 1 1 0 0 0 0   ← each bit moved left one place; bit 7 (0) wrapped to bit 0
;
; RLCA again:
;   before:  0 1 1 1 0 0 0 0
;   after:   1 1 1 0 0 0 0 0   ← RRR now occupies bits 7–5

The AND before the RLCAs serves the same purpose as in Stage 1: it zeroes the bits we do not want, so the wrapped bit is always 0 and harmless. The column calculation uses three RRCAs (rightward shift) with AND cleaning up the bits that wrapped in from the right — exactly as described above for Stage 1.

    ; Extract RRR: bits 5–3 of y → rotate left 2 → land at positions 7–5
    LD  A, B             ; A = y
    AND %00111000        ; A = 00RRR000  (isolate bits 5–3)
    RLCA                 ; A = 0RRR0000
    RLCA                 ; A = RRR00000  (RRR now in positions 7–5)
    LD  L, A             ; L = RRR00000

    ; Extract CCCCC: bits 7–3 of x → rotate right 3 → land at positions 4–0
    ; RRCA rotates, so low bits wrap into the top — AND clears them.
    LD  A, C             ; A = x
    RRCA                 ; }
    RRCA                 ; }  divide x by 8
    RRCA                 ; }
    AND %00011111        ; A = 000CCCCC  (mask off the rotated-in bits)
    OR  L                ; A = RRRCCCCC
    LD  L, A             ; L is complete

Stage 3 — Calculate the bitmask

Each byte in the display file holds 8 pixels, one per bit. To set, clear, or read a single pixel you need to know which bit within its byte represents that pixel. A bitmask is a byte with exactly one bit set — a 1 in the position of the target pixel and 0s everywhere else. You then use that mask with a logical operation to affect only the target pixel while leaving the other seven bits untouched: OR with the mask to set the pixel, AND with the inverted mask to clear it, XOR with the mask to toggle it.

On the Spectrum, bit 7 of a display byte is the leftmost pixel in that byte and bit 0 is the rightmost. A pixel at x coordinate 0 is at bit 7 of column 0; a pixel at x coordinate 7 is at bit 0 of column 0; a pixel at x coordinate 8 is at bit 7 of column 1. The bit position within the byte is always x AND 7 — the three low bits of x. So for x=0 the mask is %10000000, for x=1 it is %01000000, for x=7 it is %00000001, for x=8 it is %10000000 again (new byte, back to bit 7).

The stage calculates that mask: start with %10000000 (bit 7, the leftmost position) and rotate it right x AND 7 times to move the set bit to the correct position.

    LD  A, C             ; A = x
    AND %00000111        ; A = pixel's position within its byte (0–7). Also sets the Zero flag if result is 0.
    LD  B, A             ; B = shift count  (LD never affects flags, so Zero flag is still set from AND)
    LD  A, %10000000     ; A = leftmost pixel mask  (LD never affects flags)
    JR  Z, .mask_done    ; Zero flag still set from AND — if shift count was 0, mask is already correct
.mask_shift:
    RRCA                 ; move mask one position right
    DJNZ .mask_shift     ; Decrement B and Jump if Not Zero — loops B times then falls through
.mask_done:
    RET

calc_attr_addr: Attribute File Address

The attribute address is simpler because the attribute file is stored linearly. We convert the pixel coordinates to character cell coordinates, then compute $5800 + (cy * 32) + cx. Multiplying by 32 is done with five consecutive ADD HL, HL instructions. Each one computes HL = HL + HL = 2 × HL, so five doublings multiply the original value by 2⁵ = 32.

; calc_attr_addr
; Input:  B = y  (0–191)
;         C = x  (0–255)
; Output: HL = attribute byte address
; Destroys: A, DE
calc_attr_addr:
    ; Convert y to character row (cy = y / 8) by shifting right 3
    LD  A, B             ; A = y
    RRCA                 ; }  divide by 8
    RRCA                 ; }
    RRCA                 ; }  A = character row (0–23), with 3 rotated-in bits
    AND %00011111        ; A = cy  (masks away the rotated-in bits)

    ; Multiply character row by 32 to get byte offset of this row
    LD  H, 0
    LD  L, A             ; HL = cy  (0–23)
    ADD HL, HL           ; HL = cy *  2
    ADD HL, HL           ; HL = cy *  4
    ADD HL, HL           ; HL = cy *  8
    ADD HL, HL           ; HL = cy * 16
    ADD HL, HL           ; HL = cy * 32  (byte offset to this character row)

    ; Add the column: cx = x / 8
    LD  A, C             ; A = x
    RRCA                 ; }  divide by 8
    RRCA                 ; }
    RRCA                 ; }
    AND %00011111        ; A = cx  (0–31)
    ADD A, L             ; add column to row offset (safe: L ≤ $E0, cx ≤ $1F, sum ≤ $FF — no 8-bit overflow)
    LD  L, A             ; HL = cy*32 + cx  (offset within attribute area)

    ; Add the attribute file base address
    LD  DE, $5800        ; DE = attribute base
    ADD HL, DE           ; HL = final attribute address
    RET

These two routines are the engine beneath every drawing operation in this book. A sprite-drawing loop calls calc_pixel_addr once for the sprite's top row, then steps to subsequent rows using simple address arithmetic — which turns out to be a short sequence of operations once you understand the layout. That technique is covered in Chapter 6. For now, we have everything needed to write our first complete graphics program.

A Complete Example: Lighting a Single Pixel

When coordinates are fixed and known at assembly time you do not need a subroutine. Apply the address formula by hand, derive the numbers once, and write them directly into the code. To give all four fields of the layout something to do, let's use a non-trivial coordinate: pixel (x=52, y=100), somewhere in the middle of the screen.

Working through the formula by hand:

; y = 100 = %01100100
;            T T R R R L L L
;            0 1 1 0 0 1 0 0
;
;   TT  = 01  →  second third  (base $4800)
;   RRR = 100  →  character row 4  within that third
;   LLL = 100  →  scan line 4  within that character row
;
;  High byte:  0 1 0 0 1 1 0 0  =  $4C
;  Low  byte:  1 0 0 0 0 1 1 0  =  $86
;  Display file address  =  $4C86
;
; Cross-check:  second third base $4800
;             + scan line 4  → +$400  =  $4C00
;             + char row 4   → +$080  =  $4C80
;             + column 6     → +$006  =  $4C86  ✓
;
;  x = 52,  bit offset = 52 AND 7 = 4
;  Bitmask: %10000000 rotated right 4  →  %00001000
;
;  cy = 100 / 8 = 12,  cx = 52 / 8 = 6
;  Attribute address  =  $5800 + (12 × 32) + 6  =  $5800 + $180 + 6  =  $5986

Notice that all four fields are non-zero this time — TT, RRR, LLL and the column all contribute to the final address, so you can verify the formula is doing real work. Here is the complete program:

    ORG $8000

    ; Set pixel at (x=52, y=100)
    ; Display file address = $4C86,  bitmask = %00001000 (bit 3)
    LD  HL, $4C86        ; point at the byte containing our pixel
    LD  A, (HL)          ; read the existing byte — preserves the other 7 pixels in this byte
    OR  %00001000        ; set bit 3 — our pixel
    LD  (HL), A          ; write back

    ; Colour the character cell at (52, 100): bright yellow ink on black paper
    ; Attribute value $46 — format covered in Chapter 2
    LD  HL, $5986        ; attribute byte for this cell
    LD  (HL), $46        ; bright yellow ink on black paper

    RET                  ; return to BASIC

    END $8000

Assemble with Pasmo (or whichever Z80 assembler your toolchain uses) and load into your emulator. The pixel appears at approximately x=52, y=100 — a little over one-sixth across the screen and just past halfway down. You will see a small black square (the 8×8 character cell, whose paper colour is now black) with a single bright yellow dot inside it, against the otherwise white default background.

The OR %00001000 pattern deserves attention. The byte at $4C86 holds eight pixels, not one — bits 7 down to 0 represent the eight pixels in that horizontal run. Writing the mask directly with LD (HL), %00001000 would clear the other seven pixels in the same byte. The correct approach — and the one every graphics routine in this book follows — is to read the existing byte, OR your bit in, then write back. That preserves the neighbours. The counterpart operations are AND with an inverted mask to clear a pixel, and XOR to toggle one; both are covered in Chapter 3.

Reusable Library Files

Rather than copying the routines into every program, save each one as its own .asm file. Pasmo's INCLUDE directive pastes the file in at assembly time, making all its labels available to the rest of your program. Save the following two files alongside your programs.

A Moving Pixel

With the library files in place, the following program moves a single pixel from the left edge of the screen to the right edge and then returns to BASIC. Three instructions appear here that have not been used before:

EI — Enable Interrupts. The Z80 has a flag inside the CPU that controls whether it responds to interrupt signals from external hardware. DI (Disable Interrupts) clears that flag; EI sets it again. When you run a program from BASIC with RANDOMIZE USR, interrupts are normally already enabled, so EI here is a safety measure rather than strictly necessary — but it costs one byte and one cycle, and makes the program reliable regardless of what state the CPU was left in.

HALT suspends execution until the next maskable interrupt. The Spectrum's display chip fires that interrupt 50 times per second, so one HALT is a clean 20 ms pause — enough for the eye to follow the dot as it moves. If interrupts were disabled, HALT would pause forever, which is why EI comes first.

CPL flips every bit in A. After calc_pixel_addr returns the bitmask in A (one bit set, the rest clear), CPL inverts it to give one bit clear and the rest set — exactly the mask needed for AND (HL) to clear a single pixel while leaving its neighbours untouched.

Save the following as moving_pixel.asm in the same folder as the two library files:

    ORG  $8000

main:
    EI                   ; ensure interrupts are on so HALT works
    LD  B, 88            ; y = 88 — just above the middle of the screen
    LD  C, 0             ; x = 0 — left edge

.loop:
    ; — Draw pixel at current position —
    PUSH BC              ; calc_pixel_addr destroys B, so save coordinates
    CALL calc_pixel_addr ; HL = byte address,  A = bitmask
    OR  (HL)             ; set our pixel bit, preserve the other seven
    LD  (HL), A
    POP  BC

    ; — Wait one TV frame so the dot is visible —
    HALT                 ; 50 Hz interrupt — pauses ~20 ms

    ; — Erase pixel at current position —
    PUSH BC
    CALL calc_pixel_addr ; HL = byte address,  A = bitmask
    CPL                  ; invert mask: 0 in our pixel's bit, 1s everywhere else
    AND (HL)             ; clear our pixel bit, preserve the other seven
    LD  (HL), A
    POP  BC

    ; — Move one pixel right and loop —
    INC  C               ; x = x + 1
    JR  NZ, .loop        ; when C wraps from 255 to 0 we have crossed the screen

    RET                  ; back to BASIC

    INCLUDE "calc_pixel_addr.asm"

    END  $8000

Assemble with pasmo --tapbas moving_pixel.asm moving_pixel.tap and load the TAP into your emulator — the BASIC loader runs automatically. A single dot slides smoothly across pixel row 88, crossing all 256 x positions — eight complete character columns — before the program exits. Because calc_pixel_addr recalculates the byte address and bitmask on every iteration, the dot crosses character-cell boundaries correctly without any special-case code: the same pattern (OR (HL) to set, CPL / AND (HL) to clear) works at every x coordinate from 0 to 255.

Key fact: everything visual on the ZX Spectrum ultimately comes down to reading and writing bytes in two memory regions — the display file ($4000–$57FF) for pixel data, and the attribute file ($5800–$5AFF) for colour. No ROM calls are needed to draw anything. The address calculation routines in this chapter are the general form of exactly what the moving pixel example does on every iteration.

2. Colours & Attributes

[Back to Contents]

Chapter 1 used the attribute byte value $46 without explaining what it meant. This chapter explains exactly what is in those 8 bits, how to construct any colour combination, and how to write attribute data efficiently. By the end you will have two new library routines and a complete program that draws a coloured trail across the screen.

The Attribute Byte

The screen divides naturally into a grid of 8×8 pixel blocks — 32 columns wide and 24 rows tall. Each block is called a character cell, or just a cell. The name comes from the fact that one text character occupies exactly one cell. Every cell on screen has exactly one byte in the attribute file, and that byte controls the colour of all 64 pixels in the cell. That byte is the attribute byte for that cell, and its eight bits divide into four fields:

; Bit:   7      6      5   4   3      2   1   0
;        FLASH  BRIGHT P2  P1  P0     I2  I1  I0
;        │      │      └───┬───┘      └───┬───┘
;        │      │        PAPER            INK
;        │      │        (0–7)            (0–7)
;        │      └── BRIGHT: 0 = normal colours,  1 = bright colours
;        └───────── FLASH:  0 = steady,           1 = ink/paper swap at ~1.7 Hz

INK (bits 2–0) is the colour used to draw pixels whose bit in the display file is 1. PAPER (bits 5–3) is the colour used for pixels whose bit is 0 — the background colour of the cell. BRIGHT (bit 6) switches the entire cell to a more vivid palette. FLASH (bit 7) causes the ULA to swap ink and paper automatically at about 1.7 Hz — no code is needed to maintain it once the bit is set.

To make this concrete, here is $46 from Chapter 1 decoded field by field:

; $46 = %01000110
;
;  Bit 7   FLASH  = 0  →  steady (no flashing)
;  Bit 6   BRIGHT = 1  →  bright colours
;  Bits 5–3  PAPER = 000  →  colour 0 (black)
;  Bits 2–0  INK   = 110  →  colour 6 (yellow)
;
;  Result: bright yellow pixels on a black background

One attribute byte controls all 64 pixels in its 8×8 cell — every pixel in that block shares the same ink and paper colour. This is the central constraint of Spectrum graphics programming: you can never colour an individual pixel independently; you colour the entire cell it belongs to. This 8×8 granularity is why Spectrum games tend to align sprites to character-cell boundaries, and why two differently-coloured objects produce a colour clash when they share a cell. The pixel trail at the end of this chapter makes colour clash directly visible.

Ink, Paper, Bright & Flash

Both INK and PAPER are encoded as a 3-bit number in the range 0–7. The eight colours in order are:

ValueColourNormalBright
0BlackBlackBlack — BRIGHT has no effect on colour 0
1BlueDark blueBright blue
2RedDark redBright red
3MagentaDark magentaBright magenta
4GreenDark greenBright green
5CyanDark cyanBright cyan
6YellowDark yellowBright yellow
7WhiteWhiteWhite (slightly more vivid)

BRIGHT switches the entire cell to a more vivid palette — the ULA drives a higher voltage level for the affected cell. Because BRIGHT applies to the whole cell, both ink and paper are brightened together. The exception is colour 0: black with BRIGHT is still black. This gives 15 distinct colours in practice — 7 normal shades, 7 bright shades, and one black that looks the same at both brightness levels.

FLASH is handled entirely by the ULA in hardware. Once bit 7 of an attribute byte is set to 1, the display chip swaps that cell's ink and paper colours at roughly 1.7 Hz. No code runs to maintain the effect. Writing 0 to bit 7 stops the flash immediately on the next display frame.

Building Attribute Bytes

To assemble an attribute byte from its parts, shift each field to its correct bit position and OR the results together. The comments below use the left-shift notation <<: 1 << 6 means "take the value 1 and shift its bits six places to the left", giving %01000000. This is assembler arithmetic evaluated before your program runs — the assembler computes the result and embeds it as a plain byte, so the CPU never performs any shifting. This is different from instructions like RLCA or RRCA, which shift the live contents of A while the program is executing. << only works on constants you know when writing the code; RLCA/RRCA work on values that only exist at runtime.

; attr = (FLASH << 7) | (BRIGHT << 6) | (PAPER << 3) | INK
;
; Example: bright cyan ink on black paper, no flash
;   FLASH=0, BRIGHT=1, PAPER=0 (black), INK=5 (cyan)
;
;   FLASH  shifted left 7: 0 << 7 = %00000000
;   BRIGHT shifted left 6: 1 << 6 = %01000000
;   PAPER  shifted left 3: 0 << 3 = %00000000
;   INK                  :     5 = %00000101
;                         OR'd  = %01000101  =  $45

Alternatively, work the arithmetic out in your notes and write the final hex value directly — either way the result is the same: a constant byte baked into the program. The common pattern in game code is to give each such value a memorable name using the EQU directive. EQU (short for EQUate) tells the assembler to substitute the given value wherever the name appears. Unlike DB or ORG, it does not place any bytes in memory — it is purely a compile-time name for a number:

; Useful attribute constants
ATTR_CYAN_BRT  EQU  $45   ; bright cyan ink, black paper
ATTR_YEL_BRT   EQU  $46   ; bright yellow ink, black paper
ATTR_WHT_BRT   EQU  $47   ; bright white ink, black paper
ATTR_DEFAULT   EQU  $38   ; black ink, white paper — BASIC default

Writing Attributes

Writing an attribute byte is a one-instruction operation once you have the address: LD (HL), A. The interesting work is finding the right address and doing it efficiently for ranges of cells. This section builds three tools — a single-cell write routine, a row fill, and a full-screen fill — then puts them to work in a complete program.

Writing a Single Cell — set_attr

calc_attr_addr from Chapter 1 handles the address calculation. set_attr wraps it with the write, giving a one-call interface. Because calc_attr_addr destroys A, the attribute value must be saved across the call.

The Z80 has no instruction to push A alone — the only way to stack the accumulator is PUSH AF, which saves A and the Flags register together as a 16-bit pair. The flags are not needed here; they come along because that is how the hardware works. POP AF restores both: A gets back the attribute value, and the flags are restored to whatever state they were in before the call, which is a harmless side effect.

; set_attr
; Input:  B = y  (0–191)
;         C = x  (0–255)
;         A = attribute byte to write
; Output: none
; Destroys: HL, DE
set_attr:
    PUSH AF              ; PUSH AF saves A and Flags together — the only way to stack A
    CALL calc_attr_addr  ; HL = attribute file address  (overwrites A and DE)
    POP  AF              ; restore A (attribute byte) and Flags
    LD  (HL), A          ; write it
    RET

Save this as set_attr.asm. Any program that includes both calc_attr_addr.asm and set_attr.asm can colour any cell with a single CALL set_attr.

Writing a Row of Cells

The attribute file is linear, so the 32 bytes of one character row are at consecutive addresses. To colour a full row, find the first cell with calc_attr_addr (passing x=0), then step through the remaining 31 cells with INC HL:

; Colour one full character row
; Input:  B = any y coordinate in the target row  (0–191)
;         A = attribute byte
    PUSH AF              ; save attribute
    LD  C, 0             ; x = 0 — leftmost column
    CALL calc_attr_addr  ; HL = first attribute byte in this row
    POP  AF              ; restore attribute
    LD  B, 32            ; 32 cells per row
.row_loop:
    LD  (HL), A          ; write attribute
    INC HL               ; next cell — safe because attribute file is linear
    DJNZ .row_loop

This is an inline fragment, not a standalone routine — embed it directly in your code where you need a row fill, or wrap it in a labelled subroutine with a RET if you need to call it from multiple places. It works because attribute bytes for adjacent cells are adjacent in memory. The same trick does not work in the display file, where consecutive pixel rows are not consecutive in memory — which is exactly why the address calculation routines from Chapter 1 are necessary.

Filling the Whole Screen

The entire attribute file is 768 bytes ($5800 to $5AFF) stored linearly. A full-screen fill writes the same value to all 768 addresses. Three passes of 256 bytes each — using DJNZ's property that starting at B=0 gives 256 iterations — keeps the loop body as tight as possible:

; fill_screen_attr
; Fill all 768 attribute bytes with a single value
; Input:  A = attribute byte to fill with
; Output: none
; Destroys: BC, HL
fill_screen_attr:
    LD  HL, $5800        ; start of attribute file
    LD  B, 3             ; 3 outer passes of 256 bytes = 768 bytes total
.outer:
    PUSH BC
    LD  B, 0             ; B=0 → DJNZ loops 256 times (decrements to 255 on first pass)
.inner:
    LD  (HL), A          ; write attribute — DJNZ does not touch A
    INC HL
    DJNZ .inner
    POP  BC
    DJNZ .outer          ; 3 × 256 = 768
    RET

A Coloured Pixel Trail

This program extends the moving pixel from Chapter 1. The pixel no longer erases itself — it leaves every dot set as it advances, drawing a solid line of pixels across row 88. At each column boundary (every 8 pixels) the program pauses one frame, then writes a new attribute byte with the next ink colour in a 7-step cycle. Because the attribute colours the full 8×8 character cell, the visible result is a horizontal band one character cell tall (8 pixels) running the full width of the screen, divided into 32 coloured segments that snap into place one at a time from left to right.

The ink cycle skips colour 0 (black on black paper is invisible). The wrapping logic increments the current ink value, masks it to 0–7 with AND, then nudges it to 1 if it landed on 0, producing the sequence 1, 2, 3, 4, 5, 6, 7, 1, 2, …

Save the following as pixel_trail.asm alongside calc_pixel_addr.asm and calc_attr_addr.asm:

    ORG  $8000

main:
    EI                    ; ensure interrupts are on for HALT
    LD   B, 88           ; y = 88 — just above the middle of the screen
    LD   C, 0            ; x = 0 — left edge

.loop:
    ; At each column boundary: pause and colour the new cell
    LD   A, C
    AND  %00000111        ; x mod 8: is this the first pixel of a new cell?
    JR   NZ, .draw_pixel  ; no — just draw and continue

    HALT                  ; yes — pause ~20 ms so each coloured band is visible

    ; Advance ink colour through 1–7, skipping 0 (black on black = invisible)
    LD   A, (ink_colour)
    INC  A
    AND  %00000111        ; wrap: 8 → 0
    JR   NZ, .store_ink
    INC  A                ; nudge: 0 → 1, skipping black
.store_ink:
    LD   (ink_colour), A
    OR   %01000000        ; set BRIGHT bit — A = BRIGHT=1, PAPER=0, INK=colour
    PUSH BC
    PUSH AF               ; save A (attribute) and Flags — PUSH AF is the only way to stack A
    CALL calc_attr_addr   ; HL = attribute address for this cell  (overwrites A and DE)
    POP  AF               ; restore A (attribute) and Flags
    LD   (HL), A          ; colour the cell
    POP  BC

.draw_pixel:
    PUSH BC
    CALL calc_pixel_addr  ; HL = byte address,  A = bitmask
    OR   (HL)             ; set pixel bit, preserve neighbours
    LD   (HL), A
    POP  BC

    INC  C                ; x = x + 1
    JR   NZ, .loop        ; stop when x wraps 255 → 0

    RET                   ; back to BASIC

ink_colour: DB 0         ; current ink index (0 = uninitialised; first use advances to 1)

    INCLUDE "calc_pixel_addr.asm"
    INCLUDE "calc_attr_addr.asm"

    END  $8000

Assemble with pasmo --tapbas pixel_trail.asm pixel_trail.tap and load the TAP into your emulator — the BASIC loader runs automatically. A coloured band builds across the screen from left to right — blue, red, magenta, green, cyan, yellow, white, cycling — each cell snapping in with a 20 ms pause. The finished result is a single stripe one character cell tall spanning the full width of the screen.

Two things are worth watching closely. First, colour clash: when a new cell's attribute byte is written, every pixel already set in that cell is immediately repainted in the new ink colour. The rightmost drawn pixel changes colour as each new cell opens, not after the cell is complete. This is the attribute system working exactly as designed — ink and paper are cell properties, not pixel properties.

Second, notice that calc_attr_addr is called only 32 times (once per column boundary) while calc_pixel_addr is called 256 times (once per pixel). The attribute address calculation is the more expensive operation, but by calling it only when the cell changes the program avoids unnecessary work. This pattern — detect a boundary, then handle it — appears throughout game graphics code.

Key fact: the attribute system separates colour from pixels entirely. Writing to the display file never affects colour; writing to the attribute file never affects which pixels are set. The two are independent, which makes it possible to repaint the screen's colours without touching a single pixel, and to move pixel data without changing any colours.

3. Drawing Pixels

[Back to Contents]

Chapters 1 and 2 used pixel operations informally — OR (HL) to set a pixel, CPL / AND (HL) to clear one, with the explanation that XOR toggles. This chapter puts all three on a firm footing, explains exactly why each logical operation is the right tool, and wraps each one in a clean library routine. By the end you will have three new .asm files and a bouncing pixel that uses all of them in a proper animation loop.

Setting a Single Pixel

Setting a pixel means forcing one specific bit in a display file byte to 1 while leaving the other seven bits exactly as they are. The right tool is OR.

OR combines two bits according to one rule: the result is 1 if either input is 1, and 0 only if both inputs are 0. Applied to a full byte, each bit pair is processed independently:

Existing bitMask bitResultEffect
000Unaffected — mask bit is 0, existing 0 stays 0
011Pixel set — mask bit forces result to 1
101Unaffected — mask bit is 0, existing 1 stays 1
111Pixel set (was already set)

The bitmask from calc_pixel_addr has exactly one 1 — the target pixel's bit — and seven 0s everywhere else. OR with a 0 leaves any existing bit unchanged; OR with a 1 forces the result to 1. The seven bits that are 0 in the mask therefore pass through untouched, and only the target bit is set. This is why the read-modify-write sequence is necessary: the read preserves those seven neighbours, OR sets the one target bit, and the write puts the whole byte back.

; set_pixel
; Input:  B = y  (0–191)
;         C = x  (0–255)
; Output: none
; Destroys: A, B, HL
set_pixel:
    CALL calc_pixel_addr  ; HL = byte address,  A = bitmask
    OR   (HL)             ; set target bit, preserve the other seven
    LD   (HL), A          ; write back
    RET

Save this as set_pixel.asm. Note that calc_pixel_addr must also be included in any program that uses set_pixel, since set_pixel calls it. The routine destroys B because calc_pixel_addr uses B internally as a shift counter.

Clearing a Single Pixel

Clearing a pixel means forcing one specific bit to 0 while leaving the other seven unchanged. OR cannot do this — OR can only set bits, never clear them. The right tool is AND, but with an inverted mask.

AND produces a 1 only when both inputs are 1; if either input is 0 the result is 0:

Existing bitInverted mask bitResultEffect
010Unaffected — existing 0 stays 0
000Pixel cleared (was already 0)
111Unaffected — existing 1 stays 1
100Pixel cleared — inverted mask bit forces result to 0

The inverted mask has exactly one 0 — at the target pixel's bit position — and seven 1s everywhere else. AND with a 1 passes the existing bit through unchanged; AND with a 0 forces the result to 0. So only the target bit is cleared, and the seven neighbours are untouched.

calc_pixel_addr returns the normal mask in A (one 1, seven 0s). CPL inverts every bit in A, producing the inverted mask (one 0, seven 1s) needed for the AND:

; clear_pixel
; Input:  B = y  (0–191)
;         C = x  (0–255)
; Output: none
; Destroys: A, B, HL
clear_pixel:
    CALL calc_pixel_addr  ; HL = byte address,  A = bitmask  (one 1, seven 0s)
    CPL                   ; invert A  →  inverted mask  (one 0, seven 1s)
    AND  (HL)             ; clear target bit, preserve the other seven
    LD   (HL), A          ; write back
    RET

Save this as clear_pixel.asm.

Toggling a Pixel

Toggling a pixel means flipping one bit — 0 becomes 1, 1 becomes 0 — without needing to know which state it is currently in. Neither OR nor AND can do this cleanly. The right tool is XOR.

XOR (eXclusive OR) produces a 1 when the two inputs are different, and a 0 when they are the same:

Existing bitMask bitResultEffect
000Unaffected — XOR with 0 never changes a bit
011Flipped: 0 → 1
101Unaffected
110Flipped: 1 → 0

XOR with a 0 leaves the existing bit unchanged. XOR with a 1 flips the existing bit, regardless of what it was. Because the mask has exactly one 1, exactly one bit is flipped and the rest are left alone. Call toggle_pixel twice on the same coordinate and the pixel returns to its original state — which makes XOR ideal for animation: you do not need to track whether the pixel is currently on or off, because the toggle works correctly either way.

; toggle_pixel
; Input:  B = y  (0–191)
;         C = x  (0–255)
; Output: none
; Destroys: A, B, HL
toggle_pixel:
    CALL calc_pixel_addr  ; HL = byte address,  A = bitmask
    XOR  (HL)             ; flip target bit, leave the other seven unchanged
    LD   (HL), A          ; write back
    RET

Save this as toggle_pixel.asm.

The three operations together cover every pixel state transition possible:

ClearCPL then AND (HL)You want the pixel off, regardless of current state

A Bouncing Pixel

This program uses set_pixel and clear_pixel together to animate a pixel bouncing left and right across pixel row 88. It introduces three new ideas.

A direction variable stored in memory. The pixel's x coordinate is kept in a memory byte rather than a register, because the animation loop must preserve it across many HALTs and subroutine calls. The direction is stored as a signed byte: 1 means moving right, $FF means moving left. On the Z80, $FF is the two's complement representation of −1 — adding $FF to an 8-bit value is identical to subtracting 1. The direction byte is added to x each frame to advance the pixel; negating it reverses direction.

CP — ComPare. CP n subtracts n from A and sets the flags exactly as SUB would, but throws away the result — A is unchanged. This lets you test a value and branch on the outcome without overwriting A. After CP 0, the Zero flag is set if A was 0; after CP 255, the Zero flag is set if A was 255. Combined with JR Z, this detects when the pixel hits either edge.

NEG — Negate. NEG computes A = 0 − A, which is the two's complement negation of A. Applied to 1 it produces $FF (−1); applied to $FF it produces 1. This flips the direction between +1 and −1 with a single instruction, with no need for a branch or a comparison.

The animation loop follows the pattern every game uses: clear old position → update state → draw new position → wait for next frame:

    ORG  $8000

main:
    EI
    LD   B, 88            ; y = 88 — fixed for the whole program
    LD   A, 0
    LD   (px), A          ; starting x = 0
    LD   A, 1
    LD   (dir), A         ; starting direction = +1 (moving right)

.loop:
    HALT                  ; sync to frame start — clear+draw finish before the beam reaches row 88

    ; — Clear pixel at current position —
    LD   A, (px)
    LD   C, A             ; C = current x
    PUSH BC
    CALL clear_pixel      ; erase the dot  (destroys A, B, HL)
    POP  BC               ; restore B = y = 88,  C = current x

    ; — Advance x by direction —
    LD   A, (dir)
    ADD  A, C             ; x = x + direction
    LD   (px), A          ; save new x

    ; — Reverse direction at edges —
    CP   255              ; did x reach the right edge?
    JR   Z, .reverse
    CP   0               ; did x reach the left edge?
    JR   NZ, .draw        ; neither edge — keep going
.reverse:
    LD   A, (dir)
    NEG                   ; negate direction: 1 → $FF ($FF = −1),  $FF → 1
    LD   (dir), A

.draw:
    ; — Draw pixel at new position —
    LD   A, (px)
    LD   C, A             ; C = new x
    PUSH BC
    CALL set_pixel        ; draw the dot  (destroys A, B, HL)
    POP  BC               ; restore B = y = 88

    JR   .loop            ; repeat forever

px:  DB  0               ; current x position
dir: DB  1               ; direction: 1 = right,  $FF = left

    INCLUDE "calc_pixel_addr.asm"
    INCLUDE "set_pixel.asm"
    INCLUDE "clear_pixel.asm"

    END  $8000

Assemble with pasmo --tapbas bounce.asm bounce.tap and load the TAP into your emulator — the BASIC loader runs automatically. The pixel travels right across the screen, bounces off the right edge, travels left, bounces off the left edge, and repeats indefinitely. On real Spectrum hardware the motion is perfectly smooth. On an emulator running on a modern computer you may see occasional stuttering — the Spectrum outputs frames at 50 Hz but most monitors refresh at 60 Hz, so roughly one in every six Spectrum frames is held on screen for two monitor refresh cycles instead of one. This is a display hardware mismatch rather than a code problem; the Z80 is producing frames at a perfectly constant rate.

Notice that HALT is at the top of the loop, not the bottom. This matters for two reasons — speed consistency and flicker.

Speed. The interrupt fires at exactly 50 Hz. Every iteration starts by waiting for the interrupt, then does all its work — clear, advance, draw — in the ~19.85 ms gap before the next one arrives. Because those operations together take only a few hundred microseconds, the next HALT is always reached long before the following interrupt fires, giving a consistent 20 ms wait every time and moving the pixel at a rock-steady 50 pixels per second. Placing HALT at the bottom of the loop instead would break this: if the interrupt happened to fire just before HALT was reached, HALT would return almost immediately and the pixel would advance again after only a few microseconds, producing alternating very-short and very-long frames — the pixel darts then pauses, darts then pauses. HALT at the top is the fix.

Flicker. The Spectrum's TV beam scans from the top of the screen downward. The interrupt fires when the beam reaches the bottom — the start of the vertical blanking period — so returning from HALT means the beam is about to start a fresh pass from the top. Row 88 is roughly halfway down, which means the clear and draw both complete approximately 9 ms before the beam reaches that row. With HALT at the bottom, clear and draw happen at an unpredictable point mid-frame; if the beam happened to be scanning row 88 between those two calls the pixel would visibly flicker.

Notice also that B is saved with PUSH BC and restored with POP BC around each CALL. Both set_pixel and clear_pixel call calc_pixel_addr, which destroys B. The y coordinate must survive those calls because it is used again in the next iteration, so it is held in B between frames and pushed to the stack for the duration of each call.

Key fact: OR sets, AND-with-inverted-mask clears, XOR toggles. Every pixel operation in this book is one of these three patterns applied to the byte that calc_pixel_addr identifies. The choice between them depends entirely on what you want to happen to a bit that is already in the state you are trying to produce — OR leaves it set, AND leaves it clear, XOR flips it.

4. Drawing Lines

[Back to Contents]

Horizontal and vertical lines are the building blocks of almost every game screen — borders, platforms, maze walls, health bars, HUD frames. A line is nothing more than a sequence of pixels, but drawing it efficiently matters: a naive approach that calls set_pixel for every pixel is eight times slower than it needs to be. This chapter builds three library routines — draw_hline, draw_vline, and draw_line — and closes with a screen border example that uses the two axis-aligned routines.

Horizontal Lines

A horizontal line shares one y coordinate across all its pixels. On the Spectrum, eight consecutive pixels on the same row are packed into a single byte of the display file. Writing $FF to that byte sets all eight at once — eight times faster than calling set_pixel eight times. The routine below exploits this wherever it can.

The Three-Region Model

A horizontal line from x1 to x2 on row y spans up to three regions in the display file:

RegionDescriptionHow to draw
Left partial bytex1 to the end of its byte (if x1 is not byte-aligned)OR a mask — preserve pixels to the left of x1
Middle full bytesAll complete bytes between the two partial endsLD (HL), $FF — overwrite all eight pixels
Right partial byteStart of the last byte to x2 (if x2 is not byte-aligned)OR a mask — preserve pixels to the right of x2

When x1 and x2 fall inside the same byte there is only one region: a single OR combining both the left and right masks.

Advancing along a row is just INC L — not INC HL. All bytes on the same pixel row share the same H byte; only the low byte changes as the column advances from 0 to 31. Because a row spans at most 32 bytes, L never overflows into H, so INC L is safe and one byte shorter than INC HL.

Edge Masks

The left-edge mask covers bit positions from x1's pixel down to bit 0 of the byte. The right-edge mask covers bit positions from bit 7 down to x2's pixel. Both depend only on the low three bits of x — that is, x & 7, the pixel's position within its byte. There are only eight possible values for each, so a lookup table is the natural first idea:

(x1 to bit 0)		Right mask

To read from such a table you load its base address into HL, add the index (x & 7) to L, then read through HL. That approach works, but it consumes HL — which draw_hline needs to hold the current screen address throughout the routine. Saving and restoring HL around every table lookup adds PUSH/POP pairs that erode the speed advantage the table was supposed to provide.

For at most seven shift operations it is simpler and no slower to compute the mask directly at runtime using SRL and SLA.

draw_hline

SRL (Shift Right Logical) shifts A one bit right, filling bit 7 with 0. Repeating it n times produces $FF >> n — exactly the left-edge mask. SLA (Shift Left Arithmetic) shifts A one bit left, filling bit 0 with 0. Repeating it n times produces $FF << n — the right-edge mask. Both are CB-prefixed instructions, two bytes each, and both are valid on every Z80. The shift count is at most 7, so the loop runs at most seven iterations — fast enough that no table is needed.

The middle-byte count requires the byte column of x1 and x2 — that is, x divided by 8 (x >> 3). The Z80 has no right-shift instruction that operates on A directly in fewer than two bytes per shift, but RRCA (Rotate Right Circular A) is a single byte and very fast. After three RRCAs the original bits 7–3 have rotated into positions 4–0. AND %00011111 then masks away the three bits that wrapped around from the bottom, leaving exactly x >> 3 in the low five bits.

; draw_hline
; Draw a horizontal line on pixel row y from x1 to x2.
; Input:  B = y   (0–191)
;         C = x1  (0–255, left end)
;         D = x2  (0–255, right end, must be >= x1)
; Output: none
; Destroys: A, B, C, D, E, H, L
; Note: calc_pixel_addr preserves C and D, so x1 and x2 survive the CALL.
draw_hline:
    CALL calc_pixel_addr   ; HL = byte address of x1  (C=x1 and D=x2 are preserved)

    ; — Same-byte check: XOR high bits of x1 and x2 —
    LD   A, D
    XOR  C
    AND  %11111000         ; non-zero if x1 and x2 are in different bytes
    JR   Z, .same_byte

    ; — Left partial byte: mask = $FF >> (x1 & 7) —
    LD   A, C
    AND  %00000111         ; shift count = x1 mod 8
    LD   B, A
    LD   A, $FF
    JR   Z, .lm_done       ; count=0: x1 is at leftmost bit, mask stays $FF
.lm_loop:
    SRL  A                 ; shift right, 0 fills from top — one step of $FF >> n
    DJNZ .lm_loop
.lm_done:
    OR   (HL)              ; set pixels from x1 down to end of byte, preserve left neighbours
    LD   (HL), A
    INC  L                 ; next byte (same row — INC L safe, not INC HL)

    ; — Middle full bytes: count = (x2>>3) - (x1>>3) - 1 —
    ; Extract byte column via three RRCA then AND %00011111
    LD   A, D
    RRCA
    RRCA
    RRCA
    AND  %00011111         ; x2 byte column (0–31)
    LD   E, A
    LD   A, C
    RRCA
    RRCA
    RRCA
    AND  %00011111         ; x1 byte column (0–31)
    LD   B, A
    LD   A, E
    SUB  B                 ; x2col - x1col
    DEC  A                 ; - 1 = number of middle bytes
    JR   Z, .right_byte    ; zero: x1 and x2 are adjacent bytes, no middle
    JR   C, .right_byte    ; carry guard (should not occur)
    LD   B, A
.middle:
    LD   (HL), $FF         ; all 8 pixels set
    INC  L
    DJNZ .middle

.right_byte:
    ; — Right partial byte: mask = $FF << (7 - x2 & 7) —
    LD   A, D
    AND  %00000111         ; x2 mod 8
    LD   B, A
    LD   A, 7
    SUB  B                 ; shift count = 7 - (x2 mod 8)
    LD   B, A
    LD   A, $FF
    JR   Z, .rm_done       ; count=0: x2 is at rightmost bit, mask stays $FF
.rm_loop:
    SLA  A                 ; shift left, 0 fills from bottom — one step of $FF << n
    DJNZ .rm_loop
.rm_done:
    OR   (HL)              ; set pixels from start of byte down to x2, preserve right neighbours
    LD   (HL), A
    RET

.same_byte:
    ; — Both x1 and x2 in the same byte: AND the left and right masks —
    LD   A, C
    AND  %00000111
    LD   B, A
    LD   A, $FF
    JR   Z, .sb_lm_done
.sb_lm_loop:
    SRL  A
    DJNZ .sb_lm_loop
.sb_lm_done:
    LD   E, A              ; E = left mask

    LD   A, D
    AND  %00000111
    LD   B, A
    LD   A, 7
    SUB  B
    LD   B, A
    LD   A, $FF
    JR   Z, .sb_rm_done
.sb_rm_loop:
    SLA  A
    DJNZ .sb_rm_loop
.sb_rm_done:
    AND  E                 ; intersection: only the pixels strictly between x1 and x2
    OR   (HL)
    LD   (HL), A
    RET

Vertical Lines

A vertical line shares one x coordinate across all its pixels. Consecutive pixels on the same column are in completely different bytes — different rows have different TTRRRLLL addresses — so writing eight pixels at once is not possible. Every pixel on a vertical line needs its own display file byte access.

There is no single magic constant that steps one pixel row in all cases. The address formula from Chapter 1 shows why:

; Address = $4000 + (T × $800) + (L × $100) + (R × $20) + C
; (T = third, bits 7:6 of y;  L = scan line, bits 2:0 of y;  R = char row, bits 5:3 of y)
;
; L (scan line) lives in H bits 2:0 — one step = INC H  (+$0100)
; R (char row)  lives in L bits 7:5 — one step = ADD $20 to L  (+$0020)
;
; Moving from scan line L to L+1 increases the address by $0100 (= INC H).
; That works cleanly while L < 7.
; When L = 7, INC H would carry into H bit 3 (part of the T field) — wrong.
; Instead: AND H with $F8 to reset L=0, then ADD $20 to the low byte to step R.
; If R then wraps from 7 to 0, add $08 to H to step T.
;
; Example: y=7  → H=$47, L=C      (T=0, R=0, L=7)
;          y=8  → H=$40, L=$20+C  (T=0, R=1, L=0  — character row stepped)
;          y=63 → H=$47, L=$E0+C  (T=0, R=7, L=7  — end of first third)
;          y=64 → H=$48, L=C      (T=1, R=0, L=0  — third stepped)

The scan line (L) field is in H bits 2:0, so advancing one pixel row is normally a single INC H. The special case at L = 7 needs explicit handling: carry from H bits 2:0 into bit 3 would corrupt the T field, so the code clears the LLL bits with AND $F8 and advances R separately.

draw_vline

; draw_vline
; Draw a vertical line on pixel column x from y1 to y2.
; Input:  B = y1  (0–191, top)
;         C = x   (0–255)
;         D = y2  (0–191, bottom, must be >= y1)
; Output: none
; Destroys: A, B, C, D, E, H, L
draw_vline:
    PUSH BC                ; save y1 (B) — calc_pixel_addr destroys B
    CALL calc_pixel_addr   ; HL = byte address,  A = bitmask for column x
    LD   E, A              ; save bitmask in E before POP overwrites A
    POP  BC                ; restore B = y1  (C = x, no longer needed)

    LD   A, D              ; y2
    SUB  B                 ; y2 - y1  (B = y1 restored by POP)
    INC  A                 ; pixel count = y2 - y1 + 1
    LD   B, A              ; B = DJNZ counter

    LD   C, E              ; bitmask into C
dv_loop:
    LD   A, C              ; bitmask
    OR   (HL)              ; set pixel, preserve neighbours
    LD   (HL), A
    ; advance HL to the next pixel row
    LD   A, H
    AND  $07               ; isolate scan line field (LLL, H bits 2:0)
    CP   $07               ; at scan line 7?
    JR   Z, dv_cross       ; yes: step the character row explicitly
    INC  H                 ; no: simple scan line increment
    DJNZ dv_loop
    RET
dv_cross:
    ; Scan line 7 → 0: reset LLL, step RRR in L
    LD   A, H
    AND  $F8               ; clear H bits 2:0 (LLL = 0), T field in bits 4:3 preserved
    LD   H, A
    LD   A, L
    ADD  A, $20            ; step RRR (character row field, L bits 7:5)
    LD   L, A
    JR   NC, dv_next       ; no carry: still in same third
    LD   A, H
    ADD  A, $08            ; RRR overflowed: step TT (third field, H bits 4:3)
    LD   H, A
dv_next:
    DJNZ dv_loop
    RET

Save this as draw_vline.asm. Any program using it must also INCLUDE "calc_pixel_addr.asm".

Two register discipline points worth noting. First, calc_pixel_addr destroys B (it uses B as an internal shift counter), so y1 must be saved on the stack before the call and restored with POP BC afterwards. Second, the bitmask is moved from E to C before the loop so that A is free for the row-advance calculations inside dv_cross without disturbing the bitmask or the DJNZ counter in B.

Bresenham's Line Algorithm

Horizontal and vertical lines cover most game needs, but arbitrary diagonal lines require a general solution. Bresenham's line algorithm draws the closest integer approximation to any straight line using only addition and subtraction — no multiplication, no division, no floating-point arithmetic, making it well-suited to the Z80.

The Idea

Imagine walking from (x1, y1) to (x2, y2) one step at a time along the longer axis (the major axis). At each step you advance one pixel along the major axis. Occasionally you also step one pixel along the shorter axis (the minor axis) to track the true line's slope. The question is: when do you take the minor step?

Bresenham's answer: keep an integer error variable that accumulates the difference between where the true line is and where the drawn line is. Each major step adds a fixed amount to the error. When the error exceeds the half-way threshold, take a minor step and subtract the threshold from the error. The result is a line that stays within half a pixel of the true line at every point.

The algorithm handles all directions by tracking the sign of dx and dy separately:

; Bresenham variables
;   dx = |x2 - x1|,  sx = +1 if x2 > x1 else -1 ($FF)
;   dy = |y2 - y1|,  sy = +1 if y2 > y1 else -1 ($FF)
;   err = dx - dy
;
; Each iteration:
;   set pixel at (x, y)
;   if x==x2 and y==y2: done
;   e2 = 2 * err
;   if e2 > -dy: err -= dy;  x += sx
;   if e2 <  dx: err += dx;  y += sy

On the Z80, 2 * err is just ADD A, A (left shift by one). The comparisons use signed arithmetic — JP M (jump if minus, i.e. if the sign flag is set) rather than the unsigned JR C.

draw_line

The Z80 has no instruction to add or subtract a memory-addressed value directly to A except via (HL). Instructions like ADD A, (addr) and SUB (addr) are not valid. Every memory operand must be loaded into a register first: LD B, A to save A, then LD A, (addr), then ADD A, B. Bresenham requires several such operations, which is why the routine stores all working state in named memory variables and loads them explicitly as needed.

A second point: the error variable is a 16-bit value held in HL and stored in the two-byte dl_err. An 8-bit error is not enough: the intermediate values 2*err + dy and 2*err - dx can exceed the signed-byte range of −128 to +127 for quite modest lines (dx = 40, dy = 63 is enough), and a wrapped comparison makes the routine skip a step forever and hang. With 16-bit arithmetic every line that fits on the screen is handled correctly.

; draw_line
; Draw a line from (x1,y1) to (x2,y2) using Bresenham's algorithm.
; Input:  B = y1  (0–191)    C = x1  (0–255)
;         D = y2  (0–191)    E = x2  (0–255)
; The error term is 16-bit, so any line on the screen is handled.
; Output: none    Destroys: A, B, C, D, E, H, L
draw_line:
    LD   A, C
    LD   (dl_x),  A         ; x = x1
    LD   A, B
    LD   (dl_y),  A         ; y = y1
    LD   A, E
    LD   (dl_x2), A         ; target x2
    LD   A, D
    LD   (dl_y2), A         ; target y2

    ; dx = |x2-x1|,  sx = +1 or $FF (-1)
    ; Compare with CP so the full 0–255 range is handled without sign issues.
    LD   A, E
    SUB  C                  ; A = x2 - x1, carry set if x2 < x1
    JR   NC, .dx_pos
    NEG                     ; make positive for dx
    LD   (dl_dx), A
    LD   A, $FF
    LD   (dl_sx), A         ; sx = $FF (-1): moving left
    JR   .dy_calc
.dx_pos:
    LD   (dl_dx), A
    LD   A, 1
    LD   (dl_sx), A         ; sx = 1: moving right

.dy_calc:
    ; dy = |y2-y1|,  sy = +1 or $FF (-1)
    LD   A, D
    SUB  B                  ; A = y2 - y1, carry set if y2 < y1
    JR   NC, .dy_pos
    NEG
    LD   (dl_dy), A
    LD   A, $FF
    LD   (dl_sy), A         ; sy = $FF (-1): moving up
    JR   .err_calc
.dy_pos:
    LD   (dl_dy), A
    LD   A, 1
    LD   (dl_sy), A         ; sy = 1: moving down

.err_calc:
    ; err = dx - dy  (16-bit)
    LD   A, (dl_dx)
    LD   L, A
    LD   H, 0
    LD   A, (dl_dy)
    LD   E, A
    LD   D, 0
    OR   A                  ; clear carry for SBC
    SBC  HL, DE
    LD   (dl_err), HL

dl_loop:
    ; — Draw pixel at (x, y) —
    LD   A, (dl_y)
    LD   B, A
    LD   A, (dl_x)
    LD   C, A
    CALL set_pixel

    ; — Check if done: x==x2 and y==y2 —
    LD   A, (dl_x2)
    LD   B, A
    LD   A, (dl_x)
    CP   B
    JR   NZ, dl_not_done
    LD   A, (dl_y2)
    LD   B, A
    LD   A, (dl_y)
    CP   B
    RET  Z
dl_not_done:

    ; — e2 = 2 * err  (16-bit) —
    LD   HL, (dl_err)
    ADD  HL, HL
    PUSH HL                 ; keep e2 for the second test

    ; — if e2 + dy > 0 (i.e. e2 > -dy): err -= dy;  x += sx —
    LD   A, (dl_dy)
    LD   E, A
    LD   D, 0
    ADD  HL, DE             ; HL = e2 + dy
    BIT  7, H
    JR   NZ, dl_skip_x      ; negative: condition false
    LD   A, H
    OR   L
    JR   Z, dl_skip_x       ; zero: condition false
    LD   HL, (dl_err)
    OR   A
    SBC  HL, DE             ; err -= dy  (DE still holds dy)
    LD   (dl_err), HL
    LD   A, (dl_x)
    LD   C, A
    LD   A, (dl_sx)
    ADD  A, C               ; x += sx  ($FF + x = x - 1 in 8-bit arithmetic)
    LD   (dl_x), A
dl_skip_x:

    ; — if e2 - dx < 0 (i.e. e2 < dx): err += dx;  y += sy —
    POP  HL                 ; HL = e2
    LD   A, (dl_dx)
    LD   E, A
    LD   D, 0
    OR   A
    SBC  HL, DE             ; HL = e2 - dx
    BIT  7, H
    JR   Z, dl_loop         ; non-negative: condition false
    LD   HL, (dl_err)
    ADD  HL, DE             ; err += dx  (DE still holds dx)
    LD   (dl_err), HL
    LD   A, (dl_y)
    LD   C, A
    LD   A, (dl_sy)
    ADD  A, C               ; y += sy
    LD   (dl_y), A
    JR   dl_loop

dl_x:   DB 0   ; current x
dl_y:   DB 0   ; current y
dl_x2:  DB 0   ; target x
dl_y2:  DB 0   ; target y
dl_dx:  DB 0   ; |x2-x1|
dl_dy:  DB 0   ; |y2-y1|
dl_sx:  DB 0   ; x step: 1 or $FF
dl_sy:  DB 0   ; y step: 1 or $FF
dl_err: DW 0   ; Bresenham error accumulator (16-bit signed)

Save this as draw_line.asm. Any program using it must also INCLUDE "calc_pixel_addr.asm" and INCLUDE "set_pixel.asm".

Every memory load follows the same pattern: LD A, (addr) to get the value into A, then LD reg, A to move it to a working register, leaving A free for the arithmetic. This is the only way to operate on memory-resident values on the Z80 — there is no ADD A, (addr) instruction.

BIT 7, H — The error is a 16-bit signed number, so its sign is bit 7 of the high byte. BIT 7, H sets the Zero flag when that bit is clear (the value is non-negative) and clears it when the bit is set (negative). Both Bresenham comparisons are signed because the error accumulator represents a signed difference; testing a 16-bit result this way cannot be fooled by 8-bit overflow, which is exactly what a JP P / JP M test on an 8-bit result can be.

The dl_x, dl_y and companion variables at the end of the routine are writable working storage, not constants. The routine overwrites them on every call. This means draw_line.asm must be assembled into RAM — it cannot be placed in ROM. For a pasmo --tapbas program loaded at $8000 this is always the case.

draw_line example

The following program draws four diagonal lines radiating from the screen centre, one into each quadrant, demonstrating all four directions of travel.

Assemble with pasmo --tapbas diagonals.asm diagonals.tap. Four lines radiate from near the screen centre, forming an X. Each line spans exactly 60 pixels in both x and y; because the error accumulator is 16-bit, there is no limit on line length other than the screen itself.

A Screen Border

This program draws a one-pixel border around the full screen using draw_hline and draw_vline, then loops forever so BASIC cannot overwrite the display.

    ORG  $8000

main:

    LD   B, 0
    LD   C, 0
    LD   D, 255
    CALL draw_hline

    ; Bottom edge: y=191, x1=0, x2=255
    LD   B, 191
    LD   C, 0
    LD   D, 255
    CALL draw_hline

    ; Left edge: x=0, y1=0, y2=191
    LD   B, 0
    LD   C, 0
    LD   D, 191
    CALL draw_vline

    ; Right edge: x=255, y1=0, y2=191
    LD   B, 0
    LD   C, 255
    LD   D, 191
    CALL draw_vline

    EI
.done:

    INCLUDE "calc_pixel_addr.asm"

Assemble with pasmo --tapbas border.asm border.tap and load the TAP into your emulator — the BASIC loader runs automatically. A white rectangle appears around the full screen boundary: two horizontal lines at y=0 and y=191, two vertical lines at x=0 and x=255.

The program does not end with RET. If it returned to BASIC, the interpreter would print its 0 OK report at the bottom of the screen — character rows 20–23, which cover pixel rows 160–191. That would immediately erase the bottom border line at y=191. Instead the program loops on HALT forever, waiting for interrupts and doing nothing else. The border stays visible until you reset the machine.

Notice that draw_line is not included here — this example does not need it. Include only the library files a program actually calls; unused routines waste memory and assembly time.

Key fact: horizontal lines are fast because an entire byte of eight pixels can be written in one instruction. Vertical lines must touch a separate byte for every pixel but gain efficiency from the constant +$20 address step between rows. Arbitrary lines call set_pixel for every point and are the slowest of the three — use draw_hline and draw_vline whenever the line is axis-aligned.

5. Drawing Shapes

[Back to Contents]

The line routines from chapter 4 are the foundation for every closed shape. A rectangle is four lines. A filled rectangle is a stack of horizontal lines. A circle is a sequence of pixel pairs arranged by an integer decision variable. This chapter builds four new library routines — draw_rect, fill_rect, draw_circle, and flood_fill — and closes with a focused example for each one.

Rectangles

Hollow Rectangle

A hollow rectangle is exactly four lines: top edge, bottom edge, left edge, right edge. draw_hline draws the horizontal edges and draw_vline draws the vertical ones. The corners are included in the horizontal calls; the vertical calls run between the corners so no pixel is drawn twice — though overdrawing with OR is harmless in any case.

; draw_rect
; Draw a hollow rectangle.
; Input:  B = y1  (0–191, top)
;         C = x1  (0–255, left)
;         D = y2  (0–191, bottom, must be >= y1)
;         E = x2  (0–255, right,  must be >= x1)
; Destroys: A, B, C, D, E, H, L
draw_rect:
    ; Top edge: y=y1, x1 to x2
    PUSH BC
    PUSH DE
    LD   D, E              ; draw_hline needs x2 in D; E holds x2, D holds y2
    CALL draw_hline        ; B=y1, C=x1, D=x2
    POP  DE
    POP  BC

    ; Bottom edge: y=y2, x1 to x2
    PUSH BC
    PUSH DE
    LD   B, D              ; y = y2
    LD   D, E              ; draw_hline needs x2 in D
    CALL draw_hline        ; B=y2, C=x1, D=x2
    POP  DE
    POP  BC

    ; Skip vertical edges if there are no interior rows (y2 - y1 < 2).
    ; With height 1 or 2 the hlines already cover every row; calling
    ; draw_vline with y1+1 > y2-1 would give a count of 0 and loop 256 times.
    LD   A, D
    SUB  B                 ; y2 - y1
    CP   2
    JR   C, dr_no_vert

    ; Left edge: x=x1, y1+1 to y2-1
    PUSH BC
    PUSH DE
    INC  B                 ; y1+1 — skip corner already drawn
    DEC  D                 ; y2-1 — skip corner already drawn
    CALL draw_vline        ; B=y1+1, C=x1, D=y2-1
    POP  DE
    POP  BC

    ; Right edge: x=x2, y1+1 to y2-1
    INC  B                 ; y1+1
    DEC  D                 ; y2-1
    LD   C, E              ; x = x2
    CALL draw_vline        ; B=y1+1, C=x2, D=y2-1
dr_no_vert:
    RET

Save this as draw_rect.asm. It requires draw_hline.asm, draw_vline.asm, and calc_pixel_addr.asm.

The PUSH/POP pairs preserve the original coordinates across each sub-call. draw_hline and draw_vline both destroy B, C, D — so the inputs must be saved before every call and restored before the next. The vertical edges run from y1+1 to y2-1 to avoid drawing the corners twice; with OR semantics this is a style choice rather than a correctness requirement. The LD A, D / SUB B / CP 2 / JR C, dr_no_vert guard before the vertical calls handles the degenerate cases where the rectangle is only one or two rows tall (y2 − y1 is 0 or 1). The two horizontal edges already cover every row, and there is no interior to draw. Without the guard, the vertical calls would receive an empty or inverted range (y1+1 > y2-1); draw_vline would compute a count of 0 and DJNZ would loop 256 times, scribbling over the display file and beyond.

Filled Rectangle

A filled rectangle is a horizontal line repeated for every row from y1 to y2. The row count is y2 - y1 + 1. The row counter is kept in memory and decremented with DEC A / JR NZ — DJNZ cannot be used because draw_hline destroys B on every call.

; fill_rect
; Draw a solid filled rectangle.
; Input:  B = y1  (0–191, top)
;         C = x1  (0–255, left)
;         D = y2  (0–191, bottom, must be >= y1)
;         E = x2  (0–255, right,  must be >= x1)
; Destroys: A, B, C, D, E, H, L
fill_rect:
    LD   A, D
    SUB  B                 ; y2 - y1
    INC  A                 ; row count = y2 - y1 + 1
    LD   (fr_rows), A
    LD   A, B
    LD   (fr_y),    A      ; save starting y
    LD   A, C
    LD   (fr_x1),   A      ; save x1
    LD   A, E
    LD   (fr_x2),   A      ; save x2

fr_loop:
    LD   A, (fr_y)
    LD   B, A              ; current row
    LD   A, (fr_x1)
    LD   C, A              ; x1
    LD   A, (fr_x2)
    LD   D, A              ; x2
    CALL draw_hline

    LD   A, (fr_y)
    INC  A
    LD   (fr_y), A          ; advance to next row

    LD   A, (fr_rows)
    DEC  A
    LD   (fr_rows), A
    JR   NZ, fr_loop
    RET

fr_y:    DB 0
fr_x1:   DB 0
fr_x2:   DB 0
fr_rows: DB 0

Save this as fill_rect.asm. It requires draw_hline.asm and calc_pixel_addr.asm.

DJNZ cannot be used directly here because draw_hline destroys B. The row counter is kept in memory (fr_rows) and decremented with DEC A / JR NZ instead. The same pattern — store working state in named variables, reload before each sub-call — is the standard approach whenever a called routine destroys the registers you need to preserve.

Filled rectangles are the fastest shape per pixel: draw_hline writes eight pixels per instruction in the middle of each row. A 32×32 filled rectangle writes all 32 middle bytes per row with 32 LD (HL), $FF instructions and only touches partial bytes at the left and right edges.

Circles

The Midpoint Circle Algorithm

Drawing a circle with floating-point trigonometry is too slow for the Z80. The midpoint circle algorithm (sometimes called Bresenham's circle algorithm) draws a circle using only integer addition and subtraction — no multiply, divide, or sine table.

The algorithm exploits 8-fold symmetry: a circle centred at (cx, cy) is symmetric across both axes and both diagonals. If you know the pixel at offset (+x, +y) lies on the circle, the seven mirrors are immediate:

OctantPixel
1(cx+x, cy+y)
2(cx−x, cy+y)
3(cx+x, cy−y)
4(cx−x, cy−y)
5(cx+y, cy+x)
6(cx−y, cy+x)
7(cx+y, cy−x)
8(cx−y, cy−x)

Each step of the algorithm computes one new (x, y) offset and plots all eight mirrors. The decision variable d starts at 1 - radius and tells the algorithm whether to step only in x or also in y:

; Midpoint circle — pseudocode
;   x = 0,  y = radius,  d = 1 - radius
;
; while x <= y:
;   plot 8 symmetric pixels
;   x += 1
;   if d < 0:  d += 2*x + 1
;   else:      y -= 1 ;  d += 2*(x - y) + 1

The decision variable d is a 16-bit signed value kept in HL and stored in the two-byte dc_d. On the Z80, 2*x is ADD HL, DE done twice (or ADD HL, HL on an already-16-bit value). The test d < 0 is BIT 7, H — the same sign test used in draw_line. Note that x - y is computed in 16 bits too, so it stays correct when it goes negative.

draw_circle

All eight pixel plots call set_pixel, so B and C (the y and x inputs) must be reloaded before each call. The centre coordinates and the current x/y offsets are kept in memory. The constraint is that centre ± radius must stay within the screen boundary (0–255 in x, 0–191 in y); checking this is the caller's responsibility.

; draw_circle
; Draw a circle using the midpoint algorithm.
; Input:  B = cy  (centre y, 0-191)
;         C = cx  (centre x, 0-255)
;         D = radius  (must keep centre +/- radius within screen bounds)
; Destroys: A, B, C, D, E, H, L
; The decision variable is 16-bit, so any radius up to 255 is handled.
draw_circle:
    LD   A, B
    LD   (dc_cy), A        ; save centre y
    LD   A, C
    LD   (dc_cx), A        ; save centre x
    LD   A, D              ; radius
    LD   (dc_y),  A        ; y offset starts at radius
    XOR  A
    LD   (dc_x),  A        ; x offset starts at 0

    ; d = 1 - radius  (16-bit signed)
    LD   E, D
    LD   D, 0
    LD   HL, 1
    OR   A
    SBC  HL, DE
    LD   (dc_d),  HL

dc_loop:
    ; while x <= y
    LD   A, (dc_x)
    LD   B, A
    LD   A, (dc_y)
    CP   B                 ; y - x: if x > y, done
    JR   C, dc_done        ; carry set means y < x

    ; plot 8 symmetric pixels
    CALL dc_plot8

    ; x += 1
    LD   A, (dc_x)
    INC  A
    LD   (dc_x), A

    ; if d < 0: d += 2*x + 1
    LD   HL, (dc_d)
    BIT  7, H
    JR   NZ, dc_d_neg

    ; d >= 0: y -= 1,  d += 2*(x-y) + 1
    LD   A, (dc_y)
    DEC  A
    LD   (dc_y), A         ; y -= 1
    LD   E, A
    LD   D, 0              ; DE = new y
    LD   A, (dc_x)
    LD   L, A
    LD   H, 0              ; HL = new x
    OR   A
    SBC  HL, DE            ; HL = x - y  (16-bit signed)
    ADD  HL, HL            ; 2*(x - y)
    INC  HL                ; 2*(x - y) + 1
    LD   DE, (dc_d)
    ADD  HL, DE            ; d += 2*(x-y) + 1
    LD   (dc_d), HL
    JR   dc_loop

dc_d_neg:
    ; HL = d;  d += 2*x + 1
    LD   A, (dc_x)
    LD   E, A
    LD   D, 0
    ADD  HL, DE
    ADD  HL, DE            ; + 2*x
    INC  HL                ; + 1
    LD   (dc_d), HL
    JR   dc_loop

dc_done:
    RET

; dc_plot8 -- plot the 8 symmetric pixels for current (x, y) offsets
; set_pixel destroys all registers, so dc_x and dc_y are reloaded from
; memory before every pixel. D = x offset, E = y offset throughout.
dc_plot8:
    ; (cx+x, cy+y)
    LD   A, (dc_x)
    LD   D, A
    LD   A, (dc_y)
    LD   E, A
    LD   A, (dc_cy)
    ADD  A, E
    LD   B, A
    LD   A, (dc_cx)
    ADD  A, D
    LD   C, A
    CALL set_pixel

    ; (cx-x, cy+y)
    LD   A, (dc_x)
    LD   D, A
    LD   A, (dc_y)
    LD   E, A
    LD   A, (dc_cy)
    ADD  A, E
    LD   B, A
    LD   A, (dc_cx)
    SUB  D
    LD   C, A
    CALL set_pixel

    ; (cx+x, cy-y)
    LD   A, (dc_x)
    LD   D, A
    LD   A, (dc_y)
    LD   E, A
    LD   A, (dc_cy)
    SUB  E
    LD   B, A
    LD   A, (dc_cx)
    ADD  A, D
    LD   C, A
    CALL set_pixel

    ; (cx-x, cy-y)
    LD   A, (dc_x)
    LD   D, A
    LD   A, (dc_y)
    LD   E, A
    LD   A, (dc_cy)
    SUB  E
    LD   B, A
    LD   A, (dc_cx)
    SUB  D
    LD   C, A
    CALL set_pixel

    ; (cx+y, cy+x)  -- x and y roles swap
    LD   A, (dc_x)
    LD   D, A
    LD   A, (dc_y)
    LD   E, A
    LD   A, (dc_cy)
    ADD  A, D
    LD   B, A
    LD   A, (dc_cx)
    ADD  A, E
    LD   C, A
    CALL set_pixel

    ; (cx-y, cy+x)
    LD   A, (dc_x)
    LD   D, A
    LD   A, (dc_y)
    LD   E, A
    LD   A, (dc_cy)
    ADD  A, D
    LD   B, A
    LD   A, (dc_cx)
    SUB  E
    LD   C, A
    CALL set_pixel

    ; (cx+y, cy-x)
    LD   A, (dc_x)
    LD   D, A
    LD   A, (dc_y)
    LD   E, A
    LD   A, (dc_cy)
    SUB  D
    LD   B, A
    LD   A, (dc_cx)
    ADD  A, E
    LD   C, A
    CALL set_pixel

    ; (cx-y, cy-x)
    LD   A, (dc_x)
    LD   D, A
    LD   A, (dc_y)
    LD   E, A
    LD   A, (dc_cy)
    SUB  D
    LD   B, A
    LD   A, (dc_cx)
    SUB  E
    LD   C, A
    CALL set_pixel

    RET

dc_cx: DB 0   ; centre x
dc_cy: DB 0   ; centre y
dc_x:  DB 0   ; current x offset (0 -> radius)
dc_y:  DB 0   ; current y offset (radius -> 0)
dc_d:  DW 0   ; decision variable (16-bit signed)

Save this as draw_circle.asm. It requires set_pixel.asm and calc_pixel_addr.asm.

The helper dc_plot8 is not a general routine — it is an internal subroutine of draw_circle and should not be called from outside. Because dc_done is a RET, execution never falls into dc_plot8 by accident; it is only reached by the explicit CALL dc_plot8 inside the loop.

set_pixel destroys every register, so all four values needed per pixel — dc_x, dc_y, dc_cy, and dc_cx — are reloaded from memory before every one of the eight pixel calculations. Four loads per pixel across eight pixels equals thirty-two memory reads per call to dc_plot8. That is the cost of having no free registers to keep any of these values alive across set_pixel calls.

Range: dc_d is a 16-bit signed value, so radii up to 255 are handled correctly. (An earlier 8-bit version of this routine began to draw distorted circles from a radius of about 77, as the decision variable overflowed.) The remaining limit is geometric: the whole circle must lie on the screen, because the routine does not clip.

Flood Fill

Flood fill starts from a seed pixel and spreads to all connected unset pixels, setting each one. The simplest version is 4-connected: from each pixel, the fill spreads to the four orthogonal neighbours (up, down, left, right) but not diagonally.

The natural implementation is recursive: set the current pixel, then recurse to each unset neighbour. On the Z80 each recursive call pushes at least the return address (2 bytes) plus any saved registers — 4 bytes per call here (the return address plus the PUSH BC that saves the coordinates). Filling a 30×30 area can push the call stack hundreds of frames deep, consuming several kilobytes. This is safe when filling small enclosed areas such as icon backgrounds or HUD boxes. Do not use recursive flood fill on large open areas.

; flood_fill
; 4-connected flood fill from a seed pixel.
; Input:  B = y  (0–191)
;         C = x  (0–255)
; Fills all unset pixels reachable from (x,y) by 4-connectivity.
; The fill stops at the left and right screen edges (x does not wrap).
; Warning: stack depth grows with fill area. Safe for small regions only.
; Destroys: A, B, C, H, L (and uses stack heavily)
flood_fill:
    ; bounds check: stay within 0–255 x, 0–191 y
    LD   A, B
    CP   192
    RET  NC               ; y >= 192: off screen

    ; check if pixel is already set — if so, stop
    PUSH BC
    CALL calc_pixel_addr   ; HL = byte addr, A = bitmask
    LD   B, A              ; save bitmask
    AND  (HL)              ; test pixel
    JR   NZ, ff_already_set

    ; set the pixel
    LD   A, B
    OR   (HL)
    LD   (HL), A

    POP  BC                ; restore y=B, x=C

    ; recurse: up (y-1)
    PUSH BC
    DEC  B
    CALL flood_fill
    POP  BC

    ; recurse: down (y+1)
    PUSH BC
    INC  B
    CALL flood_fill
    POP  BC

    ; recurse: left (x-1) — skip if already at x = 0 (DEC would wrap to 255)
    LD   A, C
    OR   A
    JR   Z, ff_no_left
    PUSH BC
    DEC  C
    CALL flood_fill
    POP  BC
ff_no_left:

    ; recurse: right (x+1) — INC wraps 255 to 0 and sets Z: off the right edge
    INC  C
    RET  Z
    JP   flood_fill        ; tail call — no PUSH/POP needed for last branch

ff_already_set:
    POP  BC
    RET

Save this as flood_fill.asm. It requires calc_pixel_addr.asm.

The final recursive call (right neighbour) is a tail call — flood_fill has nothing left to do after it returns. Replacing CALL flood_fill / RET with JP flood_fill eliminates one stack frame for every right-moving step, slightly reducing peak stack depth.

The y ≥ 192 bounds check at the entry prevents going off the bottom of the screen; going above the top wraps y to 255, which fails the same check. For x the routine checks explicitly before each horizontal step: LD A, C / OR A / JR Z skips the left recursion when x is 0, and INC C / RET Z abandons the right recursion when x wraps from 255 to 0. Without these checks the fill would leak across the edge and re-emerge on the opposite side of the screen.

Example: Filled Circle

A filled circle requires two steps: draw the outline with draw_circle to create a closed border, then seed flood_fill at the centre. The flood fill follows the four-neighbour rule and stops at every set pixel — which is exactly the outline just drawn. Keep the radius small: the recursive fill uses approximately 4 bytes of stack per pixel visited, so a radius of 15 gives a 30-pixel-diameter interior of roughly 700 pixels, or about 3 KB of stack — fine if your stack has room, but keep an eye on it.

    ORG  $8000

main:
    ; Step 1 — draw the circle outline
    ; Centre (95, 127), radius 15  (interior ~700 pixels, safe stack depth)
    LD   B, 95             ; cy
    LD   C, 127            ; cx
    LD   D, 15             ; radius
    CALL draw_circle

    ; Step 2 — flood-fill from the centre (guaranteed interior pixel)
    LD   B, 95             ; seed y = cy
    LD   C, 127            ; seed x = cx
    CALL flood_fill

    EI
.done:
    HALT
    JR   .done

    INCLUDE "calc_pixel_addr.asm"
    INCLUDE "set_pixel.asm"
    INCLUDE "draw_circle.asm"
    INCLUDE "flood_fill.asm"

    END  $8000

Assemble with pasmo --tapbas filled_circle.asm filled_circle.tap. You will see a solid white disc. Seeding at the exact centre is reliable because the centre coordinate is always interior for any radius greater than zero. The fill works because draw_circle produces a fully closed border with no gaps — the eight-fold symmetry of the midpoint algorithm guarantees this for all integer radii.

Key fact: shape routines are wrappers around line routines. A rectangle is four line calls. A filled rectangle is a loop of horizontal line calls. A circle plots 8 pixels per step using the same integer decision-variable technique as Bresenham's line. Each layer of abstraction adds no new Z80 instructions — only new ways to organise calls to the primitives already built.

6. Sprites

^ Back to top

A sprite is a small bitmap — a player's ship, an enemy, a bullet, a cursor — that can be positioned and moved independently anywhere on the screen. On the ZX Spectrum every graphic is ultimately composed of individual bits in the display file, so drawing a sprite means copying a block of pre-defined pixel bytes into the correct display-file addresses. This chapter builds three library routines that make sprite drawing practical, starting from the simplest possible case and working up through transparency masking and safe screen-edge clipping.

Defining Sprite Data

The Sprite Descriptor

A sprite is described by a small block of bytes assembled into the program binary with DB directives. The first two bytes form a header that records the dimensions; the remaining bytes are the pixel data, stored row by row from top to bottom.

; Unmasked sprite layout
sprite_name:
    DB height        ; number of pixel rows           (1–191)
    DB width_bytes   ; display bytes per row          (1–32)
    DB ...           ; pixel data, row-major order
                    ; bit 7 of each byte = left-most pixel

The bit ordering follows the same convention as the display file itself: bit 7 (the most-significant bit) represents the left-most pixel of the byte, and bit 0 the right-most. A width_bytes of 1 gives an 8-pixel-wide sprite; 2 gives 16 pixels, and so on up to the full 32-byte row width of the screen.

An 8×8 Example: the Alien

The following sprite represents a classic arcade-style alien invader. Each row is a single byte; dots mark cleared bits (paper) and asterisks mark set bits (ink).

alien_sprite:
    DB 8, 1               ; 8 rows tall, 1 byte (8 pixels) wide
    ;      7 6 5 4 3 2 1 0
    DB %00100100          ; . . * . . * . .   antennae
    DB %01111110          ; . * * * * * * .   head
    DB %11011011          ; * * . * * . * *   eyes
    DB %11111111          ; * * * * * * * *   body
    DB %10111101          ; * . * * * * . *   arms
    DB %01011010          ; . * . * * . * .   waist
    DB %01000010          ; . * . . . . * .   legs
    DB %00100100          ; . . * . . * . .   feet

To visualise the sprite, read each byte from left to right, substituting * for 1 and . for 0. Reading the table above row by row produces the alien shape.

A 16×5 Example: the Spaceship

When width_bytes is greater than 1, each logical row of the sprite is stored as consecutive bytes, left byte first. A 16-pixel-wide sprite has two bytes per row; the draw routine writes them one after the other into consecutive display addresses on the same scan line.

ship_sprite:
    DB 5, 2               ; 5 rows tall, 2 bytes (16 pixels) wide
    ;      byte 0           byte 1

    DB %00000001, %10000000  ; . . . . . . . * * . . . . . . .   nose

    DB %11111111, %11111111  ; * * * * * * * * * * * * * * * *   widest

    DB %00000001, %10000000  ; . . . . . . . * * . . . . . . .   tail

Character Alignment

The routines built in this chapter require the sprite's x coordinate to be a multiple of 8 — that is, aligned to a display-file byte boundary. This is called character alignment. With alignment enforced, each sprite byte maps directly onto one display-file byte with no bit-shifting at all, keeping the drawing code simple and fast.

Pixel-precise positioning at arbitrary x coordinates requires shifting every sprite byte by the sub-character offset before writing, producing one or two output bytes per source byte. That technique — while essential for smooth animation — adds significant complexity and is beyond the scope of this chapter; the routines here use the character-aligned approach that was standard in many early Spectrum games.

Drawing Sprites

The IX Register

The existing library routines pass all parameters in the B, C, D, E register pairs. A sprite drawing routine needs a third input: a pointer to the sprite data. Neither the 8-bit registers nor HL (which calc_pixel_addr overwrites with the display address) are available, so this chapter introduces IX.

IX is one of the Z80's two 16-bit index registers. Like HL it holds a 16-bit address, but it also supports a displacement: (IX+n) reads from the byte at address IX+n without changing IX itself. This makes IX ideal for walking through structured data — read the header at offsets 0 and 1, then advance IX past the header with two INC IX instructions to point at the pixel data.

InstructionMeaning
LD A, (IX+0)Load A from address IX+0 (the byte IX points at)
LD A, (IX+1)Load A from the next byte without touching IX
INC IXAdvance IX by one (full 16-bit increment)
LD (IX+0), AStore A at the address IX points at

The Two-Loop Pattern

Drawing a rectangular sprite requires two nested loops. The outer loop counts pixel rows from top to bottom. The inner loop copies one row's worth of bytes from the sprite data into consecutive display-file addresses on the same scan line.

outer: PUSH HL              ; save start-of-row display address
       ; inner: write width_bytes from IX into HL, then INC IX and INC L
       POP  HL              ; restore start-of-row (L = original column)
       ; advance HL to the next pixel row
       ; decrement row counter; loop if not zero

The PUSH/POP pair is essential. The inner loop increments L to step across the byte columns of the current scan line. After the inner loop, L has advanced by width_bytes from where it started. Restoring HL via POP brings L back to the original column value so that the row-advance arithmetic (which affects both H and L) operates on the correct starting address.

The row-advance logic is identical to the dv_cross path in draw_vline: check whether the scan-line field (H bits 2:0) has reached 7; if not, INC H; if so, clear LLL and step the character-row field in L, propagating any carry into the screen-third field in H.

One further point on INC L versus INC HL: within a single scan line, all display bytes share the same H value. Incrementing only L steps one byte to the right without disturbing the H field that encodes the row address. Using INC HL instead would be correct but costs one extra byte and one extra clock; INC L is both shorter and faster, and Chapter 4 established that it is always safe within a row.

draw_sprite.asm

; draw_sprite
; Draw an unmasked, character-aligned sprite.
; Sprite pixels are OR'd into the display — existing set pixels are
; preserved where the sprite byte has a 0 bit; existing clear pixels
; are forced on where the sprite byte has a 1 bit.
;
; Input:  B  = y          (pixel row,    0–191)
;         C  = x          (pixel column, must be a multiple of 8)
;         IX = pointer to sprite descriptor:
;                DB height       ; number of pixel rows  (1–191)
;                DB width_bytes  ; bytes per row          (1–32)
;                DB ...          ; pixel data, row-major
; Destroys: A, B, C, D, E, H, L, IX
draw_sprite:
    LD   A, (IX+0)         ; read height from sprite header
    OR   A                 ; height = 0?
    RET  Z                 ; nothing to draw (else DEC would wrap to 255 rows)
    LD   (ds_rows), A      ; store as decreasing row counter
    LD   A, (IX+1)         ; read byte-width from sprite header
    LD   (ds_width), A
    INC  IX                ; advance past height byte
    INC  IX                ; advance past width byte — IX → first pixel byte

    CALL calc_pixel_addr   ; HL = display address of (y,x)  A = mask (unused)

ds_row_loop:
    PUSH HL                ; save start-of-row display address

    LD   A, (ds_width)
    LD   B, A              ; B = byte counter for this row
ds_col_loop:
    LD   A, (IX+0)         ; fetch next sprite pixel byte from data
    OR   (HL)              ; merge: set sprite 1-bits, keep existing display bits
    LD   (HL), A
    INC  IX                ; advance sprite data pointer
    INC  L                 ; next display byte on same row (INC L safe within a row)
    DJNZ ds_col_loop

    POP  HL                ; restore start-of-row address (L = original column)

    ; — Advance HL to the next pixel row —
    LD   A, H
    AND  $07               ; isolate LLL (scan-line field, H bits 2:0)
    CP   $07               ; last scan line of this character row?
    JR   Z, ds_cross
    INC  H                 ; no: just increment the scan-line field
    JR   ds_row_dec

ds_cross:
    ; LLL was 7: wrap scan line to 0, step character-row field RRR in L
    LD   A, H
    AND  $F8               ; clear LLL → scan line resets to 0
    LD   H, A
    LD   A, L
    ADD  A, $20            ; step RRR field (L bits 7:5 = char row within third)
    LD   L, A
    JR   NC, ds_row_dec   ; no carry: still in the same screen third
    LD   A, H
    ADD  A, $08            ; carry: step TT field (H bits 4:3) — next screen third
    LD   H, A

ds_row_dec:
    LD   A, (ds_rows)
    DEC  A
    LD   (ds_rows), A
    JR   NZ, ds_row_loop
    RET

ds_rows:  DB 0   ; rows remaining (counts down)
ds_width: DB 0   ; bytes per row (constant for the duration of the call)

Walkthrough

Header read and IX advance. The two LD A, (IX+n) instructions extract height and width from the sprite descriptor and save them in memory variables, then two INC IX instructions advance IX from the header to the first pixel byte. Because calc_pixel_addr uses and destroys B, reading the header before the call lets us pass B = y and C = x to the routine unmodified.

calc_pixel_addr. Called with B = y and C = x exactly as in every other library routine. Since x is a multiple of 8, the bitmask in A on return is always %10000000 (the leftmost bit), which the routine discards — we are writing whole bytes, not individual pixels.

Inner column loop. LD A, (IX+0) fetches the current sprite byte; OR (HL) combines it with whatever is already in the display (preserving all set bits in both the sprite and the background); LD (HL), A writes the result back. INC IX advances through the sprite data and INC L steps one byte to the right in the display. After width_bytes iterations, DJNZ falls through with IX pointing at the first byte of the next sprite row.

Row advance. After the inner loop, POP HL restores HL to the start-of-row address. Testing H bits 2:0 against 7 selects the fast path (INC H) or the wrap path (AND $F8 + ADD L, $20 + optional ADD H, $08). The full explanation of this arithmetic appears in Chapter 4's vertical-line section.

Example Usage

    ; Draw the alien at pixel row 64, column 80
    LD   B, 64             ; y = 64  (row 8 of the middle screen third)
    LD   C, 80             ; x = 80  (byte column 10, multiple of 8)
    LD   IX, alien_sprite
    CALL draw_sprite

    ; Draw the ship at pixel row 100, column 120
    LD   B, 100
    LD   C, 120            ; x = 120 = 15 × 8 ✓
    LD   IX, ship_sprite
    CALL draw_sprite

Both calls require calc_pixel_addr to be assembled into the same binary. No other library routine is needed.

Masking & Transparency

The Limitation of OR-Drawing

draw_sprite OR-merges every sprite byte into the display. This means sprite 1-bits always set the corresponding display pixel regardless of what was already there — the sprite's solid pixels appear correctly. However, sprite 0-bits leave the existing display pixel untouched: they are transparent. This sounds useful, but it creates two problems in practice.

First, when a sprite is moved, OR-drawing the new position cannot erase the old position: the old pixels are set and nothing in the new draw can clear them. The screen accumulates a trail of ghost images.

Second, OR-transparency means the sprite's "paper" colour (its background within the bounding rectangle) shows through as whatever the display happens to contain. A sprite that is supposed to have a solid coloured body looks hollow whenever it passes over existing graphics.

Both problems require the ability to clear display pixels within the sprite's opaque area as well as set them. That is what a mask achieves.

The AND-OR Technique

For each display byte covered by the sprite, three values are involved: the existing display byte, an AND mask byte, and an OR pixel byte. The update is:

display = (display AND mask_byte) OR pixel_byte

The AND mask uses a 0 bit to mean opaque (belonging to the sprite) and a 1 bit to mean transparent (background shows through). The OR pixel byte then provides the actual ink/paper pattern within the opaque area.

AND bitOR bitResultMeaning
011Sprite ink pixel
000Sprite paper pixel (background erased)
10bg bit unchangedTransparent — background preserved

The AND pass punches a hole exactly the shape of the opaque area, clearing all those display bits to zero. The OR pass then paints the sprite's ink pixels into that hole. The result is a clean, opaque sprite that fully replaces whatever was beneath it in its opaque region, while leaving the rest of the display untouched.

The Masked Sprite Format

The masked sprite descriptor uses the same header as the unmasked format, but each pixel byte is paired with a preceding AND mask byte. For a sprite with width_bytes of N, each row in the data section contains N AND bytes followed by N OR bytes — grouped as pairs, one pair per byte column, reading left to right:

masked_sprite_name:
    DB height
    DB width_bytes
    ; for each row, interleaved AND/OR pairs left-to-right:
    DB and_col0, or_col0 [, and_col1, or_col1, ...]   ; row 0
    DB ...                                            ; row 1 …

The total data size for a masked sprite is 2 + height × width_bytes × 2 bytes (twice the pixel data of an unmasked sprite of the same dimensions).

Here is the alien sprite redefined with a mask. The AND mask 0-bits enclose the alien's bounding silhouette; the OR byte provides the actual pixel pattern within that silhouette.

alien_masked:
    DB 8, 1                          ; 8 rows, 1 byte wide
    ;      AND mask    OR pixels
    ;      7 6 5 4 3 2 1 0   7 6 5 4 3 2 1 0
    DB %11011011, %00100100          ; opaque: bits 5 and 2 only  (antennae)
    DB %10000001, %01111110          ; opaque: bits 6:1            (head)
    DB %00000000, %11011011          ; fully opaque                (eyes)
    DB %00000000, %11111111          ; fully opaque                (body)
    DB %00000000, %10111101          ; fully opaque                (arms)
    DB %00000000, %01011010          ; fully opaque                (waist)
    DB %10000001, %01000010          ; opaque: bits 6:1            (legs)
    DB %11011011, %00100100          ; opaque: bits 5 and 2 only  (feet)

Notice that for the four fully-opaque body rows the AND mask is $00. Every display bit in those byte positions is cleared before the OR pixel byte is applied, so the sprite's paper colour (0 bits in the OR byte) genuinely erases the background.

draw_sprite_masked.asm

; draw_sprite_masked
; Draw a masked, character-aligned sprite.
; For every byte position: display = (display AND mask_byte) OR pixel_byte
;
; AND mask:  bit = 0 → opaque   (sprite owns this bit)
;            bit = 1 → transparent (background preserved)
; OR pixel:  within opaque bits, 1 = ink, 0 = paper
;

;         C  = x  (pixel column, must be a multiple of 8)
;         IX = pointer to masked sprite descriptor

Walkthrough: the Inner Column Loop

The key is the use of D as a temporary. The inner loop body is:

    LD  A, (IX+0)   ; A = AND mask
    AND (HL)        ; A = display & mask  (opaque area cleared)
    LD  D, A        ; stash the cleared-display value
    INC IX          ; IX now points to the OR pixel byte
    LD  A, (IX+0)   ; A = OR pixel
    OR  D           ; A = (display & mask) | pixel
    LD  (HL), A     ; write the result
    INC IX          ; advance to AND byte of next column
    INC L

D holds the intermediate value — the display byte after the AND mask has punched the hole — between the two INC IX instructions. After the OR D, the accumulated result is the final pixel value for that byte position. The DJNZ then repeats for the next byte column, where IX now points at the next AND byte. The register D is available because the row loop does not otherwise use it; E and the rest of the registers are either the loop counter (B via DJNZ) or the addresses (H, L, IX).

Erasing Sprites

A masked sprite can be erased cleanly only if the background it was drawn over is known. Two practical approaches cover most Spectrum games.

XOR erase (unmasked sprites only). When draw_sprite OR-draws a sprite over a blank background (all display bytes zero in that region), XOR-ing those same sprite bytes back removes them: every bit that was set by OR is cleared by XOR. Chapter 3's toggle_pixel demonstrates the principle — XOR with a value once to draw; XOR again with the same value to erase. This works only when the background is guaranteed clear. A simple XOR variant of draw_sprite replaces OR (HL) with XOR (HL).

Background save and restore. Before drawing, copy the display bytes that the sprite will overwrite into a save buffer the same size as the sprite's pixel data. To erase, copy the save buffer back. This is the robust general solution and underpins the double-buffering technique covered in Chapter 9.

Clipping at Screen Edges

The Corruption Problem

The display file occupies addresses $4000–$57FF. The attribute file follows immediately at $5800–$5AFF. If a sprite write strays below pixel row 191 the routine advances HL into the attribute file and overwrites colour data with pixel bytes — corrupting colours but not crashing the machine. Writing further still reaches general RAM. Neither draw_sprite nor draw_sprite_masked performs any boundary check, so callers must guarantee the sprite fits entirely on-screen.

There are two practical strategies. The first is a pre-clip guard that simply refuses to draw the sprite if any part would land off-screen. The second is partial clipping that reduces the effective height and width to only the visible portion. The library provides both: a guard is easily written by the caller; draw_sprite_clipped implements partial clipping for the bottom and right edges.

Understanding the Clip Boundaries

For a character-aligned sprite starting at (y, x):

EdgeOff-screen conditionClipped value
Bottomy + height > 192visible_rows = 192 − y
Rightx/8 + width_bytes > 32visible_cols = 32 − x/8

Left and top clipping require the x or y start position to be negative — outside the range of an unsigned byte. The routines in this book treat all coordinates as unsigned 8-bit values (0–255), so negative positions cannot be expressed. Games that need left or top clipping typically manage it by storing sprite positions as signed 16-bit values and computing the starting offset into the sprite data before calling the draw routine; that technique is not covered here.

Bottom Clipping: Capping the Row Count

The bottom clip is computed with a single comparison. If the sprite fits, the full height is used; if not, the available number of rows (192 − y) is used instead. In Z80 this is a subtraction followed by a comparison:

    LD   A, (IX+0)         ; full sprite height → D
    LD   D, A
    LD   A, 192
    SUB  B                 ; available rows = 192 - y  (B = y)
    CP   D                 ; available >= height?
    JR   NC, .h_ok         ; yes: use the full height
    LD   D, A              ; no:  use available rows
.h_ok:
    LD   (dsc_rows), D     ; store the clipped row count

The CP instruction sets carry if A (available) is less than D (height). If carry is clear, there is enough room; if carry is set, the available count in A is the clip limit.

Right Clipping: Capping the Byte Count

Byte-column arithmetic operates in the range 0–31. The starting byte column is x / 8 (three right rotations and an AND to discard the garbage rotated in). Available columns to the right are 32 − start_col. If the sprite's width_bytes exceeds that, it is capped.

    LD   A, (IX+1)         ; full sprite width in bytes → E
    LD   E, A
    LD   A, C              ; C = x
    RRCA
    RRCA
    RRCA
    AND  $1F               ; start byte-column = x / 8
    LD   D, A              ; D = start column
    LD   A, 32
    SUB  D                 ; available byte-columns to the right
    CP   E                 ; available >= width?
    JR   NC, .w_ok
    ; clip: record how many bytes to skip per row so IX stays in sync
    LD   (dsc_width), A    ; visible byte-columns
    LD   D, A
    LD   A, E
    SUB  D                 ; skip = full_width - clipped_width
    LD   (dsc_skip), A
    JR   .draw
.w_ok:
    LD   (dsc_width), E    ; use full width
    XOR  A
    LD   (dsc_skip), A    ; nothing to skip

The dsc_skip variable is the key difference from plain draw_sprite. When the sprite is wider than the visible area, the column loop writes only dsc_width bytes per row. To keep IX aligned with the sprite data for the next row, the skip loop must advance IX by dsc_skip additional steps before the row-advance logic runs. Without this, every subsequent row would read from the wrong position in the sprite data.

draw_sprite_clipped.asm

; draw_sprite_clipped
; Draw a character-aligned sprite with bottom and right edge clipping.
; Rows that would fall below y=191 and byte-columns that would extend past
; column 31 are silently trimmed before drawing begins.
; If y >= 192 the sprite is entirely off-screen and is not drawn.
; Left and top edge clipping are not supported: x must be 0–248 (multiple of
; 8) and y must be 0–191 before calling.
;
; Input:  B  = y  (pixel row,    0–191)
;         C  = x  (pixel column, multiple of 8, 0–248)
;         IX = pointer to sprite descriptor (same format as draw_sprite)
; Destroys: A, B, C, D, E, H, L, IX
draw_sprite_clipped:
    ; — Return immediately if the sprite starts below the screen —
    LD   A, B
    CP   192
    RET  NC

    ; — Clip height: limit to rows that fit below y —
    LD   A, (IX+0)         ; full sprite height
    LD   D, A              ; D = full height
    LD   A, 192
    SUB  B                 ; available rows from y to the screen bottom (192 - y)
    CP   D                 ; available >= full height?
    JR   NC, dsc_h_ok
    LD   D, A              ; no: use only the available rows
dsc_h_ok:
    LD   A, D
    LD   (dsc_rows), A

    ; — Clip width: limit to byte-columns that fit to the right of x —
    LD   A, (IX+1)         ; full sprite width in bytes
    LD   E, A              ; E = full width (kept for skip-count calculation below)
    LD   A, C
    RRCA
    RRCA
    RRCA
    AND  $1F               ; start byte-column = x / 8  (0–31)
    LD   D, A
    LD   A, 32
    SUB  D                 ; byte-columns available to the right of start_col
    CP   E                 ; available >= full width?
    JR   NC, dsc_w_ok
    LD   (dsc_width), A    ; clip: store only the available column count
    LD   D, A              ; D = clipped width
    LD   A, E
    SUB  D                 ; skip = full_width - clipped_width (bytes per row to skip)
    LD   (dsc_skip), A
    JR   dsc_draw
dsc_w_ok:
    LD   A, E
    LD   (dsc_width), A
    XOR  A
    LD   (dsc_skip), A     ; no bytes to skip on the right

dsc_draw:
    LD   A, (dsc_rows)
    OR   A
    RET  Z                 ; zero rows after clipping: nothing to draw
    INC  IX                ; skip height byte in header
    INC  IX                ; skip width byte  in header — IX → first pixel byte
    CALL calc_pixel_addr   ; HL = display-file address of (y, x)

dsc_row_loop:
    PUSH HL                ; save start-of-row display address

    ; — Draw one row's visible bytes —
    LD   A, (dsc_width)
    LD   B, A
dsc_col_loop:
    LD   A, (IX+0)
    OR   (HL)
    LD   (HL), A
    INC  IX
    INC  L
    DJNZ dsc_col_loop

    ; — Advance IX past the right-clipped bytes so it reaches the next row —
    LD   A, (dsc_skip)
    OR   A
    JR   Z, dsc_row_adv    ; nothing clipped: no skip needed
    LD   B, A
dsc_skip_loop:
    INC  IX
    DJNZ dsc_skip_loop

dsc_row_adv:
    POP  HL                ; restore start-of-row address

    ; — Advance HL to the next pixel row —
    LD   A, H
    AND  $07               ; isolate LLL (scan-line field)
    CP   $07
    JR   Z, dsc_cross
    INC  H
    JR   dsc_row_dec
dsc_cross:
    LD   A, H
    AND  $F8               ; clear LLL
    LD   H, A
    LD   A, L
    ADD  A, $20            ; step RRR (character-row field)
    LD   L, A
    JR   NC, dsc_row_dec
    LD   A, H
    ADD  A, $08            ; step TT (screen-third field)
    LD   H, A
dsc_row_dec:
    LD   A, (dsc_rows)
    DEC  A
    LD   (dsc_rows), A
    JR   NZ, dsc_row_loop
    RET

dsc_rows:  DB 0            ; row count after bottom clipping
dsc_width: DB 0            ; byte-columns per row after right clipping
dsc_skip:  DB 0            ; bytes to advance IX past at end of each row

The Skip Loop

The skip loop — LD B, A followed by DJNZ dsc_skip_loop — is only entered when dsc_skip is non-zero. The OR A test before it sets the zero flag without changing A, allowing the JR Z to bypass the entire loop for unclipped rows. When the loop does run, it simply performs dsc_skip additional INC IX steps, discarding those sprite bytes, so that IX arrives at the correct position — the start of the next sprite row — before the row-advance logic is applied.

A Guard for the Left and Top Edges

When a sprite could potentially start off the left or top edge, the caller must ensure valid coordinates before calling any draw routine. A simple guard might look like this:

    ; Reject the draw if y or x would place the sprite's top-left off-screen.
    ; (Left and top clipping are not supported by the library routines.)
    LD   A, B
    CP   192
    RET  NC              ; y off the bottom (draw_sprite_clipped handles partial)
    LD   A, C
    AND  %00000111
    JR   NZ, .skip     ; x not byte-aligned: skip this sprite
    CALL draw_sprite_clipped

Static Decoration with draw_sprite

The three bunkers are drawn once during setup, before main_loop begins, with no bookkeeping and no erase. draw_sprite is the right tool here because the bunkers are static: the display starts all-black, so a simple OR writes exactly the pixels that should be set with no concern about what was underneath. The three calls are structurally identical — load B with the y row, C with the x column, IX with the sprite address, then call. draw_sprite carries no overhead for masks, skip counts, or clip calculations; it is the fastest of the three routines and appropriate for any sprite that is drawn once and left alone.

The interesting consequence reveals itself later. draw_sprite only adds pixels; it has no way to protect them once drawn. When the invader sweeps through BUNKER_Y = 160, the erase step applies INV_ERASE via draw_sprite_masked. Every AND byte in that sprite is $00, which clears every display byte in the 16‑×‑8 bounding box to zero, regardless of what was already there — including any bunker pixels that happen to fall inside the box. The invader has no knowledge of the bunkers; the erasure is simply the result of a fully-opaque AND mask applied over the same screen area. This is the defining limitation of unmasked drawing: pixels can be added but not selectively protected from future masked operations.

Animated Movement with draw_sprite_masked

The invader uses an erase-then-draw pattern every frame. The erase step calls draw_sprite_masked with INV_ERASE, which has AND = $00 and OR = $00 in every byte. For each display byte the operation is (display AND $00) OR $00 = $00 — an unconditional clear. The entire 16‑×‑8 bounding box is set to paper colour (black) with no regard for any other pixels inside it. The draw step then applies the animated frame data against the guaranteed-clean background.

Animation is produced by toggling inv_frame between 0 and 1 each frame using XOR 1. Frame A has wide legs on row 6 and inner feet on row 7; frame B swaps the two. Rows 0–5 are identical between frames, so only 16 bytes change per cycle. IX is loaded with INV_SPRITE_A or INV_SPRITE_B before the draw call, and draw_sprite_masked reads the frame pointer from IX to traverse whichever data it points to.

Five state variables drive the movement. inv_x and inv_y hold the current top-left pixel coordinate; inv_dir is 0 for rightward and 1 for leftward. Each frame, inv_x is stepped by STEP_X = 8 in the current direction. When x reaches RIGHT_MAX = 240 or underflows below 0, the direction is reversed and inv_step_down adds STEP_Y = 16 to inv_y, wrapping to 0 if the result would exceed BOTTOM_MAX = 184. Clamping at both edges ensures inv_x is always a character-aligned column in the range 0–240, as all three sprite routines require.

The main loop ends with JP main_loop rather than JR main_loop. JR encodes a signed 8-bit displacement and can only reach within ±127 bytes of the following instruction. The UFO-clearing loop added enough code between main_loop and the jump to exceed that range, so JP — which uses a full 16-bit address — is used instead. This is a practical reminder that JR is efficient for short forward or backward branches but must be replaced by JP when the target grows too distant.

UFO Clipping with draw_sprite_clipped

draw_sprite_clipped performs a pure OR-draw with no AND mask, so it cannot erase its own previous frame: ORing zero bits into the display leaves existing pixels unchanged. The solution used here is a clear-before-draw pattern: the entire character row the UFO occupies is zeroed before each frame is drawn, removing any trace of the previous position automatically regardless of where the sprite was.

Character row 1 (pixel rows 8–15) spans eight scan lines. Within the display file, all eight share the same byte-column layout: L runs from $20 (column 0) to $3F (column 31), while H steps from $40 (scan line 0, y=8) to $47 (scan line 7, y=15). The clear loop exploits this regularity directly: it sets H = $40 and an outer counter D = 8, then for each of the eight scan lines it resets L = $20, runs a 32-byte inner DJNZ loop writing $00, and increments H to step to the next scan line. The entire 256-byte row is zeroed in two nested loops with no address arithmetic beyond a single INC H per scan line.

The UFO's x coordinate is stored as a single byte. Each frame STEP_X = 8 is added with an 8-bit ADD A, STEP_X. When x = 248 the next addition produces 256, which the 8-bit register truncates to 0 — the UFO reappears at the left edge automatically, with no comparison or branch required. The full sequence of positions is 0, 8, 16, …, 240, 248, 0, 8, … and the hardware overflow is the wrap.

At x = 248 the 2-byte UFO needs byte columns 31 and 32. Column 32 does not exist. draw_sprite_clipped detects this: it converts x to a byte-column (248 ÷ 8 = 31), finds that only 32 − 31 = 1 byte-column is available while the sprite is 2 bytes wide, and reduces the draw width to 1. The skip count (dsc_skip) is set to 1 so that IX advances past the right-hand byte of each sprite row without writing it. Only the left 8 pixels of the UFO appear at x = 248; the right half is trimmed silently with no caller-side handling.

UFO_Y is set to 8 so that the invader never overlaps the UFO's character row. The invader's y coordinate advances in multiples of STEP_Y = 16 from 0, producing only the values 0, 16, 32, 48, … The value 8 is never in that sequence, so the invader's 8-row bounding box (rows y to y + 7) never covers rows 8–15. The UFO row clear and the invader erase operate on disjoint areas of the display file.

What You See

The screen opens black with three bunker shapes near the bottom at columns 24, 112, and 200. The invader appears at the top-left and moves right one character column per frame, legs alternating between frame A and frame B. A small UFO travels across the second character row. As the UFO approaches the right edge its right half shrinks — at x = 248 only the left 8 pixels of the 16-pixel body remain — then the full shape reappears at the left edge on the next frame as the coordinate wraps through zero.

Each time the invader reverses it steps down two character rows. When it eventually reaches y = 160 — the bunker row — its erase sprite blacks out a 16‑×‑8 box on every frame. Any bunker whose position coincides exactly with the invader's bounding box on that pass has its pixels cleared by the AND = $00 erase, one pass at a time. Bunkers at x = 24, 112, or 200 are erased when the invader is at the same x on its y = 160 sweep; bunkers at other columns survive. The destruction is not programmed explicitly — it is the natural consequence of a fully-opaque masked erase applied over the same screen region as an unmasked OR-draw.

Scrolling the Whole Screen

Scrolling the ZX Spectrum display is not a simple block memory move. The display file occupies $4000–$57FF, but those 6144 bytes are arranged by scan-line offset within character row within screen third, not by visual top-to-bottom order. A naive LDIR from $4020 to $4000 would not move the second character row up to the first — it would shift the second scan line of character row 0 over the first, leaving the remaining 23 rows unchanged.

To scroll correctly we need to understand how H and L encode a display address. For a pixel at visual row y and byte column x:

  • H = $40 | (TT << 3) | LLL — TT selects the screen third (0 = rows 0–63, 1 = rows 64–127, 2 = rows 128–191) and LLL is the scan-line offset within the character row (0–7).
  • L = (RRR << 5) | x — RRR selects the character row within the third (0–7) and x is the byte column (0–31).

The key insight that makes efficient scrolling possible: for a fixed H value (fixed TT and LLL), the eight character rows of that third each contribute a 32-byte block sitting at L = 0, 32, 64, 96, 128, 160, 192, and 224. These eight blocks fill L from $00 to $FF without any gap. That means a single LDIR of 224 bytes can shift seven rows (rows 1–7 of the third) upward into the positions of rows 0–6, all without any inner loop.

The only complication is the boundary between thirds. Character row 8 (first row of TT=1) must move into character row 7's slot (last row of TT=0). Source and destination have different H values, so this 32-byte copy cannot be merged with either adjacent 224-byte block. The same applies to the boundary between TT=1 and TT=2 (rows 16 and 15).

Because the 224-byte within-third LDIR overwrites rows 0–6 using the original data from rows 1–7, the cross-boundary copy (row 8 → row 7) must happen before row 7 is overwritten. The correct per-LLL sequence is therefore: within TT=0, cross TT=0→1, within TT=1, cross TT=1→2, within TT=2, then clear row 23. The outer loop iterates that sequence once for each of the eight scan-line offsets (LLL = 0–7).

Because LDIR destroys BC, the current LLL value cannot be kept in a register across the copies. The routine stores it in a one-byte variable suc_lll and reloads it before each address computation.

scroll_up_char.asm

; scroll_up_char
; Scrolls the entire ZX Spectrum display up by one character row (8 pixels).
; Character row 0 is lost; the new bottom row (char row 23) is filled with
; zeros.  Attributes at $5800–$5AFF are not touched.
; Destroys: A, B, C, D, E, H, L.
scroll_up_char:
    XOR  A
    LD   (suc_lll), A      ; LLL = 0  (scan-line offset counter)
suc_lll_loop:
    ; ── TT=0: copy char rows 1–7 → rows 0–6 (224 bytes) ────────────────
    ; Within H = $40 | LLL, all 8 char rows of the first third sit at
    ; L = 0, 32, 64 … 224.  Copying from L=$20 (row 1) to L=$00 (row 0)
    ; for 224 bytes shifts rows 1–7 into rows 0–6 in one LDIR.
    LD   A, (suc_lll)
    OR   $40               ; H = $40 | LLL  (TT=0, this scan-line offset)
    LD   H, A
    LD   L, $20            ; source: char row 1 (RRR=1, L = 1×32 = $20)
    LD   D, H              ; dest same third and LLL
    LD   E, $00            ; dest: char row 0 (RRR=0, L=$00)
    LD   BC, 224           ; 7 rows × 32 bytes per row
    LDIR

    ; ── Cross TT=0→1: char row 8 → char row 7 ─────────────────────────
    ; Row 8 is the first row of TT=1 (H = $48|LLL, L=$00).
    ; Row 7 is the last row of TT=0  (H = $40|LLL, L = 7×32 = $E0).
    LD   A, (suc_lll)
    OR   $48               ; source H: TT=1, this LLL
    LD   H, A
    LD   L, $00            ; first byte of TT=1 (RRR=0)
    LD   A, (suc_lll)
    OR   $40               ; dest H: TT=0, this LLL
    LD   D, A
    LD   E, $E0            ; dest: char row 7 (RRR=7, L = $E0)
    LD   BC, 32
    LDIR

    ; ── TT=1: copy char rows 9–15 → rows 8–14 (224 bytes) ──────────────
    LD   A, (suc_lll)
    OR   $48               ; H = $48 | LLL  (TT=1)
    LD   H, A
    LD   L, $20            ; source: char row 9 (RRR=1 within TT=1)
    LD   D, H
    LD   E, $00            ; dest: char row 8
    LD   BC, 224
    LDIR

    ; ── Cross TT=1→2: char row 16 → char row 15 ────────────────────────
    LD   A, (suc_lll)
    OR   $50               ; source H: TT=2, this LLL
    LD   H, A
    LD   L, $00
    LD   A, (suc_lll)
    OR   $48               ; dest H: TT=1, this LLL
    LD   D, A
    LD   E, $E0            ; dest: char row 15 (last row of TT=1)
    LD   BC, 32
    LDIR

    ; ── TT=2: copy char rows 17–23 → rows 16–22 (224 bytes) ────────────
    LD   A, (suc_lll)
    OR   $50               ; H = $50 | LLL  (TT=2)
    LD   H, A
    LD   L, $20
    LD   D, H
    LD   E, $00
    LD   BC, 224
    LDIR

    ; ── Clear char row 23 (TT=2, RRR=7) for this LLL ───────────────────
    LD   A, (suc_lll)
    OR   $50
    LD   H, A
    LD   L, $E0            ; RRR=7, L = 7×32 = $E0
    LD   B, 32
    XOR  A
suc_clr:
    LD   (HL), A
    INC  L
    DJNZ suc_clr

    ; ── Advance to next scan-line offset ────────────────────────────────
    LD   A, (suc_lll)
    INC  A
    LD   (suc_lll), A
    CP   8
    JR   NZ, suc_lll_loop
    RET

suc_lll: DB 0              ; current scan-line offset (0–7)

The outer loop runs eight times, once for each LLL value. Each pass executes three LDIR blocks of 224 bytes and two of 32 bytes, then clears 32 bytes — a total of 3×224 + 2×32 + 32 = 768 bytes processed per LLL, or 6144 bytes over the full loop. That matches the display-file size, confirming every pixel byte is visited exactly once.

Scrolling Attributes

The colour attribute file at $5800–$5AFF (768 bytes) is arranged in simple top-to-bottom, left-to-right order: 32 bytes per character row, 24 rows. Scrolling it up by one character row is a straightforward LDIR followed by a clear of the bottom row. Unlike the pixel scroll, no scrambled-address logic is required.

Pixel-Level Shifting

A character-row scroll moves the display in 8-pixel jumps, which is visibly jerky. Smooth animation needs single-pixel granularity. Scrolling by one pixel row means copying each of the 192 pixel rows into the slot above it, then clearing the bottom row.

The relationship between consecutive pixel rows in memory is not constant. Within a character row, consecutive scan lines differ by one in the H register (same L): scan line 0 of char row 0 is at H = $40, scan line 1 at H = $41, and so on up to scan line 7 at H = $47. But the first scan line of character row 1 (visual pixel row 8) is at H = $40, L = $20 — H drops back to $40 while L advances by 32. This is the same cross-character-row step used by the sprite routines.

The routine below tracks two addresses simultaneously: DE is the destination (the row being overwritten) and HL is the source (the row one step below). After each 32-byte LDIR, the old source address becomes the new destination, and HL is advanced to the next pixel row using the same H/L step logic from the sprite drawing code.

; scroll_up_pixel
; Scrolls the entire display up by one pixel row (one scan line).
; Pixel row 0 is lost; the new bottom row (y=191) is filled with zeros.
; Destroys: A, B, C, D, E, H, L.
scroll_up_pixel:
    LD   DE, $4000         ; dest: pixel row 0  (TT=0, LLL=0, RRR=0)
    LD   HL, $4100         ; src:  pixel row 1  (TT=0, LLL=1, RRR=0)
    LD   B, 191            ; 191 copies: rows 1..191 → rows 0..190
sup_loop:
    PUSH BC                ; save row counter — LDIR overwrites BC
    PUSH HL                ; save source start — LDIR advances HL
    LD   BC, 32
    LDIR                   ; copy 32 bytes: source row → dest row
    POP  HL                ; restore source start address
    LD   D, H
    LD   E, L              ; old source becomes next iteration's dest
    ; Advance HL to the next pixel row using the ZX Spectrum row-step logic
    LD   A, H
    AND  $07               ; isolate LLL (scan-line offset field)
    CP   $07
    JR   Z, sup_cross
    INC  H                 ; LLL < 7: step scan-line field in H
    JR   sup_dec
sup_cross:
    LD   A, H
    AND  $F8               ; LLL = 7: clear scan-line field (→ LLL=0)
    LD   H, A
    LD   A, L
    ADD  A, $20            ; step RRR (character-row field in L)
    LD   L, A
    JR   NC, sup_dec
    LD   A, H
    ADD  A, $08            ; carry: step TT (screen-third field in H)
    LD   H, A
sup_dec:
    POP  BC
    DJNZ sup_loop

    ; After the loop DE points to the start of pixel row 191.
    LD   H, D
    LD   L, E
    LD   B, 32
    XOR  A
sup_clr:
    LD   (HL), A
    INC  L
    DJNZ sup_clr
    RET

Why HL Starts at $4100

Pixel row 0 is at H = $40, L = $00. Pixel row 1 — the first scan line of the same character row, one step down — is at H = $41, L = $00, i.e. address $4100. The first LDIR therefore copies 32 bytes from $4100 to $4000, sliding the visual second row into the first slot. After the copy, HL is restored to $4100, set as the new DE, and then advanced to pixel row 2 ($4200) by a single INC H.

The crossing case occurs seven times per character row, each time at pixel row 8k−1 where LLL = 7. For example, after copying pixel row 7 ($4700) into pixel row 6 ($4600), HL holds $4700 and the advance logic clears LLL, adds $20 to L (stepping RRR from 0 to 1), and produces $4020 — the address of pixel row 8 (char row 1, scan line 0). That is exactly the same step performed by the sprite drawing routines.

Speed Comparison

scroll_up_char processes all 6144 display bytes in one call using 8 × 5 LDIR blocks plus the clears. scroll_up_pixel moves almost as many bytes (191×32 = 6112 plus the 32-byte clear) but adds 191 PUSH/POP pairs and 191 row-advance computations — about 125 extra T-states per row, or roughly 24,000 in all. The cost is dominated by LDIR itself at 21 T-states per byte: about 129,000 T-states for scroll_up_char and about 153,000 for scroll_up_pixel. On a 3.5 MHz machine that is roughly 37 ms and 44 ms — nearly two full 20 ms frames each, and the pixel version is only about 20% slower. Neither can run every frame at 50 Hz; expect 25 scrolls per second at best, with no time left for anything else.

Smooth Scrolling Techniques

Horizontal Scrolling

Vertical scrolling moves the screen up or down by shifting data between scan-line addresses. Horizontal scrolling moves every pixel left or right, which means rotating bits within each row rather than copying bytes between rows.

Z80 provides the RR (rotate right through carry) instruction that rotates a register or memory location one bit to the right: the existing carry flag enters bit 7 (the leftmost pixel), and old bit 0 exits into the carry flag. Applying RR (HL) to each byte from left to right with carry cleared before the first byte creates a right-scroll: bit 0 of each byte flows into bit 7 of the next, carrying pixels across byte boundaries. The carry initially set to zero injects a blank pixel at the left edge.

Note that OR A clears the carry flag as a side effect (it always resets CF). AND A also works. Both are one byte and four T-states, making them the standard idiom for clearing carry on the Z80.

Avoiding Tearing

The Spectrum's ULA refreshes the screen continuously at 50 Hz. If the CPU is writing to the display file while the electron beam is drawing those bytes, the visible result is a horizontal tear — part of the frame shows the old pixels, part shows the new. Tearing is most noticeable with large scroll operations.

The safe window for display updates is when the beam is away from the pixels you are changing. The ULA fires its interrupt at the start of each frame, and the beam does not reach the first pixel row until about 64 scan lines (roughly 4 ms) later, so an IM 1 or IM 2 handler can write to the top of the screen ahead of the beam. Only operations shorter than that window are fully tear-free; a full-screen scroll takes about 37–44 ms, so it will tear unless it is hidden by double buffering (Chapter 9) or you restrict it to a smaller region. A simpler but less precise alternative is to count T-states and start the work at a calculated point in the frame.

For demos where a small amount of tearing is acceptable, the fastest approach is simply to call the scroll routine as quickly as possible and let the timing fall where it may. At 50 fps the tear moves up or down the screen each frame and blends into the motion.

Combining Scroll with Sprites

A common game pattern is a scrolling background with sprites moving over it. The simplest approach:

  1. Erase each sprite at its current position (using draw_sprite_masked with an all-zero erase sprite, as in the invader demo).
  2. Call scroll_up_pixel or scroll_up_char to advance the background.
  3. Redraw each sprite at its new position.

This works cleanly because the masked erase only touches the sprite's bounding box; the scroll only touches the background behind it. As long as step 1 precedes step 2, the erase clears the correct pixels before they are shifted, and the redraw in step 3 places the sprite correctly against the new background.

Scroll Speed

Each scroll call takes about two frames (see the speed comparison above), so scroll_up_pixel can manage only about 25 pixels per second — smooth but slow — and scroll_up_char about 200 pixels per second (8 pixels × 25 calls). To go faster you must scroll less data: a smaller window, or a double-buffered scheme (Chapter 9). The speed difference between the two routines comes from the step size, not from the routine being cheaper to run.

A practical rule of thumb: because each scroll call costs about two frames whatever its step size, the scroll step is what sets your speed — use scroll_up_char to move 8 pixels per call, and scroll_up_pixel only when you need single-pixel steps. At roughly 25 calls per second, scroll_up_char gives about 200 pixels per second and scroll_up_pixel about 25. Either routine consumes the whole CPU budget while it runs, so on a stock Spectrum scroll only every few frames, or scroll a smaller region (a custom routine that moves fewer rows) if you need time for sprites and game logic.

Build with: pasmo --tapbas scroll_demo.asm scroll_demo.tap

Why there is no sprite in this demo

Keeping a sprite visually fixed on a scrolling background seems straightforward: erase the sprite, scroll the background, redraw the sprite at the same position. The problem is timing. Each of the Chapter 7 scroll routines must touch every one of the 6 144 bytes in the display file, which at 3.5 MHz takes between about 37 ms (scroll_up_char) and about 56 ms (scroll_left_pixel). A PAL ZX Spectrum redraws its screen every 20 ms. The scroll routine alone therefore spans at least two complete display refreshes — and during the whole of that time the sprite has been erased but not yet redrawn. The electron beam sweeps through the sprite's row while the pixels are black, producing a visible flash on every single frame.

The standard solution is double buffering: draw the complete next frame — background and sprite together — into a second block of memory that is not currently being displayed, then show it only when it is complete. On a 48K machine that means copying the parts that changed to the screen just after the frame interrupt, while the beam is still above them (a full-screen copy takes nearly two frames, so it cannot be hidden in the blanking interval); on a 128K machine it means flipping to the second screen. Either way the viewer never sees a partial frame. Double buffering is covered in full in Chapter 9.

Background and Initialisation

draw_background fills the display with horizontal stripes by iterating through the 24 character rows. For each row it computes three values stored in memory variables — the fill byte, the base H value, and the starting L value — then runs a small inner loop to fill all eight scan lines. The two pieces of arithmetic are worth noting:

  • B AND $18 (= AND %00011000) extracts bits 4:3 of the character row index, which equals TT × 8 directly, avoiding any division. OR $40 builds the complete H_base in one further instruction.
  • Five consecutive ADD A, A instructions multiply RRR by 32, computing L_start (the column-0 address of the character row) without needing a shift loop or lookup table.
; draw_background
; Fills the display with horizontal stripes: even character rows all $FF
; (all pixels = ink colour), odd rows all $00 (all pixels = paper colour).
draw_background:
    LD   B, 0              ; B = character row index (0..23)
db_next_row:
    LD   A, B
    AND  1
    JR   NZ, db_is_odd
    LD   A, $FF
    JR   db_have_val
db_is_odd:
    XOR  A
db_have_val:
    LD   (db_val), A

    ; H_base = $40 | (TT<<3).  B AND $18 gives TT<<3 for B in 0..23.
    LD   A, B
    AND  $18               ; bits 4:3 of B = TT<<3  (0, 8, or 16)
    OR   $40
    LD   (db_hbase), A

    ; L_start = (B AND 7) << 5 = RRR * 32
    LD   A, B
    AND  $07
    ADD  A, A
    ADD  A, A
    ADD  A, A
    ADD  A, A
    ADD  A, A               ; five doublings: A = RRR << 5
    LD   (db_lstart), A

    LD   C, 0              ; C = LLL (0..7), reset for each new character row
db_scan:
    LD   A, (db_hbase)
    ADD  A, C              ; H = H_base + LLL
    LD   H, A
    LD   A, (db_lstart)
    LD   L, A
    LD   A, (db_val)
    PUSH BC                ; DJNZ overwrites B; save B=char-row and C=LLL
    LD   B, 32
db_fill:
    LD   (HL), A
    INC  L
    DJNZ db_fill
    POP  BC                ; restore B=char-row, C=LLL
    INC  C
    LD   A, C
    CP   8
    JR   NZ, db_scan

    INC  B
    LD   A, B
    CP   24
    JR   NZ, db_next_row
    RET

db_val:    DB 0
db_hbase:  DB 0
db_lstart: DB 0

The Main Loop

The main loop checks for SPACE (exit), then reads the held key and calls the appropriate scroll routine. A short software delay paces the loop to roughly 10 frames per second so the motion is easy to follow.

main_loop:
    ; Exit on SPACE
    LD   BC, $7FFE
    IN   A, (C)
    AND  $01
    RET  Z

    ; Key 6 → scroll_up_char (8-pixel jump) + attribute scroll

    CALL scroll_up_char_attr
    JR   after_scroll
not_key6:

    LD   BC, $F7FE
    IN   A, (C)

    JR   NZ, not_key5
    CALL scroll_left_pixel
    JR   after_scroll
not_key5:
    ; Key 8 → scroll_right_pixel
    LD   BC, $EFFE
    IN   A, (C)
    BIT  2, A
    JR   NZ, not_key8
    CALL scroll_right_pixel
    JR   after_scroll
not_key8:
    ; Default: scroll_up_pixel (smooth 1-pixel-per-frame upward scroll)
    CALL scroll_up_pixel

    CALL demo_delay
    JP   main_loop

The keyboard uses the ZX Spectrum half-row port system: port $EFFE covers the number keys 6–0, port $F7FE covers 1–5. Within each port, bits are active low — a zero bit means the key is currently held. BIT n, A sets the Z flag if bit n is zero, so JR NZ skips the scroll call when the key is not pressed, and falls through when it is.

Observing scroll_up_char vs scroll_up_pixel

Release all keys (or hold any key other than 5, 6, or 8): the background glides upward one pixel per frame, the stripe boundaries shifting smoothly and continuously. Hold key 6: each frame jumps the display by a full character row (8 pixels). The yellow bar nearest the top disappears in one instant rather than fading out across eight frames — the distinctive staircase of coarse scrolling. The paired call to scroll_up_char_attr keeps the attribute colours locked to the stripe positions; without it the colours drift out of alignment after the first press.

Observing scroll_left_pixel and scroll_right_pixel

Hold key 5 or 8. The whole display slides sideways one pixel per frame. The horizontal scrolls do not wrap: pixels that leave one edge are lost and paper (zero) pixels enter at the other, so the picture is gradually erased from the side it is moving away from. This is a good visual reminder that the scroll routines treat the display as a flat array of bytes — they have no concept of stripes, sprites, or any other higher-level structure.

What You See

The display opens with 12 solid yellow bars alternating with 12 black gaps, each 8 pixels tall. By default the background scrolls up one pixel per frame, the bars flowing continuously toward the top. The routines do not wrap, so blank rows enter at the bottom and the pattern empties out as it scrolls. Holding 6 produces the same net motion but in visible 8-pixel jumps. Holding 5 or 8 slides the display sideways, blanking it from one edge as zero pixels are shifted in.

8. Character & Text Graphics

^ Back to top

The Spectrum has no text mode. Every letter you see on screen is a small bitmap — eight bytes, one per scan line — copied into an 8×8 character cell of the same display file you have been drawing pixels into since Chapter 1. This is good news: the machinery for printing text is a close cousin of the sprite code you already have, and it is faster, because a character cell is always byte-aligned and exactly eight bytes tall. This chapter builds five small routines — draw_glyph, print_char, print_string, fill_attr_cells and make_bold — and finishes with a program that mixes ROM text, generated bold text and hand-drawn graphics characters in colour.

Using the ROM Character Set

The Spectrum ROM contains a font of 96 characters: codes 32 (space) to 127 (the copyright sign). Each glyph is 8 bytes, top scan line first, with bit 7 as the leftmost pixel — exactly the same convention as the sprite data in Chapter 6. The whole font is 96 × 8 = 768 bytes and lives at $3D00–$3FFF. The glyph for character code c starts at $3C00 + 8c:

The ROM keeps $3C00 — the address the glyph for code 0 would have if the font were complete — in the system variable CHARS at address 23606. Our routines use the same idea, for the same reason: with a base that is "code 0", the address of any glyph is just base + 8 × code, with no subtraction of 32 to get wrong. The bytes of the letter A show what a glyph looks like:

; the glyph for "A" at $3E08
;   $00   . . . . . . . .
;   $3C   . . # # # # . .
;   $42   . # . . . . # .
;   $42   . # . . . . # .
;   $7E   . # # # # # # .
;   $42   . # . . . . # .
;   $42   . # . . . . # .
;   $00   . . . . . . . .

Notice that the glyph leaves the top and bottom scan lines and the rightmost column blank. That built-in spacing is why text printed in adjacent cells reads cleanly, and it is also what makes the bold transformation later in this chapter possible.

Character Cell Addresses

Text is positioned by character cell, not by pixel: row 0–23, column 0–31. The address of a cell's top scan line uses the same field layout as always — 010TT000 in H and RRRCCCCC in L — but because a cell is already aligned to a byte column and a scan-line-0 boundary, no x shifting or masking is needed. The character row r splits into TT (r AND %00011000) and RRR (r AND %00000111). The three RRCA instructions that line RRR up in bits 7–5 do the same wrap-around trick as calc_pixel_addr: the AND beforehand guarantees that only the three wanted bits can wrap.

Once you have the address of scan line 0, the other seven scan lines of the same cell are at +$100, +$200 … +$700: INC H. This is the one place where INC H is always safe, because the low three bits of H hold the scan line and a cell never reaches scan line 8. (A sprite that is more than 8 rows tall has to use the full row-advance logic from Chapter 6.)

draw_glyph.asm

; draw_glyph
; Draw one 8x8 glyph into a character cell, replacing whatever was there.
; Input:  DE = pointer to 8 glyph bytes (top scan line first)
;         B  = character row    (0–23)
;         C  = character column (0–31)
; Output: none
; Destroys: A, B, D, E, H, L
draw_glyph:
    LD   A, B
    AND  %00011000         ; TT field of the row: 0, 8 or 16
    OR   %01000000         ; H = 010TT000  (scan line 0)
    LD   H, A
    LD   A, B
    AND  %00000111         ; RRR = row within its third
    RRCA                   ; }
    RRCA                   ; } rotate right 3 = shift left 5: A = RRR00000
    RRCA                   ; }
    OR   C                 ; add the column: A = RRRCCCCC
    LD   L, A
    LD   B, 8              ; eight scan lines per cell
dg_loop:
    LD   A, (DE)           ; next glyph byte
    LD   (HL), A           ; write it to the current scan line
    INC  DE
    INC  H                 ; next scan line (safe: stays inside one cell)
    DJNZ dg_loop
    RET

Save this as lib/draw_glyph.asm. It needs no other library file. It draws any eight bytes — a letter, a user-defined graphic, a piece of a tile map — and replaces the cell: the byte is stored, not OR'd, so whatever was there before is gone. That is the right behaviour for text, and it makes the routine very fast: eight loads and eight stores, and no address arithmetic per row.

print_char.asm

; print_char
; Print one character from the current character set into a character cell.
; Input:  A = character code (32–127)
;         B = character row    (0–23)
;         C = character column (0–31)
; Output: none
; Destroys: A, B, D, E, H, L
; Requires draw_glyph.asm.
print_char:
    LD   L, A
    LD   H, 0
    ADD  HL, HL            ; * 2
    ADD  HL, HL            ; * 4
    ADD  HL, HL            ; * 8: eight bytes per glyph
    LD   DE, (charset_ptr) ; address of the glyph for code 0 (font base - 256)
    ADD  HL, DE            ; HL = address of this character's glyph
    EX   DE, HL            ; DE = glyph pointer for draw_glyph
    JP   draw_glyph

; The default points at the ROM font: glyph for code 32 is at $3D00,
; so the "code 0" address is $3D00 - 32*8 = $3C00.  This is the same value
; the ROM keeps in the CHARS system variable (address 23606).
charset_ptr: DW $3C00

Save this as lib/print_char.asm; it requires draw_glyph.asm. Multiplying the character code by 8 takes three ADD HL, HL instructions. The character-set pointer is read from memory, not hard-coded, so the very same routine prints ROM text, generated fonts and your own fonts: a program switches fonts by storing a different value in charset_ptr. The final JP draw_glyph is a tail call — draw_glyph's RET returns directly to the caller of print_char.

print_string.asm

; print_string
; Print a zero-terminated string, wrapping to the next row after column 31.
; Input:  HL = pointer to the string (bytes 32–127, ended by a 0 byte)
;         B  = starting character row    (0–23)
;         C  = starting character column (0–31)
; Output: none
; Destroys: A, B, C, D, E, H, L
; The caller must keep the text on the screen: rows beyond 23 are not checked.
; Requires print_char.asm and draw_glyph.asm.
print_string:
    LD   A, (HL)
    OR   A
    RET  Z                 ; zero byte: end of string
    INC  HL
    PUSH HL                ; print_char destroys HL
    PUSH BC                ; ... and B
    CALL print_char
    POP  BC
    POP  HL
    INC  C                 ; next column
    LD   A, C
    CP   32
    JR   C, print_string   ; still on this row
    LD   C, 0              ; wrap to the start of the next row
    INC  B
    JR   print_string

Save this as lib/print_string.asm; it requires print_char.asm and draw_glyph.asm. Strings are stored with DB "TEXT", 0: the zero byte marks the end, so no length needs to be passed. print_char destroys B (draw_glyph uses it as a counter) and HL, so both are saved on the stack around the call. When the column reaches 32 the routine wraps to column 0 of the next row. It does not check for row 24, so keep text on the screen.

Colouring Text: fill_attr_cells.asm

Printing writes only the pixel bytes; the colour of each cell comes from its attribute byte (Chapter 2). Setting a run of cells with set_attr would mean converting cell numbers into pixel coordinates and back again, so there is a small routine that works in cell units directly:

; fill_attr_cells
; Set a run of attribute cells on one character row to the same value.
; Input:  A = attribute byte
;         B = character row    (0–23)
;         C = first column     (0–31)
;         E = number of cells  (1–32; 0 does nothing)
; Output: none
; Destroys: A, B, D, E, H, L
fill_attr_cells:
    LD   D, A              ; park the attribute while we test the count
    LD   A, E
    OR   A
    RET  Z                 ; nothing to do (DJNZ with B=0 would loop 256 times)
    LD   A, D
    PUSH AF                ; keep the attribute across the address arithmetic
    LD   H, 0
    LD   L, B
    ADD  HL, HL            ; row * 2
    ADD  HL, HL            ; row * 4
    ADD  HL, HL            ; row * 8
    ADD  HL, HL            ; row * 16
    ADD  HL, HL            ; row * 32
    LD   B, E              ; B = cell count (the row number is no longer needed)
    LD   D, 0
    LD   E, C
    ADD  HL, DE            ; + column
    LD   DE, $5800
    ADD  HL, DE            ; HL = address of the first attribute cell
    POP  AF
fac_loop:
    LD   (HL), A
    INC  HL
    DJNZ fac_loop
    RET

Save this as lib/fill_attr_cells.asm. The attribute for cell (row, col) is at $5800 + row×32 + col: five doublings of the row number give row×32 in HL, and the column is added as a 16-bit value so the result cannot overflow (row 23 × 32 is already 736). The count is tested against zero first, because DJNZ with B = 0 would run 256 times and write colour over the next several character rows.

Custom Character Sets

Because print_char looks up its glyphs through charset_ptr, a custom character set is nothing more than 8 bytes per character somewhere in RAM and one store:

    LD   HL, my_font - 256    ; address "code 0" would have: base - 32 * 8
    LD   (charset_ptr), HL
    ...
my_font:                      ; glyph for code 32 (space) comes first
    DB   0, 0, 0, 0, 0, 0, 0, 0
    DB   ...

The subtraction is done by the assembler. If your font only covers part of the range — say just the digits and a few symbols — put those glyphs in a table and compute the base as table - first_code * 8; only codes inside the table may then be printed.

Generating a Font: make_bold.asm

You do not have to draw a whole font by hand. Many useful variants can be computed from the ROM font when the program starts, and stored in a 768-byte RAM buffer. The simplest is bold: OR each glyph byte with itself shifted right by one pixel, which thickens every vertical stroke by one column. It works because the ROM glyphs leave their rightmost column empty:

; make_bold
; Build a bold version of the ROM font in RAM.
; Each glyph byte is OR'd with itself shifted one pixel to the right,
; which thickens every vertical stroke by one pixel.
; Input:  HL = destination buffer (768 bytes: 96 glyphs x 8 bytes)
; Output: none
; Destroys: A, B, C, D, E, H, L
; Use it by pointing charset_ptr at (buffer - 256).
make_bold:
    LD   DE, $3D00         ; ROM glyph for code 32
    LD   BC, 768           ; 96 glyphs * 8 bytes
mb_loop:
    LD   A, (DE)
    LD   (HL), A           ; copy the original byte
    RRCA                   ; shift right one pixel (bit 0 wraps into bit 7)
    AND  %01111111         ; discard the wrapped bit
    OR   (HL)              ; merge with the original
    LD   (HL), A
    INC  DE
    INC  HL
    DEC  BC
    LD   A, B
    OR   C
    JR   NZ, mb_loop
    RET

Save this as lib/make_bold.asm. RRCA rotates, so the pixel that falls off the right end re-enters at bit 7; the AND %01111111 throws that pixel away. The result is merged with the original byte by OR (HL) — the original was stored at (HL) a moment earlier, since the Z80 can only OR with memory through HL. The loop counts 768 bytes in BC, so it tests for zero with LD A, B / OR C: DEC BC does not set the Zero flag.

The same approach gives italics (shift the top rows right and the bottom rows left by one pixel), outline, underline (set the last scan line) or inverse text (CPL each byte). Each is a short loop over the 768 bytes.

User Defined Graphics (UDGs)

A user defined graphic is simply a glyph that is not a letter: a heart, a brick, a smiling face, a piece of a border. On the Spectrum, BASIC lets you define 21 of them and print them with CHR$ 144 to CHR$ 164. In assembly there is nothing special about them at all — draw_glyph takes a pointer to any eight bytes, so a UDG is eight DB lines and a label:

udg_heart:
    DB %00000000
    DB %01100110
    DB %11111111
    DB %11111111
    DB %11111111
    DB %01111110
    DB %00111100
    DB %00011000

Writing the bytes in binary lets you see the picture in the source. A UDG is not limited to one cell: a bigger graphic is a rectangle of cells, each drawn with its own draw_glyph call, and a tile map — a level made of repeated bricks, floors and ladders — is a table of bytes that selects which glyph goes into which cell.

How does this compare with the sprites of Chapter 6? A UDG is locked to the 8×8 grid, has no mask, and replaces its cell instead of blending with the background. In exchange it costs a fraction of the time and needs no clipping, because a valid cell is always entirely on the screen. That makes UDGs the right tool for HUD elements, tile-based backgrounds and anything that never needs to move by single pixels.

9. Double Buffering & Flicker-Free Animation

^ Back to top

Chapter 6 animated a sprite by erasing it and drawing it again, and Chapter 7 warned that the same approach breaks down when a lot of work happens between the erase and the redraw. The cause is the display itself: the ULA reads the display file continuously, fifty times a second, in step with the electron beam. Anything you change on screen can be caught by the beam half-way through. If the beam passes while a sprite is erased, the viewer sees a gap; if it passes while a sprite is half drawn, the viewer sees part of the new picture and part of the old. This chapter removes both problems by never letting the beam see unfinished work.

Off-Screen Buffer Techniques

The idea is simple: build the next frame in a block of memory that is not being displayed, and show it only when it is complete. On a 48K Spectrum the buffer is a 6,144-byte area that has exactly the same layout as the display file, so all the address arithmetic you already have still works. In this book the buffer lives at $A000–$B7FF, above the program.

The buffer layout is identical to the screen layout, so an address in the buffer differs from the matching screen address only in the high byte. The display file's high byte is 010TTLLL; the buffer's is 101TTLLL. Adding a constant to H moves any screen address into the buffer, without disturbing the TT and LLL fields, as long as the constant leaves the five low bits of the base zero (the row-advance code only ever touches those five bits). The constant is kept in a variable, draw_offset, so one routine can draw to several places:

$00the screen at $4000drawing directly (no buffer)
$60the buffer at $A00048K double buffering (the default)
$80bank 7 at $C000128K page flipping, later in this chapter

draw_sprite_masked_buf.asm

This is draw_sprite_masked from Chapter 6 with one change: after calc_pixel_addr returns the screen address, the offset is added to H. Everything else — the AND-then-OR masking, the row-advance logic — is unchanged.

; draw_sprite_masked_buf
; Draw a masked, character-aligned sprite into an off-screen display buffer.
; Identical to draw_sprite_masked except that the address is moved into the
; buffer by adding draw_offset to the high byte of the display address.
;
;   draw_offset = $00  draw straight to the screen at $4000
;   draw_offset = $60  draw to a buffer at $A000   (48K double buffering)
;   draw_offset = $80  draw to bank 7 at $C000     (128K page flipping)
;
; Input:  B  = y (0–191)   C = x (multiple of 8)
;         IX = masked sprite descriptor (see draw_sprite_masked)
; Destroys: A, B, C, D, E, H, L, IX
draw_sprite_masked_buf:
    LD   A, (IX+0)
    OR   A                 ; height = 0?
    RET  Z                 ; nothing to draw
    LD   (dmb_rows), A
    LD   A, (IX+1)
    LD   (dmb_width), A
    INC  IX                ; skip height byte
    INC  IX                ; skip width byte

    CALL calc_pixel_addr   ; HL = screen address of (y, x)
    LD   A, (draw_offset)
    ADD  A, H              ; move the address into the buffer
    LD   H, A

dmb_row_loop:
    PUSH HL                ; save start-of-row address
    LD   A, (dmb_width)
    LD   B, A
dmb_col_loop:
    LD   A, (IX+0)         ; AND mask byte
    AND  (HL)              ; punch a hole in the background
    LD   D, A
    INC  IX
    LD   A, (IX+0)         ; OR pixel byte
    OR   D                 ; fill the hole with sprite pixels
    LD   (HL), A
    INC  IX
    INC  L
    DJNZ dmb_col_loop
    POP  HL

    LD   A, H              ; step down one pixel row (same logic as draw_sprite)
    AND  $07
    CP   $07
    JR   Z, dmb_cross
    INC  H
    JR   dmb_row_dec
dmb_cross:
    LD   A, H
    AND  $F8               ; back to scan line 0
    LD   H, A
    LD   A, L
    ADD  A, $20            ; next character row within the third
    LD   L, A
    JR   NC, dmb_row_dec
    LD   A, H
    ADD  A, $08            ; next third
    LD   H, A
dmb_row_dec:
    LD   A, (dmb_rows)
    DEC  A
    LD   (dmb_rows), A
    JR   NZ, dmb_row_loop

dmb_rows:    DB 0
dmb_width:   DB 0

Save this as lib/draw_sprite_masked_buf.asm; it requires calc_pixel_addr.asm. The sprite format is exactly the masked format from Chapter 6. The routine also returns immediately for a sprite of height zero, which would otherwise draw 256 rows.

; clear_buffer

copy_cells.asm

Copying the whole buffer to the screen is the obvious last step, but it is also the slow step: LDIR costs 21 T-states per byte, so 6,144 bytes take about 129,000 T-states — nearly two whole frames (a frame is 69,888 T-states). Copying everything every frame would be slower than drawing directly. The practical answer is to copy only the part of the screen that changed. Because the buffer and the screen have the same layout, a rectangle of character cells is just eight LDIRs, one per scan line, each as wide as the rectangle:

; copy_cells
; Copy a rectangle of character cells from the off-screen buffer to the screen.
; Input:  B = first character row     (0–23)
;         C = first character column  (0–31)
;         D = height in character rows (1–24)
;         E = width in cells           (1–32)
; Output: none
; Destroys: A, B, C, D, E, H, L
; Requires draw_sprite_masked_buf.asm (for draw_offset).
copy_cells:
    LD   A, E
    LD   (cc_width), A
    LD   A, D
    LD   (cc_rows), A

    LD   A, B              ; HL = screen address of the first cell, scan line 0
    AND  %00011000
    OR   %01000000
    LD   H, A
    LD   A, B
    AND  %00000111
    RRCA
    RRCA
    RRCA
    OR   C
    LD   L, A

cc_row:
    LD   B, 8              ; eight scan lines per character row
cc_scan:
    PUSH BC
    PUSH HL                ; remember this scan line's screen address
    LD   D, H
    LD   E, L              ; DE = destination (screen)
    LD   A, (draw_offset)
    ADD  A, H
    LD   H, A              ; HL = source (buffer)
    LD   A, (cc_width)
    LD   C, A
    LD   B, 0
    LDIR                   ; copy one scan line of the rectangle
    POP  HL
    POP  BC
    INC  H                 ; next scan line of this character row
    DJNZ cc_scan

    LD   A, H              ; eight INC H have moved us to the next 8-block:
    SUB  8                 ; step back to scan line 0 of this character row
    LD   H, A
    LD   A, L
    ADD  A, $20            ; next character row
    LD   L, A
    JR   NC, cc_same_third
    LD   A, H
    ADD  A, 8              ; crossed into the next third
    LD   H, A
cc_same_third:
    LD   A, (cc_rows)
    DEC  A
    LD   (cc_rows), A
    JR   NZ, cc_row
    RET

cc_width: DB 0
cc_rows:  DB 0

Save this as lib/copy_cells.asm; it requires draw_sprite_masked_buf.asm for draw_offset. The routine keeps the destination in DE and builds the source by adding the offset to H. After eight INC H steps the address has moved to the next 8-block, so the routine subtracts 8 to get back to scan line 0 of the same character row, and then adds $20 to step to the next character row — carrying into the third field exactly as the sprite routines do.

Synchronising to the Vertical Blank

A buffer removes the half-drawn sprite, but the copy into the screen can still be caught by the beam. To avoid that, the copy has to happen at the right moment in the frame. The ULA generates an interrupt at the start of every frame, and the Z80 instruction HALT stops the processor until the next interrupt arrives — so after an EI, a single HALT is a frame synchroniser:

    EI                       ; interrupts must be enabled
frame:
    ...                      ; build the next frame in the buffer
    HALT                     ; wait here until the next frame interrupt
    ...                      ; copy to the screen now
    JR   frame

Here is the timing of a 48K frame, in T-states at 3.5 MHz:

EventTime after the interrupt
Interrupt fires (the ROM's handler runs: frame counter, keyboard scan)0
Beam reaches the first pixel row (64 lines × 224 T-states)14,336
Beam reaches pixel row y14,336 + 224 × y
Beam finishes the last pixel row57,344
Frame ends, next interrupt69,888

The rule that follows is: a region of the screen can be updated without tearing if the update is finished before the beam reaches that region's first pixel row. Right after HALT the beam is nowhere near the picture. A character row near the top of the screen gives you 14,336 T-states minus the interrupt handler; a row lower down gives you 1,792 more for every character row. A character row copied with copy_cells costs roughly 6,500 T-states (256 bytes at 21 T-states, plus about 1,000 of loop overhead), so one or two rows at the top are safe, and a row in the middle of the screen has several times the time it needs. The budget is the reason that the example below copies only the rows the sprite touches.

The 128K Spectrum has a slightly different frame (70,908 T-states) and ULA timing, but the same principle applies.

Measuring with the Border

To see how long a piece of code takes, bracket it with writes to the border port. The colour change takes effect at the beam's current position, so the height of each coloured band on the border is the duration of the code:

    LD   A, 2                ; red
    OUT  ($FE), A            ; border red from this moment...
    CALL my_routine
    XOR  A                   ; black
    OUT  ($FE), A            ; ...until this moment

If the red band is taller than a frame, the routine takes more than a frame, and a frame-locked animation will drop to half speed. This technique is used in the Chapter 10 example as well.

Walkthrough

Background. init_bg fills the buffer one 256-byte page at a time. Bit 0 of the high byte is bit 0 of the scan line number, so alternating pages get $AA and $55, giving a checkerboard on every scan-line pair. restore_row redraws the same pattern on character row 12 only, which is cheaper than redrawing the whole background: this is how the sprite is erased.

Frame order. The expensive work — restoring the row and drawing the sprite — comes before HALT, while the previous frame is being displayed. The only thing after HALT is the short copy. If the drawing ever took longer than a frame, HALT would simply wait for the following frame and the animation would slow down; it could never tear. The position is updated only once every third frame so that the 8-pixel steps are easy to follow.

Why the copy is safe. Row 12 starts at pixel row 96, so the beam does not reach it until 14,336 + 224 × 96 = 35,840 T-states after the interrupt. The copy begins within a couple of thousand T-states of the interrupt and takes roughly 6,500, so it finishes with plenty of margin.

Page Flipping

Copying from a buffer is the best a 48K machine can do, and it only works well for small areas. The 128K Spectrum offers something better: two complete screens, and a hardware switch that chooses which one the ULA displays. Instead of copying a finished frame onto the screen, you draw into the screen that is not being displayed and then flip the switch. The flip costs a few T-states, whatever the size of the picture.

ScreenRAM bankAddress (when paged in)Attributes at
Normal screen5$4000 (always)$5800
Shadow screen7$C000 (bank 7 paged in)$D800

Port $7FFD controls the memory layout. Bits 0–2 choose which RAM bank appears at $C000, bit 3 chooses which screen the ULA displays (0 = bank 5, 1 = bank 7), bit 4 selects the ROM, and bit 5 locks the paging. The ROM keeps a copy of the last value written in the system variable BANKM ($5B5C), and a program must update it with every write or any ROM routine that does its own paging will undo the change.

flip_screen.asm

; flip_screen / init_page_flip
; 128K Spectrum only.  The 128K machine has two screens: the normal one in
; bank 5 (always at $4000) and a shadow screen in bank 7.  Bit 3 of port $7FFD
; chooses which one the ULA displays.  Bank 7 can be written through the
; $C000–$FFFF window, so with bank 7 paged in the program can draw into the
; hidden screen at $C000 and then flip.
;
; init_page_flip: page bank 7 in at $C000, display bank 5, draw to bank 7.
; flip_screen:    swap the displayed screen and retarget draw_offset at the
;                 screen that is now hidden.  Call it straight after a HALT.
; Input: none      Output: none      Destroys: A, B, C
; Requires draw_sprite_masked_buf.asm (for draw_offset).
BANKM EQU $5B5C            ; 128K system variable: copy of the last OUT to port $7FFD

init_page_flip:
    DI
    LD   A, (BANKM)
    AND  %11110000         ; keep the ROM-select (bit 4) and paging-lock (bit 5) bits
    OR   %00000111         ; bits 2-0 = 7: bank 7 at $C000; bit 3 = 0: show bank 5
    LD   (BANKM), A
    LD   BC, $7FFD
    OUT  (C), A
    EI
    LD   A, $80            ; displayed = bank 5, so draw into $C000
    LD   (draw_offset), A
    RET

flip_screen:
    DI                     ; the update of BANKM and the port must stay together
    LD   A, (BANKM)
    XOR  %00001000         ; bit 3: 0 = display bank 5, 1 = display bank 7
    LD   (BANKM), A
    LD   BC, $7FFD
    OUT  (C), A
    EI
    AND  %00001000         ; Z set: bank 5 is now displayed, so draw to bank 7
    LD   A, $80            ; (LD does not touch the flags)
    JR   Z, fs_store
    XOR  A                 ; bank 7 is displayed: draw straight to $4000
fs_store:
    LD   (draw_offset), A
    RET

Save this as lib/flip_screen.asm; it requires draw_sprite_masked_buf.asm for draw_offset. init_page_flip maps bank 7 at $C000, displays bank 5, and points draw_offset at $80 — so draw_sprite_masked_buf adds $80 to a $4x address and lands at $Cx. flip_screen toggles bit 3, writes the new value to both BANKM and the port, and then retargets draw_offset: $80 when bank 5 is on show (draw into bank 7), $00 when bank 7 is on show (draw straight to $4000). Interrupts are disabled around the update so an interrupt cannot fall between the two writes.

A complete frame then looks like this:

    CALL init_page_flip      ; once, at the start
    EI
frame:
    CALL clear_buffer        ; wipe the hidden screen
    ...                      ; draw the whole frame with draw_sprite_masked_buf
    HALT                     ; wait for the start of the next frame
    CALL flip_screen         ; show it; the screen just shown becomes the target
    JR   frame

There are four things to remember. It needs a 128K machine — on a 48K Spectrum port $7FFD does nothing, and $C000 is ordinary RAM. Each screen has its own attribute area, so the colours at $5800 must be copied to $D800 (LDIR, 768 bytes) before the first flip, and every later colour change must be made on the hidden page. Banks 1, 3, 5 and 7 are contended on the 128K machine, so code and data accessed there run slower when the ULA is reading it. And the flip happens after HALT, so if drawing takes longer than a frame the program simply misses a flip and runs at 25 frames per second — still without tearing, which is the whole point.

The code in this section has not been run on 128K hardware or an emulator: build it, and test it on your own.

10. Graphics Optimisation

^ Back to top

A Spectrum frame is 69,888 T-states. Clearing the screen the obvious way takes nearly two of them. This chapter is about where that time goes and three standard ways to win it back: choosing the right block-copy method, unrolling loops, and replacing calculations with table look-ups. Each technique trades something — code size, memory or flexibility — for speed, so the chapter also says when not to use it.

Using LDIR for Block Copies

LDIR is the Z80's block-copy instruction: it copies the byte at (HL) to (DE), increments both, decrements BC, and repeats until BC is zero. One instruction replaces a loop, and it is what scroll_up_char and clear_buffer use. Three rules keep it safe:

  • BC = 0 means 65,536 bytes, not zero. Check the count first if it can be zero.
  • Overlapping copies have a direction. If the destination is above the source and the blocks overlap, LDIR overwrites bytes before it reads them; copy backwards with LDDR, starting at the ends of the blocks.
  • A fill is a copy onto itself. Store the value in the first byte and set DE = HL + 1: each copied byte becomes the source of the next. clear_buffer does this.

But LDIR is not fast. It takes 21 T-states for every byte it copies (16 for the last). Here is what a full 6,144-byte screen costs with each method, using the fastest loop of each kind:

The reason PUSH wins is that it writes two bytes in 11 T-states and needs no pointer increment: the stack pointer decrements itself. The trick is to aim SP at the screen. The stack grows downwards, so start at the end of the area to fill and push towards the start.

clear_screen_fast.asm

; clear_screen_fast
; Clear the whole 6144-byte display file by pushing zeros onto the screen.
; PUSH HL writes two bytes in 11 T-states (5.5 per byte); LDIR needs 21.
; Input:  none      Output: none
; Destroys: B, H, L.  Leaves interrupts ENABLED.
; Interrupts are disabled while SP points into the display file, because an
; interrupt would push its return address on top of the pixels.
clear_screen_fast:
    DI
    LD   (csf_sp), SP      ; save the real stack pointer
    LD   SP, $5800         ; one past the end of the display file
    LD   HL, 0
    LD   B, 192            ; 192 passes of 16 PUSHes = 192 * 32 bytes = 6144
csf_loop:
    REPT 16
    PUSH HL                ; SP -= 2, (SP) = HL: two zero bytes
    ENDM
    DJNZ csf_loop
    LD   SP, (csf_sp)      ; restore the real stack
    EI
    RET
csf_sp: DW 0

Save this as lib/clear_screen_fast.asm. Note the three safety rules for stack tricks. Interrupts must be off while SP points into the display file: an interrupt pushes its return address on the stack, and the ROM's handler would write over your pixels. SP must be saved and restored — here through a memory variable — or the RET would jump to an arbitrary place. And the routine ends with EI, so it is only for programs that run with interrupts enabled; that is true of every example in this book.

The inner block of 16 PUSH HLs is produced by the assembler's REPT 16 ... ENDM repetition directive (pasmo syntax; other assemblers call it DUP/EDUP or similar), and DJNZ repeats it 192 times: 192 × 32 = 6,144 bytes. HL does not have to be zero: any 16-bit pattern can be pushed, so the same routine fills the screen with a stripe or checkerboard pattern, and the same idea with SP = $5B00 and 384 pushes fills the attribute file.

This trick only fills; it cannot copy, because the data has to come from somewhere other than SP. For copies the choice is LDIR (small and convenient) or a run of unrolled LDIs (about a quarter faster, but 2 bytes of code per byte copied).

Loop Unrolling

Look at the cost of a simple fill loop, such as the inner loop of fill_screen_attr:

inner:
    LD   (HL), A      ; 7 T-states: the useful work
    INC  HL           ; 6
    DJNZ inner        ; 13: the loop overhead

Only 7 of the 26 T-states per byte do any work; the INC HL and especially the 13-T-state DJNZ are overhead. Unrolling means writing the body several times in a row, so the DJNZ is paid once per several bytes instead of once per byte:

; fill_screen_attr_fast
; Same job as fill_screen_attr, with the inner loop unrolled eight times.
; Input:  A = attribute byte
; Output: none
; Destroys: B, HL
fill_screen_attr_fast:
    LD   HL, $5800        ; start of attribute file
    LD   B, 96            ; 96 passes of 8 bytes = 768 bytes
fsaf_loop:
    REPT 8
    LD   (HL), A
    INC  HL
    ENDM
    DJNZ fsaf_loop
    RET

Save this as lib/fill_screen_attr_fast.asm. It is a drop-in replacement for fill_screen_attr. Eight bytes now cost 8 × 13 + 13 = 117 T-states, about 14.6 per byte, so filling the 768 attribute bytes takes roughly 11,000 T-states instead of 20,000. The returns diminish quickly:

Most of the gain comes in the first doubling or two; beyond 8 copies you are spending memory for under a T-state per byte. The count must divide the amount of work evenly (96 × 8 = 768 here), or you need a separate leftover loop.

Where to Unroll

Unroll inner loops that run thousands of times per frame, and nothing else. A horizontal scroll is a good candidate: the inner loop of scroll_left_pixel does RL (HL) / DEC L / DJNZ, which is 15 + 4 + 13 = 32 T-states per byte. A row is exactly 32 bytes, so writing RL (HL) / DEC L 32 times in a row removes the DJNZ entirely and cuts the cost to 19 T-states per byte — about 41% less, and the whole scroll falls from roughly 56 ms to roughly 33 ms. The price is 96 bytes of code instead of 5. Try it as an exercise; the hard part is the carry flag, which must flow through the whole run unharmed (DEC L does not touch the carry flag, which is why this works).

Do not unroll code that runs rarely, code that is already dominated by something else (such as an LDIR), or code where the loop count varies — unless the variable part is handled by jumping into the middle of the unrolled block, a classic trick known as Duff's device.

Lookup Tables for Screen Addresses

Every call to calc_pixel_addr works out the same bit-shuffling from scratch: about 150 T-states, plus 17 for every bit of x mod 8 in the mask-shift loop. For code that needs one address per pixel, such as draw_circle or draw_line, that is where nearly all the time goes. A lookup table does the work once, at start-up, and turns every later calculation into a memory read.

There are only 192 pixel rows, and the address of the start of each row never changes. A table of 192 two-byte addresses costs 384 bytes of RAM:

build_row_table.asm

; build_row_table
; Fill a 192-entry table of display-file row addresses.
; Entry y (two bytes, low byte first) is the address of the first byte of
; pixel row y.  Needs 384 bytes at row_table, which the program must define
; with EQU (or allocate itself) before including this file.
; Input:  none      Output: none
; Destroys: A, B, C, D, E, H, L
; Requires calc_pixel_addr.asm.
build_row_table:
    LD   DE, row_table     ; DE = where the next entry goes
    XOR  A
    LD   (brt_y), A
brt_loop:
    LD   A, (brt_y)
    LD   B, A              ; B = y
    LD   C, 0              ; C = x = 0
    PUSH DE
    CALL calc_pixel_addr   ; HL = address of the start of row y
    POP  DE
    EX   DE, HL            ; HL = table pointer, DE = row address
    LD   (HL), E           ; low byte
    INC  HL
    LD   (HL), D           ; high byte
    INC  HL
    EX   DE, HL            ; DE = table pointer again
    LD   A, (brt_y)
    INC  A
    LD   (brt_y), A
    CP   192
    JR   NZ, brt_loop
    RET
brt_y: DB 0

Save this as lib/build_row_table.asm; it requires calc_pixel_addr.asm. The program must define row_table (for example row_table EQU $9000) and keep 384 bytes free there. Call build_row_table once; it uses the routine you already trust to generate the data, so the table cannot disagree with it.

get_row_addr.asm

; get_row_addr
; Look up the display-file address of the start of pixel row y.
; Input:  B  = y (0–191)
; Output: HL = address of the first byte of that row
; Destroys: DE
; Requires the table built by build_row_table.
get_row_addr:
    LD   H, 0
    LD   L, B
    ADD  HL, HL            ; y * 2: each entry is a word
    LD   DE, row_table
    ADD  HL, DE            ; HL = address of the table entry
    LD   E, (HL)
    INC  HL
    LD   D, (HL)
    EX   DE, HL            ; HL = row address
    RET

Save this as lib/get_row_addr.asm. Doubling y gives the byte offset of the entry, because each entry is two bytes. The whole look-up costs about 77 T-states, plus 17 for the CALL — and unlike calc_pixel_addr its speed does not depend on x. Add the column byte (x / 8) to L to reach any byte on the row, which is always safe because a row never crosses a 256-byte boundary.

The same idea applies wherever the answer comes from a small set of possibilities:

  • Pixel masks: a table of the eight values $80, $40, ... $01 replaces the shift loop in calc_pixel_addr. If the table starts on a 256-byte boundary, the look-up is just AND 7 / LD L, A / LD H, high_byte / LD A, (HL).
  • Attribute rows: 24 entries give the address of each attribute row.
  • Pre-shifted sprites: eight copies of a sprite, one for each pixel offset within a byte, so a sprite at any x position is drawn with the OR/AND loop instead of shifting every byte at run time. This trades memory (eight times the sprite data) for speed.
  • Multiplication, sine and square tables for anything that multiplies or rotates.

The cost to weigh is memory. 384 bytes is cheap on a 48K machine and a bargain next to the time saved, but pre-shifted sprites multiply every sprite by eight, and a 16-bit table costs two bytes per entry.
